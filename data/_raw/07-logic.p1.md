## [g-horizontal] 水平越权——只校验了登录，没校验"这是你的"

### [h-idor-principle] 水平越权原理与前提 | medium | 水平越权;IDOR | 对象级授权缺失
> 后端只验证"已登录"，未验证资源归属，导致任意用户可读写他人数据。

#### 这个条目的作用
先看懂水平越权（IDOR）为什么会存在，才能在测试时一眼认出它。它不靠什么高深技巧，本质只有一句话：**服务端把"对象 ID"当成了访问凭证**。你登录后拿到合法会话，然后动手把请求里的资源 ID（用户 id、订单号、文件编号）换成别人的，服务端只检查"你登录了没"，不检查"这东西是不是你的"，就把数据原样返回。

#### 前置条件
- 一个可登录的普通账号（不需要管理员）
- Burp Suite 或任意抓包工具，能改包重放
- 知道几个资源 ID 的样本（自己的、或任意能看到订单号/用户编号的场合）

#### 第 1 步：看懂触发链（操作：先在脑子里过一遍，不需要动手）
水平越权成立需要同时满足三个条件，缺一不可：
1. **资源 ID 可预测**：自增数字 id、连续订单号、时间戳拼接的编号——你能猜到别人的 ID 长什么样。
2. **ID 在请求中明文传递**：出现在 URL 路径 `/api/user/10086/info`、GET 参数 `?uid=10086`、或 JSON body `{"userId": 10086}` 里，而不是服务端自己从会话里取。
3. **服务端不做归属校验**：换掉 ID 后响应内容跟着变——这就是最直接的证据。

> [!tip] 判断归属校验是否缺失，别猜，看响应：把 id 换成别人的，响应体字段变多/变少、返回了"无权访问"以外的内容，都是"没校验归属"的信号。

#### 第 2 步：判断资源 ID 是否可预测（操作：登录后抓一个带 ID 的请求）
先登录账号，随便打开一个显示"个人信息/我的订单/我的文件"的页面，去 Burp 的 HTTP History 里找那个请求。看 ID 的形态：
- `id=1001`、`orderId=20240101001` 这类**顺序数字** → 可预测，直接遍历就能撞上别人的数据。
- `uuid 字符串`（如 `f5a8c2…`）→ 不可枚举，但可能通过其他接口泄露，或接口自己有列表页返回他人 ID，仍值得测替换。
- 预期结果：你能说出"下一个 ID 大概是什么"，就说明可预测。
- 如果不行：ID 全是随机串也先别放弃，重点转向"请求里能否直接指定 ID 而不被忽略"。

#### 第 3 步：确认 ID 明文传递且服务端信任（操作：改包换 ID 重放）
在 Burp Repeater 里打开抓到的请求，把 ID 改成另一个真实存在的值（比如自己的账号是 1001，改成 1002），发送后观察：
- **返回了 1002 的数据** → 水平越权（读），漏洞实锤。
- 返回 200 但数据为空 → 可能是软删除/权限过滤，换一个"确定存在"的 ID 再试一次确认。
- 返回 403/404/无权访问 → 说明这里有校验，换别的参数继续测（看 h-idor-detect）。

```http
GET /api/user/1002/profile HTTP/1.1
Host: target.com
Cookie: session=你自己的会话
```

#### 第 4 步：顺带检查"接口是否按角色区分"（操作：对比同一接口不同角色调用）
水平越权常与接口设计耦合：如果**所有角色共用同一个接口**（普通用户和管理员调的都是 `/api/user/{id}/info`），而服务端又不区分角色，那换 ID 就是通的。观察接口路径语义：`/api/user/{id}/profile`、`/api/order/{orderId}/detail`、`/api/file/{fileId}/download`，凡是"路径里直接带资源 ID"的接口，都默认列入越权候选。常见参数名记一份：`id`、`uid`、`userId`、`orderId`、`fileId`、`groupId`、`tenantId`。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 换了 id 返回 404 | 目标资源不存在，或接口对不存在资源统一 404 | 先确认目标 ID 真实存在（可从列表页/分享链接拿到） |
| 换了 id 还是返回自己的数据 | 服务端用 session 里的身份，忽略了请求里的 id | 属正常防护；把参数名换成 `userId`/`uid` 等变体再试一次 |
| 响应能换数据但页面不显示 | 前端用了自己的登录态渲染 | 别信页面，看 Burp 里的响应体是否包含他人数据 |
| 以为只有 GET 需要测 | 写接口（PUT/DELETE）越权危害更高 | 见 h-idor-detect，GET/POST/PUT/DELETE 全测 |

#### 实战要点
- 判断标准只有一个：**响应数据是否随"资源 ID"变化而属于不同的人**。
- ID 可预测 + 明文传递 + 不校验归属，三者齐了才是洞；只满足两个继续追。
- 路径里带 `{id}` 的接口是首选目标，body 里嵌套的 id（如 `{"order": {"id": 2}}`）同样要替换。
- 水平越权往往连坐：一个接口中招，同模型的十几个接口大概率全中，测出来要横向扩散。
- 写操作（改/删他人数据）比读操作危害高一个量级，复现时优先在测试账号之间做，别碰真实业务数据。

### [h-idor-detect] IDOR 检测流程 | medium | IDOR;越权检测 | 遍历
> 从功能点出发，系统化替换资源标识，用响应差异判定越权。

#### 这个条目的作用
把"碰运气试 ID"变成一条可复制的标准流程：两个账号 → Burp 抓包 → 替换 id → 对比响应，四步走完就能把常见 IDOR 面扫一遍，且每一步都有明确的预期结果和"如果不行"的备选动作。检测的本质是**制造差异并解释差异**：两个身份访问同一资源，响应不一样就是校验点，响应一样且数据属于对方就是漏洞。

#### 前置条件
- 两个普通账号 A、B（同角色、无权限差异即可，甚至注册两个新号），能分别登录
- Burp Suite（Proxy + Repeater + Comparer），或能改包重放的任意工具
- 知道自己账号的 ID 值（从任意带 id 的请求里能看到）

#### 第 1 步：登录两个账号，分别抓包确认会话可用（操作：浏览器 + Burp Proxy）
先开 Burp Proxy，浏览器走代理。依次做：
1. 用账号 A 登录，抓登录请求和登录后的首个业务请求，确认 A 的 Cookie 能访问业务。
2. 登出，用账号 B 登录，同样抓包确认 B 的会话。
3. 把 A、B 两个会话的 Cookie 分别复制到两个 Repeater Tab（或用 Burp 的 Session Handling 规则自动切换）。
预期结果：两个会话都能正常访问各自的数据。如果不行：换个浏览器无痕窗口分别登录，或检查代理是否生效（Burp 里能看到请求才算）。

#### 第 2 步：用 A 账号把业务功能走一遍，收集所有带资源 ID 的请求（操作：Burp 抓包）
用 A 账号在站点里逐一点击：查看个人信息、打开订单详情、上传/下载文件、查看收藏、修改资料。每点完一个动作，回 Burp 的 HTTP History，按域名过滤，把所有**请求路径或参数里带数字 ID / 业务编号**的请求标记出来。确认每个请求的三要素：
- 出处在哪（哪个页面动作触发的）
- ID 在什么位置（路径、GET 参数、还是 JSON body）
- 请求方法（GET/POST/PUT/DELETE）

> [!tip] 不要只抓 GET：修改资料、删除文件、改订单这些操作才是写接口，越权危害更高，必须每个都抓到包。

#### 第 3 步：记录基线响应（操作：Repeater 里原样发送 A 的请求）
把 A 的每个请求在 Repeater 里原样发送一次，记录三样东西：**状态码、响应体长度、响应里的关键字段**（比如"username": "A"）。这就是"正常基线"。建议把基线响应存成文件或用 Burp Comparer 保存，后面每一轮替换都能拿它对比。预期结果：每个请求都返回 A 自己的数据。如果不行：说明某些请求需要先调用前置接口（比如先创建订单才有订单 id），把前置流程走通再抓。

#### 第 4 步：替换 ID 为 B 的，对比响应（操作：Repeater 改 id → 发送 → 对比）
拿第 2 步收集的每个请求，逐一把 ID 换成 B 的（路径参数、GET 参数、body 里的字段都换），发送后和基线对比：
- 返回 B 的数据（能看到 B 的用户名/订单内容）→ **水平越权（读），命中**。
- 返回 200 但数据为空 → 可能软删除或权限过滤，换一个 B 的真实 ID（先从 B 的列表页确认 B 的 ID 确实存在）再试。
- 返回 403/404/无权访问 → 这个参数有校验，记录"已防护"，继续测其他参数、其他请求。
- 响应完全没变化（还是 A 的数据）→ 服务端忽略了这个 id，改用可信会话，属正常防护。

```http
GET /api/user/10086/profile HTTP/1.1
Host: target.com
Cookie: session=账号A的会话
# 把 10086 改成账号 B 的 id 再发送，响应里若出现 B 的用户名即越权
```

#### 第 5 步：边界与批量探测（操作：换不存在 id、0、all、省略 id）
同一请求继续做四组替换，看是否有"通配/全量返回"的意外分支：
- `id=0`、`id=-1`：有些框架把非正数当"不限"。
- `id=99999999`（不存在的超大 id）：返回 404 正常，返回 200+空列表说明没做存在性校验。
- `id=all`、`id=*`、省略 id 参数：部分实现会返回全量数据。
- 批量接口 `?ids=1,2,3`：把数组元素逐个换成别人的 ID。

#### 第 6 步：写接口同样测（操作：对修改/删除类请求替换 ID）
对收集到的 PUT/POST/DELETE 请求重复第 4 步：改别人的资料、删别人的文件、修改他人订单状态。写接口危害更高，但**先在两个测试账号 A/B 之间验证**，确认命中后再评估是否需要在真实数据上做最小化验证。

> [!warn] 检测时避免直接修改真实业务数据。先读后写，写操作一律使用测试账号数据，确认漏洞后立即停止，截图留证走报告流程。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 替换 ID 后响应与基线一样 | 服务端从 session 取身份，忽略请求参数 | 换参数名变体（userId/uid/user_id）重试；若仍一样则记"已防护" |
| 只测了 GET，写接口全漏 | 抓包时没操作修改/删除功能 | 回到第 2 步，把每个业务动作都点一遍 |
| 只换了路径参数，body 嵌套 ID 没换 | 漏掉 `{"data": {"userId": 2}}` 这类结构 | 对请求体逐层检查所有数字字段 |
| 多级资源只换了一个 ID | `/api/order/2/user/3` 两个 ID 都要换 | 每个位置分别替换并组合替换 |
| 两个账号的 Cookie 搞混了 | 会话串号导致误判 | 每个请求发送前核对 Cookie 属于哪个账号 |
| 响应对比靠肉眼 | 数据多时看不出来 | 用 Burp Comparer，或记录状态码+长度+关键字段做成矩阵 |

#### 实战要点
- 完整四步：**登录两个账号 → 抓包 → 替换 id → 对比响应**，缺一步都可能误判"没洞"。
- 读接口命中记"水平越权（读）"，写接口命中记"水平越权（写）"，写优先验证、优先报告。
- 响应长度是最高效的差异信号：长度显著变化 ≈ 返回了不同数据。
- 同一 ID 出现在路径+参数+body 多处时，全部替换、逐个组合，别只改一处。
- 记全"已防护"的接口，避免重复劳动；把命中的请求原样保存在 Burp 里作为报告证据。

### [h-idor-bruteforce] 批量遍历脚本思路 | hard | IDOR;脚本编写 | IDOR 遍历
> 用脚本批量遍历连续 ID，通过响应长度/状态码差异自动标记越权点。

#### 这个条目的作用
手动替换 ID 只能验证三五个点，遇到自增数字 ID 的业务，写个脚本把整个 ID 空间扫一遍，用"状态码 + 响应长度 + 关键字段"三个信号自动捞出越权点，省时且不容易漏。脚本本身不复杂：一个循环、一次请求、一组判定条件，十几行就能跑通。

#### 前置条件
- 已手动确认至少一个可越权的 ID 样本（如 id=1001 能读到他人数据），**先手动后脚本**，脚本只是放大手动发现
- Python 3 + `requests` 库，能拿到目标站点有效期内的会话 Cookie
- 明确知道 ID 空间的形态（自增数字 / 时间戳编号）与大致范围

#### 第 1 步：手动确认样本并抓取会话（操作：浏览器 + Burp）
登录账号，在 Repeater 里手动把 ID 换成相邻值，确认至少一个 ID 能返回"别人的数据"（读到了、或者响应长度与基线显著不同）。同时把会话 Cookie 复制出来。预期结果：你手里有一个确定的命中样本，脚本只是把它扩展成一批。如果不行：没有任何样本就上脚本，扫出来全是噪声，先回头做 h-idor-detect 确认存在越权面。

#### 第 2 步：确定 ID 空间（操作：分析 ID 形态并定范围）
- 自增数字：直接从 1（或当前号段附近）开始遍历，范围先小后大，从 50 个起步验证脚本正确性，再决定扩大到多少。
- 时间戳/订单号：先收集 5-10 个已知编号样本，观察规律（前缀+日期+序号），推导可能的区间。
- 如果 ID 空间过大（百万级），先扫"当前注册量附近"的号段，或按时间窗口分片扫。

#### 第 3 步：写基线获取函数（操作：本地编辑器写脚本）
先写一个 `grab(uid)` 函数，返回 `(状态码, 响应体长度, 响应前 50 字符)`，并把"确定是自己的 ID"的响应作为基线存下来。

```python
import requests

BASE = "http://target/api/user/{uid}/profile"
s = requests.Session()
s.headers["Cookie"] = "session=YOUR_SESSION"  # 换成你抓到的会话

def grab(uid):
    r = s.get(BASE.format(uid=uid), timeout=5)
    return r.status_code, len(r.content), r.text[:50]

base = grab(10000)          # 用确定属于自己的 ID 取基线
print("baseline:", base)
```

#### 第 4 步：写遍历主循环 + 差异化判定（操作：继续写脚本）
遍历目标号段，判定规则：**状态码为 200 且响应长度与基线差异超过阈值（如 50 字节）→ 疑似越权**。同时排除"未登录/空数据"这类固定长度响应（它们的长度往往恒等于某个值，可在脚本里先拿一个不存在的 ID 记录"空白基线"再过滤）。

```python
import time

blank = grab(99999999)      # 不存在的 ID，作为"空白响应"基线
print("blank:", blank)

for uid in range(10000, 10050):
    st, ln, head = grab(uid)
    # 200 且长度既不同于基线也不同于空白 → 疑似命中真实数据
    if st == 200 and abs(ln - base[1]) > 50 and abs(ln - blank[1]) > 50:
        print(f"[HIT] uid={uid} len={ln} head={head}")
    time.sleep(0.2)          # 控制速率，避免频控封禁
```

#### 第 5 步：验证命中并过滤噪声（操作：对每个 HIT 手工复核）
脚本输出的每个 `[HIT]` 都要手动验证：把该 ID 的完整响应拉出来，看是否真的包含他人的数据字段（用户名、手机号、订单内容）。判定规则：
- 响应里含明确的他人身份信息 → 越权命中。
- 响应只是长度略不同但内容是空壳/错误页 → 噪声，调整阈值（50 调大到 200）再跑。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 全是 HIT，但手动看都是空数据 | 接口对不存在 ID 返回了固定的长响应 | 用不存在 ID 建立空白基线，把它的长度精确排除 |
| 扫到一半被封 IP / 触发验证码 | 请求太快触发频控 | 加 `time.sleep(0.2~1)` 随机间隔；换代理 IP 重试 |
| 用错会话：全返回 401 | Cookie 过期或复制少了字段 | 重新抓包，复制完整 Cookie，必要时带完整请求头 |
| 扫描范围太大跑不完 | 没先小范围验证脚本 | 先用 50 个 ID 确认脚本与判定正确，再扩范围 |
| 脚本扫到的是别人的真实数据 | 越权面比预想大 | 立即停止扩大扫描，只保留少量证据截图，走报告流程 |

> [!tip] 控制速率：加 `time.sleep(0.2)` 或随机间隔，避免触发频率限制和封禁；大批量遍历前先确认目标授权范围内，扫描会读取大量真实用户数据，越权面确认后立即收敛。

#### 实战要点
- 铁律：**先手动确认一个命中样本，再写脚本放大**，没有样本的脚本等于盲扫。
- 差异化判定三信号：状态码、响应长度、关键字段值；其中长度最廉价但最容易被空壳响应干扰，必须配空白基线。
- 空白基线（不存在的 ID）和真实基线（自己的 ID）都先采一次，命中判定用两者双重过滤。
- 遍历范围先小后大、速率先慢后快，任何一次封禁都会中断任务还打草惊蛇。
- 命中信息用于报告时只保留必要证据（最小化真实数据），扫描产生的他人数据不得外传。

## [g-vertical] 垂直越权——普通用户调了管理员接口

### [v-role-model] 角色判断与权限模型 | easy | 垂直越权;权限模型 | 提权
> 权限只在前端或单一字段上区分，后端没有独立鉴权模型。

#### 这个条目的作用
垂直越权（提权）的第一步不是乱试接口，而是**先搞清楚这个站点的角色是怎么判断的**。很多站点权限只存在前端或一个可篡改的字段里，找到角色判断的位置，提权就完成了一半。本条目教你在登录、注册、抓包里定位角色机制，判断它到底是"后端独立鉴权"还是"形同虚设"。

#### 前置条件
- 一个普通账号 + 一个身份信息（最好知道管理员账号用户名，如 `admin`）
- Burp Suite 能抓包改包
- 浏览器开发者工具（F12，看 localStorage / Cookie）

#### 第 1 步：登录响应里找角色字段（操作：Burp 抓登录请求与响应）
用普通账号登录，在 Burp 里看登录**响应体**，搜索关键词：`role`、`isAdmin`、`level`、`permission`、`authority`、`type`。同时看响应头里的 `Set-Cookie`——有些站点把角色直接写进 Cookie。预期结果：找到形如 `"role": "user"` 或 `role=user` 的字段。如果不行：响应里没有角色字段，继续第 2 步，角色可能在请求侧或前端存储里。

#### 第 2 步：检查请求侧的角色载体（操作：F12 看存储 + Burp 看请求头）
- F12 → Application → Local Storage / Session Storage：搜 `admin`、`role`、`user` 关键词。
- Burp 里看所有请求的请求头、Cookie、JWT（Authorization: Bearer 开头的就是）。
- 判定规则：
  - `localStorage["isAdmin"]=false` → 前端角色，改成 true 再刷新即可提权（配合 v-frontend-bypass）。
  - Cookie 里 `role=user` 明文 → 改成 `role=admin` 重放请求，看后端是否认。
  - JWT payload 里 `"role":"user"` → 先验签再动 payload（见第 4 步），别一上来就改。

#### 第 3 步：注册接口能否传角色参数（操作：注册时抓包加字段）
打开注册功能，随便填一个测试账号，Burp 抓注册请求，在 JSON body 里追加角色字段重放：
```http
POST /api/register HTTP/1.1
Host: target.com
Content-Type: application/json

{"username": "test123", "password": "x", "role": "admin"}
```
预期结果：要么注册成功且新账号是管理员（漏洞实锤），要么注册成功但角色被忽略（继续下一步）。如果不行/被拒：服务端至少做了角色白名单，把这几个变体也试试：`"isAdmin": true`、`"level": 1`、`"type": "admin"`、`"permission": "all"`。

#### 第 4 步：JWT 场景验签（操作：先验签再改 payload）
如果角色在 JWT 里：把 token 丢到 jwt.io 或本地工具，先看 `alg` 和签名密钥：
- `alg: none` → 删掉签名部分直接把 payload 改成 `role: admin` 重放，后端可能直接信。
- `alg: HS256` 且密钥是弱密钥（如 `secret`、`123456`）→ 爆破出密钥后自行签发 admin token。
- 密钥未知且 alg 正常 → 改 payload 过不了验签，不是这条路，回到第 2/3 步找其他载体。

> [!warn] JWT 场景：先验签（alg 是否为 none、密钥是否泄露），别一上来就改 payload——改完要能通过服务端验签才算漏洞，否则只是改了个寂寞。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 改了前端 role 也没权限 | 后端有独立鉴权，前端只是展示层 | 这不算漏洞，回到接口层测 v-admin-api |
| JWT 改了 payload 请求报 401 | 签名校验没过 | 先验签；确认密钥不可得后放弃此路 |
| 注册加 role=admin 成功但功能没变 | 角色字段被服务端忽略或另有角色表 | 换字段名变体测试，或去调管理接口验证 |
| Cookie 里找不到角色 | 角色存在 session 服务端侧 | 走 v-admin-api 直接测管理接口，不必找到角色字段 |

#### 实战要点
- 角色判断三查：登录响应、请求侧载体（Cookie/JWT/存储）、注册接口参数——按这个顺序查完基本能定位。
- 权限模型缺陷四件套：角色写在前端（localStorage）、角色在 Cookie/JWT 明文、接口无角色校验、只校验"是否登录"。
- "只校验是否登录 = 登录即全权限"是最高频的垂直越权：管理员和普通用户共用一套接口，普通用户直调管理接口即提权。
- 前端角色≠后端角色：改前端永远只是验证手段，最终以"后端接口是否放行"为准。
- 凡是"响应里出现 role 字段"的站点，注册/登录/个人资料接口都值得测角色参数注入。

### [v-admin-api] 普通用户调 admin 接口 | medium | 垂直越权;接口测试 | -
> 接口文档或 JS 中暴露管理接口，普通用户直接调用即提权。

#### 这个条目的作用
管理功能通常藏在 URL 里：`/admin`、`/manage`、`/console`。前端不展示管理入口不代表接口不存在——把接口找出来，用**普通用户自己的会话**直接请求，返回 200 就是垂直越权。本条目给出找管理接口的四条路线（JS、接口文档、参数猜测、替换测试）和验证方法。

#### 前置条件
- 一个普通账号的可用会话 Cookie
- Burp Suite（Repeater + 可搜索的 History）
- 浏览器 F12 的 Network / Sources 面板

#### 第 1 步：从前端 JS 里挖管理接口（操作：F12 Sources 搜索关键词，或下载 JS 本地搜）
打开站点任意页面，F12 → Sources，按 Ctrl+Shift+F 全站搜索关键词：`admin`、`manage`、`console`、`backstage`、`internal`、`api/v1`。或把主 JS 文件（webpack 打包的通常几个 MB）下载到本地用编辑器/ripgrep 搜。预期结果：搜出一批你从没见过的路径，如 `/api/admin/user/list`、`/manage/order/export`。如果不行：JS 里没有，走第 2 步找接口文档。

> [!tip] 优先搜 `baseURL`、`axios.create`、`fetch(` 附近的常量，接口前缀通常集中定义在那一处。

#### 第 2 步：找接口文档（操作：浏览器直接访问常见文档路径）
直接在浏览器/Repeater 里访问这些路径，看是否返回 JSON 文档：
```
/swagger-ui.html  /v2/api-docs  /v3/api-docs  /api-docs
/openapi.json    /swagger-resources  /graphql
```
预期结果：出现 Swagger UI 或 JSON 文档 → 里面列着全部接口，直接抄管理接口列表。如果不行：没有文档，走第 3 步参数猜测。若返回 403/404 也不用停，先记下这些路径，后面用别的身份/方式再试。

#### 第 3 步：参数/路径猜测（操作：把普通接口 URL 做替换变形）
拿已抓到的普通接口做变形，规则很简单：
- `user` → `admin`：`/api/user/list` → `/api/admin/list`
- `get/list` → `manage/delete`：`/api/order/list` → `/api/order/manage/delete`
- `v1` → `v2`：旧版本接口常有不同鉴权
- 追加关键词：`?debug=1`、`/test`、`/dev`、`/backdoor`

#### 第 4 步：普通用户会话验证（操作：Repeater 里用普通 Cookie 发管理请求）
把找到的每个管理接口，用**普通用户的 Cookie** 在 Repeater 里发送：
```http
GET /api/admin/user/list HTTP/1.1
Host: target.com
Cookie: session=普通用户会话
```
```http
GET /api/user/delete?id=1 HTTP/1.1
Host: target.com
Cookie: session=普通用户会话
```
判定规则：返回 200 + 管理数据（用户列表、订单全量）→ **垂直越权，命中**；返回 403/401 → 有后端鉴权，记录"已防护"后换下一个。

#### 第 5 步：批量替换验证（操作：脚本对普通接口列表做关键词替换后批量请求）
把抓到的普通接口列表存成文本，用脚本对每个接口做关键词替换（`user→admin`、`list→delete`、`v1→v2`），批量请求并输出（状态码, 响应长度）。长度显著大于 403 响应的，多半返回了真实管理数据，人工复核。

```bash
# bash 思路：对接口列表逐条替换关键词并请求
for path in $(cat api_list.txt); do
  for p in "${path/user/admin}" "${path/list/manage}" "${path/v1/v2}"; do
    code=$(curl -s -o /dev/null -w "%{http_code} %{size_download}" \
      -H "Cookie: session=普通用户会话" "http://target$p")
    echo "$code $p"
  done
done
```

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 管理接口返回 403 | 后端有角色校验 | 先确认是不是 IP/UA 校验（换浏览器 UA 重试），仍 403 则记"已防护" |
| 接口 404 但前端菜单里有 | 路径带版本/前缀 | 回 JS 里找 baseURL 前缀拼上再试 |
| 用 admin 会话测通了，用普通会话不通 | 管理接口本身要管理员权限 | 那不算漏洞；垂直越权必须是**普通会话**直接访问成功 |
| Swagger 路径返回 404 | 站点关掉了文档 | 不依赖文档，走 JS/猜测两条路 |
| 批量脚本全是 403 | 关键词替换方向不对 | 观察 403 与 200 的响应长度差异，用长度信号过滤，别用状态码一刀切 |

#### 实战要点
- 管理接口四来源：前端 JS 关键词、Swagger/OpenAPI 文档、普通接口 URL 变形、HTML 注释与响应头提示。
- 验证凭据必须是**普通用户自己的会话**，换成别人的 Cookie 都不算，管理员会话测通更不算。
- 状态码会骗人：某些框架对越权统一返回 403 但 body 里带了数据，响应长度才是更稳的信号。
- 老接口（v1/v2）、调试接口（debug/test/dev）常与正式接口鉴权不一致，优先测。
- 找接口时用的关键词清单（admin/manage/backstage/internal/debug）值得沉淀成自己的速查表。

### [v-frontend-bypass] 前端鉴权绕过 | easy | 前端鉴权;路由守卫 | -
> 权限控制全部在前端路由守卫，直接请求后端接口即绕过。

#### 这个条目的作用
SPA（单页应用）项目最常见的"伪防护"：路由守卫在前端拦截页面跳转，看起来"没权限进不去管理页"，但**数据接口在后端没有任何鉴权**。绕过前端路由只需要一步——不经过页面，直接用工具请求接口。本条目教你识别前端鉴权、四种绕过方式，以及最重要的：**如何确认这是真漏洞**。

#### 前置条件
- 一个普通账号会话
- Burp Repeater 或 curl
- 浏览器 F12（看路由配置和 localStorage）

#### 第 1 步：识别前端路由守卫（操作：F12 看代码 + 手动访问 /admin 路径观察）
F12 → Sources，找路由配置文件（Vue 项目搜 `router` / `beforeEach`，React 项目搜 `PrivateRoute` / `RequireAuth`），看是否包含 `isAdmin` / `role` 判断。同时在浏览器地址栏直接输入 `/admin` 回车观察：
- 自动跳回登录页/首页 → 有路由守卫，前端确实拦了。
- 直接渲染了管理页面 → 前端路由根本没拦，页面级越权已经成立。
预期结果：确认"页面访问被前端拦着"。如果不行/没有路由文件：可能没有前端鉴权，直接进入第 3 步，反正重点是后端接口。

#### 第 2 步：直接调后端接口绕过（操作：Repeater 绕过页面直连接口）
这是核心一步：**永远不要跟路由守卫较劲，直接请求接口**。用抓包或 JS 分析拿到管理接口路径，用普通账号 Cookie 在 Repeater 里直接请求：
```http
GET /api/admin/user/list HTTP/1.1
Host: target.com
Cookie: session=你的普通用户会话
```
预期结果：返回 200 + 管理数据 → 后端无鉴权，漏洞成立。如果不行（403）：后端有鉴权，这个站点的"前端守卫"只是障眼法但接口有真防护，继续第 3/4 步换思路，或判定为安全。

> [!warn] 前端鉴权绕过本身不是漏洞，必须验证**后端接口是否真的无鉴权**：改完前端状态后直接调管理接口，200 才是漏洞。页面能渲染但接口 403，那只是"能看个壳"。

#### 第 3 步：改前端存储状态（操作：F12 控制台写入 localStorage 后刷新）
如果页面渲染依赖前端状态，直接在 F12 Console 里写：
```javascript
localStorage.setItem('isAdmin', 'true');
// 或 sessionStorage，字段名以第 1 步搜到的为准
```
然后刷新页面，观察管理入口是否出现。**注意：这一步只证明前端状态可控，必须回到第 2 步用这个会话调接口验证后端**——页面显示管理菜单不等于接口放行。

#### 第 4 步：抓包改登录响应提权（操作：Burp 拦截登录响应修改 role）
在 Burp Proxy 的 HTTP history 里找到登录接口，开启 Intercept，重放登录请求，把响应里的 `"role": "user"` 改成 `"role": "admin"` 后放行，前端拿到"管理员"状态渲染出全部功能。同样，这只是前端视角，最后一步仍是接口验证。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 改了 URL 到 /admin 页面空白 | 前端路由/组件懒加载拦了 | 不用页面，直接回第 2 步调接口 |
| localStorage 写了 isAdmin 没反应 | 字段名不对，或状态在别处（vuex/pinia） | 回第 1 步确认守卫判断的准确字段 |
| 页面渲染了管理菜单但接口全 403 | 后端有鉴权，前端只是展示层 | 结论：无漏洞，记录"前端伪防护+后端有鉴权" |
| 只测了 GET，改状态的接口没测 | 写接口才是重头 | 管理接口的 POST/PUT/DELETE 同样用普通会话测 |
| 改了响应但应用崩溃 | 前端字段类型校验（expect boolean） | 把 `"role":"admin"` 与 `"isAdmin":true` 两处都改，保持 JSON 合法 |

#### 实战要点
- 绕过顺序：直连接口（最稳）→ 改前端状态 → 改登录响应 → 改 URL，前两者覆盖九成场景。
- 铁律：**一切前端操作只是铺垫，最终判定永远是"后端接口用普通会话直连返回 200"**。
- 前端守卫分析看三处：路由守卫、localStorage 状态、登录响应里的 role 字段。
- 报告里要写清链路：前端守卫可绕过（证据）+ 后端接口无鉴权（证据），两者缺一不可。
- 这种洞在前后端分离项目里极常见，Vue/React 管理后台新建项目时几乎必踩。

## [g-authflow] 注册登录逻辑——认证流程的每一步都可能被绕

### [a-register-overwrite] 注册覆盖与批量注册 | hard | 注册逻辑;账号覆盖 | 同名注册
> 注册逻辑未校验用户名唯一性或未加验证，可覆盖已有账号或批量灌号。

#### 这个条目的作用
注册功能是很多人眼中的"入口"，但它的逻辑缺陷能直接送你一个管理员账号：注册接口查重逻辑不严（或对管理员账号所在的表不做查重），你可以注册一个与管理员同名的账号并直接登录；验证码缺失/可复用则能批量灌号。本条目给出同名注册、并发覆盖、批量注册三条测试链路的安全验证方法。

#### 前置条件
- 一个测试用的全新用户名（如 `admin_test` 之类，别一上来就用真实存在的管理员名）
- Burp Repeater，能改包重放
- 知道目标管理员常用用户名（通常是 `admin`，可先测"用户名已存在"提示确认）

#### 第 1 步：分析注册流程与字段（操作：Burp 抓注册请求）
用全新用户名正常注册一个账号，Burp 抓注册请求，确认三件事：
1. 用什么字段提交用户名（`username` / `mobile` / `email`？）
2. 服务端是否要求验证码（请求里有没有 code/captcha 字段）
3. 是否要求手机/邮箱验证（决定覆盖攻击是否可行）
同时用已存在的用户名（如 `admin`）再注册一次，记录提示语：**"用户名已存在"→ 服务端至少做了查重；出现别的提示（如直接成功、或"验证码错误"）→ 查重逻辑可疑**。

#### 第 2 步：同名注册覆盖测试（操作：Repeater 直接提交 admin 用户名）
用管理员用户名（先确认它存在，比如登录页提示/注册提示泄露）直接提交注册：
```http
POST /api/register HTTP/1.1
Host: target.com
Content-Type: application/json

{"username": "admin", "password": "MyPass123!", "email": "x@x.com"}
```
判定规则：
- 返回"用户名已存在" → 查重正常，走第 3 步并发测试。
- 注册成功 → **直接尝试用 admin/MyPass123! 登录**，登录成功即拿到管理员账号，**立即停止后续操作，截图留证**。

> [!danger] 覆盖管理员是最严重的注册漏洞：直接获得管理员账号控制权。发现后立即停止进一步操作，走报告流程。不要用真实管理员账号名做并发轰炸，确认"存在查重"即可收手。

#### 第 3 步：并发同名注册测试（操作：并发提交两条同名注册）
查重逻辑若是"先查询再插入"（check-then-act），并发下两条同名请求都通过查询、都能插入。用两个完全相同的注册请求同时发送（Turbo Intruder 或双线程脚本）：
```python
import requests, threading

def reg():
    r = requests.post("http://target/api/register",
                      json={"username": "race_admin", "password": "x"},
                      timeout=5)
    print(r.status_code, r.text[:80])

for _ in range(2):
    threading.Thread(target=reg).start()
```
判定规则：两次都返回成功、且随后用该用户名能登录 → 存在并发覆盖窗口。如果不行：查重是 DB 唯一约束或加锁，此路不通。

#### 第 4 步：批量注册测试（操作：无验证码则循环注册 2-3 个账号）
先看注册要不要验证码：
- 无验证码 → 直接连续注册几个账号，观察是否有频率限制（间隔/次数/封 IP）。
```bash
# 循环注册（假设无验证码、无频控）
for i in $(seq 1 20); do
  curl -s -X POST http://target/api/register \
    -d "username=test$i&password=123456" -o /dev/null -w "%{http_code}\n"
done
```
- 有验证码 → 测"同一验证码能否复用"：用同一个 code 连续提交两次注册，都成功即验证码不失效。
判定规则：连续 20 个请求全部 200 且都注册成功 → 批量灌号成立（资源消耗型漏洞，危害中低，但常作为撞库/薅羊毛前置）。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 注册 admin 提示已存在就放弃了 | 没测并发窗口 | 见第 3 步，check-then-act 型查重并发下会失效 |
| 覆盖成功但登录不了 | 新注册的和原管理员是两个体系（如邮箱去重） | 检查注册用的唯一键是 username 还是 email/手机号 |
| 以为覆盖成功没影响 | 管理员在另一张表维护 | 只要"同名注册成功"就要试登录；登录成功才是漏洞闭环 |
| 并发测试没复现 | 两个请求没真正同时到达 | 用 Turbo Intruder 并发连接（不要用串行重放），或增大并发数 |
| 批量注册被验证码拦住 | 有验证码 | 先测验证码复用/空值/绕过（见 a-verify-bypass），绕不过则停止灌号 |

#### 实战要点
- 同名覆盖的前提：注册表与管理员账号表不是同一套数据，或查重存在 check-then-act 窗口。
- 注册接口允许客户端指定用户名 + 服务端未查重 → 直接同名注册；查重存在但并发弱 → 并发覆盖。
- 覆盖成功的危害评级：能登录管理员账号 = 最高级；只注册成功但进不去管理 = 中低级，如实定级。
- 批量灌号本身危害有限，但验证码复用 + 批量注册组合是撞库、薅羊毛链路的入口，报告中一并说明。
- **检测规则红线**：所有覆盖/并发测试用自建测试名，确认"存在同名注册成功"现象即可，禁止真的覆盖线上真实管理员账号。
