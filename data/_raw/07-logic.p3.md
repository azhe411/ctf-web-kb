## [g-captcha] 验证码与频率——验证码和限流都可能形同虚设

### [c-image-captcha] 图形验证码绕过 | medium | 图形验证码;OCR | -
> 图形验证码可 OCR、可复用、可空值绕过，或校验在前端。

#### 这个条目的作用
图形验证码是拦住自动化请求的"第一道门"：登录、注册、下单前先让你认一张扭曲的字母数字图。这道门经常是纸糊的——后端根本不校验、校验了但不标记已用、甚至答案就写在响应里。学会本条目，你能在 5 分钟内判断一个图形验证码是"真校验"还是"纯摆设"，并走完从最省力到最费力的完整绕过顺序，避免一上来就傻乎乎跑 OCR。

#### 前置条件
- 一个已登录或可匿名访问的目标，且在你的授权测试范围内
- Burp Suite（或任意抓包工具），能拦截、重放、修改请求；目标页面里能看到图形验证码（登录/注册/找回密码/下单等场景）
- 可选：Python 环境 + `requests` 库；tesseract OCR（仅最后手段才用）

#### 第 1 步：抓包定位验证码的"生成"和"校验"两个接口
打开 Burp 代理，触发一次验证码刷新和一次表单提交，观察两条链路：

```http
GET /api/captcha/generate HTTP/1.1
Host: target.com

HTTP/1.1 200 OK
Content-Type: image/png
Set-Cookie: captchaId=abc123
```

```http
POST /api/login HTTP/1.1
Host: target.com
Content-Type: application/x-www-form-urlencoded

username=test&password=123456&captchaId=abc123&captcha=4F7K
```

预期结果：你能分清"生成接口"（返回图片、下发 captchaId）和"校验接口"（表单提交里带 captcha 字段）。
如果不行：页面可能是前端本地生成验证码（JS 绘制），请求里没有 captcha 字段——这本身就是线索，跳到第 4 步。

> [!tip] 记下 captchaId 与 captcha 的对应关系。后面所有测试都围绕"同一 captchaId 换不同 captcha 值"展开。

#### 第 2 步：测空值与固定值绕过（最省力，先测这个）
原理：后端可能"收到 code 字段就放行"，或对 `0000`/`1234` 这类值做了特判。逐项提交变体：删字段 → 空值 → `0000`/`1234`/`8888` → `null` 字符串 → 超长字符串，观察是否通过：

```http
POST /api/login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

username=test&password=123456&captchaId=abc123&captcha=
```

```http
POST /api/login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

username=test&password=123456&captchaId=abc123&captcha=0000
```

预期结果：任一变体返回"验证码正确"或直接放行（登录/下单成功），即命中。
如果不行：全部报"验证码错误"，说明后端确实比对，继续第 3 步。

> [!warn] 提交"验证码错误"本身就是业务分支，某些目标存在"错误验证码触发某逻辑、正确验证码反而跳过"的反向缺陷，也值得各测一次。

#### 第 3 步：测复用——同一验证码多次提交
原理：服务端生成验证码后不标记"已用"，或标记有延迟，同一个 captchaId+captcha 组合能反复使用。先正常获取一次验证码，连续提交 3 次：

```bash
for i in 1 2 3; do
  curl -s -X POST http://target.com/api/login \
    -d "username=test&password=123456&captchaId=abc123&captcha=4F7K" \
    -o /dev/null -w "%{http_code}\n"
done
```

预期结果：3 次都成功 → 验证码可复用，配合脚本可实现无限次自动化登录/爆破。
如果不行：第二次起报"验证码已失效"，说明有一次性标记，继续第 4 步。

#### 第 4 步：测前端校验与答案回显
- **前端校验**：浏览器开发者工具 → Sources 里搜 `captcha` 关键词，若看到 `if (code === "4F7K")` 这类硬编码比对，或验证码由前端 Canvas 生成且后端不收 captcha 字段——直接构造请求绕过前端。
- **答案回显**：抓"生成验证码"接口的响应体/响应头/Set-Cookie，看是否直接包含答案：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"captchaId": "abc123", "captcha": "4F7K"}
```

预期结果：JS 里有明文答案，或响应里带 captcha 字段 → 校验形同虚设，直接读出答案提交。
如果不行：以上都干净，进入第 5 步。

#### 第 5 步：测图片 URL 或答案泄露在页面/接口
- 页面源码里搜验证码图片的 src，若是 `http://target/captcha/4F7K.png` 这种把答案写进 URL 的形式，直接读 URL。
- 检查生成接口的响应头：`X-Captcha: 4F7K`、`Captcha-Answer: 4F7K` 这类自定义头。

预期结果：任何一处泄露答案 → 脚本化：请求生成接口 → 解析答案 → 提交表单，全自动绕过。
如果不行：答案确实藏在图片像素里，才轮到 OCR（下一步）。

#### 第 6 步：OCR 识别（最后手段，成功率最不可控）
只有前五步全部失败才做 OCR。先下载几张验证码图片人工确认：纯数字、无干扰线、无扭曲 → 值得 OCR；中文/复杂扭曲 → 直接放弃这个点。

```python
import requests
import subprocess

s = requests.Session()
img = s.get("http://target.com/api/captcha/generate").content
open("cap.png", "wb").write(img)
# 预处理（二值化、放大）后识别，成功率更高
out = subprocess.run(
    ["tesseract", "cap.png", "stdout", "--psm", "7"],
    capture_output=True, text=True
).stdout.strip()
print("OCR 结果:", out)
```

预期结果：OCR 出的数字能通过校验 → 写循环自动识别自动提交。
如果不行：识别率低说明验证码质量高，本点到此为止，如实记录"验证码强校验，未绕过"。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 空值测试全返回"验证码错误" | 后端校验了字段存在性，但没校验值 | 继续测复用与回显，别停在第 2 步 |
| 换了 captchaId 后原 captcha 失效 | 验证码与 captchaId 强绑定 | 复用测试必须用"同一次生成的 captchaId+captcha" |
| 前端 JS 里搜不到 captcha | 验证码逻辑在压缩打包的 JS 里 | 搜 `captcha`/`code`/`verify` 关键词，或格式化后再搜 |
| OCR 识别出的值提交失败 | 图片有干扰线/扭曲，识别错位 | 用 `--psm 7` 单行模式 + 二值化预处理，或放弃 OCR |

#### 实战要点
- **按成本排序测试**：空值/删字段 → 固定值 → 复用 → 前端校验 → 响应回显 → OCR，永远把 OCR 放最后
- 复用缺陷比 OCR 更有价值：一次拿到合法验证码就能无限自动化，写 PoC 时优先展示复用
- 验证码接口往往同时存在频率限制问题（无限制可无限刷新图片），一并记录
- 同一验证码在登录、注册、找回密码多个入口共用时，跨入口复用也要测

## [g-race] 状态机与竞态——业务逻辑不是原子的

### [r-state-machine] 订单状态跳变与越步操作 | hard | 状态机;订单逻辑 | 越步操作
> 订单状态流转无严格校验，可跳过中间状态直达终态。

#### 这个条目的作用
订单是一台状态机：待支付 → 已支付 → 已发货 → 已完成，外加退款、取消、关闭等旁路状态。安全的状态机要求"每个转换都校验前置状态"——只有"待支付"的订单能支付，只有"已支付"的订单能发货。但很多后端只校验"目标状态"或干脆不校验，导致你能让订单**跳变**：没付钱就发货、没发货就退款、退完款还能再退。学会本条目，你能画出目标的状态机、定位每一个非预期转换，把"订单逻辑漏洞"从碰运气变成按图索骥。

#### 前置条件
- 目标站有完整的订单业务流程（下单 → 支付 → 发货 → 收货），且在你的授权范围内
- 至少一个能下单的普通账号，最好能模拟支付成功（有些靶场/测试环境有模拟支付入口）
- Burp Suite 或抓包工具；熟悉请求重放；一张纸或文档用来画状态机图

#### 第 1 步：先画目标订单的状态机（别急着乱测）
把业务流程完整走一遍：下单、支付、发货、收货、退款、取消，每步抓包记录接口路径和订单状态字段的变化：

```txt
待支付 --支付--> 已支付 --发货--> 已发货 --收货--> 已完成
   \               \                \
    \--取消--> 已关闭     \--退款--> 已退款    \--退货--> 售后中
```

预期结果：你手里有一张表：每个状态 + 每个操作接口 + 当前订单状态字段值（`status=0/1/2/3` 或字符串）。
如果不行：接口抓不全，去前端 JS 里搜订单操作相关路径，或参考接口文档（Swagger/api-docs）。

#### 第 2 步：收集订单操作接口清单，标注每个接口的"合法前置状态"
常见订单操作接口及理论上的合法前置状态：

| 接口 | 合法前置状态 |
|---|---|
| 支付/确认支付 | 待支付 |
| 发货 | 已支付 |
| 收货/确认收货 | 已发货 |
| 退款 | 已支付 / 已发货（视业务） |
| 取消 | 待支付 |
| 完成/结算 | 已完成（幂等） |

预期结果：接口清单里每个接口都标注了"它应该只能从哪个状态进入"。
如果不行：部分接口（如发货）前端没有入口，但接口路径可通过 JS 搜索或路径猜测找到，直接记录备用。

> [!tip] 状态字段不一定叫 status，也可能是 `state`/`orderStatus`/`phase`。从下单接口的请求/响应里找订单状态的载体。

#### 第 3 步：逐接口测"非预期状态转换"（核心测试）
对每个操作接口，用**错误前置状态**的订单去调用，观察是否被放行。以退款接口为例：

```http
POST /api/order/refund HTTP/1.1
Host: target.com
Content-Type: application/json

{"orderId": "20240101001"}   # 这个订单当前是"待支付"，能退款吗？
```

测试矩阵：待支付订单调退款、已关闭订单调发货、待支付订单调发货、已退款订单再次退款。
预期结果：任一调用返回成功（200 + 业务成功），即状态跳变漏洞。
如果不行：全部返回"当前状态不允许此操作"，说明前置状态校验严格，记录为安全。

> [!danger] 跳变测试可能真的改变订单状态（如真的退款、真的发货）。优先用自己下单的测试订单，别动真实业务订单。

#### 第 4 步：测越步操作——跳过中间状态直达终态
有些接口只校验"目标状态对不对"，不校验"从哪里来"，导致跳步。典型测试：
- **跳过支付直接发货**：新下单一笔"待支付"订单，直接调发货接口
- **未支付先退款**：待支付订单直接调退款
- **未发货先收货**：已支付订单直接调确认收货
- **取消已发货订单**：对已发货订单调取消接口，观察是否退款或改状态

```http
POST /api/order/ship HTTP/1.1
Host: target.com
Content-Type: application/json

{"orderId": "20240101002"}   # 该订单从未支付，能发货成功？
```

预期结果：跳步成功（如待支付订单直接变成已发货）→ 状态转换链断裂。
如果不行：接口校验了前置状态，跳到第 5 步测终态幂等。

#### 第 5 步：测终态幂等——重复完成/重复结算
状态机的最后一道常见缺陷：终态不幂等。把"已完成"的订单重复调用完成/结算/评价接口，观察是否二次入账：

```http
POST /api/order/complete HTTP/1.1
Content-Type: application/json

{"orderId": "20240101003"}   # 连续发送 3 次
```

预期结果：重复调用触发二次结算/二次返利/二次评价奖励 → 状态机无终态保护。
如果不行：终态校验正常，把全部结果整理成"状态 × 接口"通过矩阵。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 测试全是"状态不允许" | 状态校验确实严格，或你用的订单状态不对 | 核对订单当前状态，确保覆盖每个状态样本 |
| 找不到发货/退款接口 | 前端没入口，接口隐藏 | JS 里搜 `ship`/`refund`/`deliver`，或按接口命名规律猜测 |
| 请求成功但状态没变 | 接口返回 200 但内部校验失败 | 看响应体的业务码，别只看 HTTP 状态码 |
| 越步测试污染了数据 | 测试订单状态被改乱 | 每次跳变测试都用新订单，别复用同一订单反复测 |

#### 实战要点
- **先画状态机再动手**：状态转换的合法性依据是"业务规则"，画出图才测得全
- 状态跳变的价值排序：未支付退款 / 跳过支付发货 > 重复结算 > 取消异常状态
- 响应体里的业务码（如 `code: 0` vs `code: 40301`）比 HTTP 状态码更可信
- 把"状态 × 接口"通过矩阵记录进报告；跳变与竞态常叠加（见 r-concurrency）

### [r-duplicate] 重复提交 | easy | 重复提交;幂等 | -
> 下单/提现/转账等接口无幂等，同一请求重复发送多次产生多次业务。

#### 这个条目的作用
"幂等"的意思是：同一个请求发一次和发一百次，效果应该一样。下单、提现、转账、签到这类写操作必须幂等——但很多后端没做，同一请求重复发送就会生成多个订单、多次扣款、多次到账。这是逻辑漏洞里最基础也最容易验证的一类：抓包 → 重放 → 数订单，三步出结果，非常适合入门第一个实战点。

#### 前置条件
- 一个能执行写操作的账号（能下单/提现/签到/领奖任一即可），在授权范围内
- Burp Suite 的 Repeater（重放器）或 curl；一个能查看结果的途径（订单列表、账户余额、签到记录）

#### 第 1 步：选一个写操作，抓包拿到完整请求
选一个会产生"业务记录"的操作（下单、签到），用 Burp 抓包，把请求完整拷贝到 Repeater：

```http
POST /api/order/create HTTP/1.1
Host: target.com
Content-Type: application/json
Cookie: session=YOUR_SESSION

{"itemId": 1001, "quantity": 1}
```

预期结果：Repeater 里有一个完整可重发的请求，且你知道这次操作成功了（生成了订单号）。
如果不行：请求被前端签名/加密，先看是否有独立的防重放令牌（见常见错误表）。

> [!tip] 优先选"签到/领奖"这类无资金风险的操作练手，确认思路后再测下单/提现。

#### 第 2 步：原样重放 2-3 次，数业务结果
不改任何参数，把同一个请求连续发送 2-3 次，然后去业务页面核对：

```bash
for i in 1 2 3; do
  curl -s -X POST http://target.com/api/order/create \
    -H "Cookie: session=YOUR_SESSION" \
    -H "Content-Type: application/json" \
    -d '{"itemId": 1001, "quantity": 1}' \
    -o /dev/null -w "%{http_code}\n"
done
```

预期结果：订单列表里出现 2-3 个新订单，或积分/余额增加了多次 → 无幂等，漏洞成立。
如果不行：只产生一条记录，第二次起被拒（"订单已存在"或返回相同订单号）→ 有幂等保护。

#### 第 3 步：对比两次响应的订单号（关键判定）
看两次响应的订单号：

```txt
第一次响应: {"orderId": "20240101001", "code": 0}
第二次响应: {"orderId": "20240101002", "code": 0}   ← 订单号不同 → 重复下单
第二次响应: {"orderId": "20240101001", "code": 0}   ← 订单号相同 → 幂等正常
```

预期结果：订单号不同 = 生成了多条业务记录 = 漏洞；订单号相同 = 服务端做了去重。
如果不行：响应里没有订单号，就改用"业务结果计数"判定（第 2 步的核对法）。

#### 第 4 步：测"状态类"重复提交——支付回调重放
很多重复提交藏在支付回调里：支付平台回调接口通知"订单已支付"，服务端不校验回调是否重复，重放回调就重复入账。抓到回调请求后（或构造格式相同的回调）连续重放：

```http
POST /api/pay/callback HTTP/1.1
Host: target.com
Content-Type: application/x-www-form-urlencoded

orderId=20240101001&status=paid&transactionId=TXN123
```

预期结果：订单余额/状态被多次更新，或响应里出现重复入账记录。
如果不行：回调有签名或一次性校验，跳过此步。

#### 第 5 步：记录危害等级并补测变体
重复提交的变体：加请求头重放、URL 参数与 body 同时带订单号、`idempotency-key` 换值重放（服务端若以该 key 做幂等，换 key 即绕过）：

```http
POST /api/withdraw HTTP/1.1
Content-Type: application/json
Idempotency-Key: key-A

{"amount": 100}
# 换 Idempotency-Key: key-B 再发一次，观察是否二次到账
```

预期结果：换 key 后再次成功 → 幂等 key 形同虚设，危害等同于无幂等。
如果不行：key 与用户/请求绑定校验，记录为安全。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 第二次请求直接 401/失效 | 请求里带了前端一次性 token/防重放令牌 | 检查是否每次操作都刷新 token；有的防重放只在登录态，绕过需看令牌生成逻辑 |
| 重放 3 次只有 1 条记录 | 服务端用订单号/请求指纹去重 | 属正常防护，记录"幂等正常"，换接口再测 |
| 响应相同但页面记录多条 | 判定标准错了 | 以业务结果（订单列表/余额）为准，不以响应为准 |
| 重放真的扣了两次钱 | 测试操作有真实资金风险 | 提现/转账类先用最小金额测试，或换签到/领奖类接口 |

#### 实战要点
- 判定铁律：**以业务结果为唯一标准**——订单数、余额、积分变化，不看响应文案
- 同一接口测三种重放：原样重放、换幂等 key 重放、延迟后重放（见 r-concurrency）
- 重复提交常与竞态叠加：并发重放比串行重放更容易绕过"计数型"防护
- 报告里写清楚"重放 N 次产生 M 条记录"，数字比形容词有说服力
- 找目标时优先看：签到、领奖、下单、提现、评价返利、支付回调——都是重放高发区

### [r-concurrency] 并发竞态与时间窗利用 | hard | 竞态;并发 | Race Condition
> 先查后写、非原子校验逻辑在并发下失效，制造重复权益或绕过限制。

#### 这个条目的作用
竞态（Race Condition）的本质：服务端有一段"先查后写"的逻辑，查和写之间有一个时间窗。串行请求下这个时间窗毫秒级过去，看不出问题；但当你让**多个请求同时到达**，它们都能在"写"发生之前通过"查"——于是 10 个请求全部判定"库存还有 1 件"，全部下单成功。这是重复提交的进阶版：重复提交是"同一请求反复发"，竞态是"同一请求同时发"。学会本条目，你能识别典型的非原子逻辑、用 Turbo Intruder 和多线程脚本制造真实并发、验证时间窗。

#### 前置条件
- 一个存在"先查后写"业务的目标（优惠券核销、库存扣减、签到、余额扣减、验证码校验），在授权范围内
- Burp Suite 专业版（含 Turbo Intruder 扩展）或 Python 多线程脚本环境
- 重要认知：**串行重放不是竞态证据**，必须真实并发

#### 第 1 步：找出"先查后写"的竞态点
竞态点都有共同特征：逻辑里存在"查条件 → 通过 → 执行写"。典型场景：

| 场景 | 非原子逻辑 |
|---|---|
| 优惠券/积分 | 先查"是否已使用" → 再标记已用 |
| 库存 | 先查"库存>0" → 再扣减 |
| 余额扣减 | 先读余额 → 再写回新余额 |
| 签到 | 先查"今日已签" → 再写入签到记录 |
| 验证码 | 先校验 code → 再标记已用 |
| 支付状态 | 先查"待支付" → 再置"已支付" |

预期结果：你圈出 1-2 个候选接口（优先选优惠券核销、签到这类"条件检查型"）。
如果不行：没有明显的条件检查型接口，直接按第 2 步用并发验证候选点。

#### 第 2 步：用 Turbo Intruder 制造真实并发（首选工具）
在 Burp 里右键请求 → Extensions → Turbo Intruder，把模板改成并发轰炸：

```python
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=20,
                           pipeline=False)
    for i in range(100):
        engine.queue(target.req, i)

def handleResponse(req, **kwargs):
    table.add(req)
```

预期结果：100 个并发请求中，多个返回成功（优惠券被核销多次 / 库存扣成负数 / 签到记录多条）。
如果不行：全部只有一个成功——服务端用了唯一约束或行锁，记录为防护正常。

> [!warn] Turbo Intruder 的 `concurrentConnections` 是并发连接数，不是循环次数，真正起效的是连接数。

#### 第 3 步：自写 Python 多线程脚本（无 Burp 专业版时）
等价实现：线程 + 屏障让请求同时发出：

```python
import threading
import requests

URL = "http://target.com/api/coupon/use"
COOKIE = {"session": "YOUR_SESSION"}
results = []
barrier = threading.Barrier(30)

def attack(i):
    barrier.wait()
    r = requests.post(URL, cookies=COOKIE,
                      json={"couponId": 5001, "orderId": f"T{i}"}, timeout=10)
    results.append((i, r.status_code, r.text[:60]))

threads = [threading.Thread(target=attack, args=(i,)) for i in range(30)]
for t in threads:
    t.start()
for t in threads:
    t.join()

ok = [r for r in results if "success" in r[2]]
print(f"成功 {len(ok)}/{len(results)} 个")
```

预期结果：成功数 > 1 → 竞态成立；成功数 == 1 → 有并发防护。
如果不行：屏障放行后仍只有一个成功，检查请求是否带了递增参数导致请求不同（见常见错误表）。

#### 第 4 步：时间窗利用——放大竞态窗口
有些竞态窗口太短，普通并发打不进去，但业务给了"宽限期"：比如优惠券核销与订单取消之间、改价与支付之间有时间差。先发第一个请求（触发"查"），延迟 500ms 再发第二个（抢在"写"完成前）：

```python
import time, requests
r1 = requests.post(URL, cookies=COOKIE, json={"couponId": 5001, "orderId": "T1"})
time.sleep(0.5)   # 卡在服务端"查→写"窗口内
r2 = requests.post(URL, cookies=COOKIE, json={"couponId": 5001, "orderId": "T2"})
print(r1.status_code, r1.text[:50])
print(r2.status_code, r2.text[:50])
```

预期结果：两次都成功 → 窗口被利用；第二次失败说明窗口更短，回到第 2/3 步加大并发力度。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 并发后只有一个成功 | 服务端有唯一约束/行锁/乐观锁 | 属正常防护；换"余额扣减"这类无唯一约束的点再测 |
| 请求全部失败/全部成功但无异常 | 请求里带了时间戳或递增序号，每个请求都是"新业务" | 保证并发请求完全同构，参数只改无业务意义的占位 |
| 串行重放多次成功 | 那是重复提交不是竞态 | 先按 r-duplicate 判定，竞态必须并发证明 |
| 数据库层报唯一键冲突 | 防护在数据库约束层 | 记录为"DB 唯一约束兜底"，仍值得报告（应用层缺校验） |

#### 实战要点
- **竞态证据必须是并发**：报告里附上"30 并发中 27 个成功"的截图/日志，串行结果不算数
- 判定成功看业务结果（核销多次、余额变负、库存超卖），不看 HTTP 状态码
- 优先测有"唯一性要求"的点：优惠券、签到、验证码、抽奖——这些天然该幂等
- 竞态常与状态机叠加（见 r-state-machine）；打不进普通竞态时用时间窗方法找宽限期

## [g-method] 越权检测方法论——系统化地找越权，别靠运气

### [m-compare] 接口对比法 | easy | 越权检测;方法论 | -
> 用两个账号对比同一接口的响应，快速定位越权面。

#### 这个条目的作用
越权检测最容易犯的错是"乱试"：登录一个账号，看到 id 就改，改完看运气。接口对比法把这件事变成流水线：**同一接口 × 多个身份 → 对比响应 → 差异即线索**。它不依赖你对业务的理解，只需要两个账号、一次抓包、一次批量重放，是越权检测的第一课，也是后面参数替换法、角色矩阵法的基础。

#### 前置条件
- 目标站支持注册两个及以上账号（同角色即可，权限略有差异更好），在授权范围内
- 如能注册管理员账号（测试环境/靶场），价值更高
- Burp Suite（含 Repeater 或 Intruder），或 Python + requests

#### 第 1 步：准备三个身份：A、B、C
- A、B：普通用户账号，各注册一个，B 账号里预先造一点数据（一条订单、一条个人信息）
- C：管理员账号（能拿到就拿到，拿不到先跳过，用 B 对比 A 已够用）

预期结果：三个账号都已登录，Cookie/Token 已保存，随时可用。
如果不行：无法注册管理员，就先做 A/B 两个普通账号的同角色对比，一样能发现水平越权。

#### 第 2 步：用 A 登录，抓全 A 的全部业务请求
开启 Burp 抓包，用 A 走一遍核心功能：查看个人信息、订单列表、订单详情、修改资料、删除/退出等。把所有带资源 id（uid、orderId、fileId）的请求收集起来，逐个存进 Repeater，按读/写两类分组。

预期结果：你手里有一批"A 身份"的完整请求，且知道每个请求正常返回什么。
如果不行：请求太多分不清，就按读/写两类分批处理。

#### 第 3 步：把 A 的请求逐个换成 B 的 Cookie 重放，对比响应
这是核心动作。对每个请求：只替换 Cookie/Authorization 为 B 的凭证，其余参数不动，重放并记录：

| 请求 | A 的响应 | B 的响应（B 的 Cookie） | 判定 |
|---|---|---|---|
| GET /api/user/1001/profile | 200，A 的数据 | 200，仍是 A 的数据 | 水平越权（B 读到了 A 的数据） |
| GET /api/user/1001/profile | 200，A 的数据 | 403 无权限 | 有校验 |
| GET /api/order/5001/detail | 200，A 的订单 | 200，仍是 A 的订单 | 水平越权 |

预期结果：出现"用 B 的凭证返回 A 的数据"→ 水平越权命中。
如果不行：全部 403/404，说明接口有归属校验，继续下一接口。

> [!tip] 响应对比不只靠肉眼：用 Burp 的 Comparer 比较两次响应，或记录 `状态码 + 响应长度 + 关键字段`，比读全文快得多。

#### 第 4 步：换成 C（管理员）的 Cookie 重放，找垂直越权
把同一批请求的凭证换成 C，重点观察"普通接口的管理员响应"。
预期结果：普通接口用管理员凭证返回了管理字段（用户列表、他人订单、配置项）→ 垂直越权。
如果不行：管理员凭证被拒绝，说明接口有角色校验，记录为安全。

#### 第 5 步：批量跑完整个请求集，产出对比矩阵
别手动一个个点，用脚本或 Burp Intruder 批量跑：同一批请求 × A/B/C 三个身份，输出矩阵。

```python
import requests

requests_list = [
    ("GET", "http://target/api/user/1001/profile"),
    ("GET", "http://target/api/order/5001/detail"),
    ("POST", "http://target/api/user/1001/update"),
]
cookies = {
    "A": {"session": "A_SESSION"},
    "B": {"session": "B_SESSION"},
    "C": {"session": "C_SESSION"},
}

for method, url in requests_list:
    row = []
    for who, ck in cookies.items():
        r = requests.request(method, url, cookies=ck, timeout=10)
        row.append(f"{who}:{r.status_code}/{len(r.content)}")
    print(url, " | ".join(row))
```

预期结果：矩阵中"身份与返回内容不匹配"的格子一目了然，直接作为报告数据。
如果不行：脚本报错先检查 Cookie 格式与请求体（POST 需要带 body，脚本里要补 data）。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 换 Cookie 后全部 401 | Cookie 与 IP/UA 绑定，或凭证格式不对 | 保持同一 UA/IP 环境，检查 Cookie 是否复制完整 |
| 两个账号响应完全相同 | 接口返回的是公共数据，或两个账号数据相同 | 给 B 造差异化数据后再对比；确认 URL 里 id 真的指向 A 的资源 |
| 响应长度没变但内容不同 | 只比长度会漏判 | 长度相同也要抽查响应体，字段值变化同样是越权证据 |
| 分不清是越权还是数据本身公开 | 该接口本来就是公开数据 | 用"未登录"请求做第三对比：未登录也有 → 公开数据，不算越权 |

#### 实战要点
- **三身份基线**：A（自己）→ B（同角色他人）→ C（管理员），每个接口都过三遍
- 判定标准是"身份与返回内容是否匹配"，不是"是否返回 200"
- 用 `状态码/响应长度` 做快速筛选，命中后再看响应体确认数据归属
- 写接口（改资料、删订单）对比价值高于读接口，优先覆盖；可疑点用 m-param-swap、m-role-matrix 深挖

### [m-param-swap] 参数替换法 | medium | 越权检测;参数测试 | -
> 系统化替换请求中的身份/资源参数，发现隐藏校验点。

#### 这个条目的作用
接口对比法回答"哪些接口有越权"，参数替换法回答"**哪些参数**是越权开关"。同一接口里往往藏着多个身份/资源参数：URL 里一个 `id`，body 里一个 `userId`，请求头里一个 `token`——后端校验了其中一个，漏了另一个。本条目给你一份**参数替换清单 + 替换动作清单**，把"改哪个参数、改成什么值"变成打钩的流程，专治"漏测嵌套 id、漏测隐藏身份参数"。

#### 前置条件
- 已用 m-compare 或人工找出 1-2 个可疑接口（建议优先写操作接口）
- 两个账号的凭证（用于替换成"他人 id"）
- Burp Repeater 或 Python requests

#### 第 1 步：把请求拆开，按类别列出所有参数
抓一个可疑请求，把每个参数归类到身份/资源/角色/作用域四类：

```txt
身份: uid userId user_id openid token mobile
资源: id orderId fileId goodsId itemId
角色: role type level isAdmin permission
作用域: tenantId orgId groupId channel storeId
```

```http
POST /api/order/detail HTTP/1.1
Host: target.com
Content-Type: application/json
Cookie: session=A_SESSION

{"orderId": 5001, "userId": 1001, "tenantId": 1}
```

预期结果：你有一份"参数清单"，标出每个参数属于哪一类。
如果不行：参数名不规范（如 `oid`、`fid`），按语义归类即可，重点是别漏参数。

#### 第 2 步：对每个参数执行"值替换集"
对清单里每个参数，依次替换成：另一个账号的值 / 0 / -1 / 空字符串 / 超大值(999999) / 数组 [1,2] / 字符串 "1"，每次记录响应。以 `userId` 为例：

```python
import requests

url = "http://target.com/api/order/detail"
base = {"orderId": 5001, "userId": 1001, "tenantId": 1}
s = requests.Session()
s.cookies.set("session", "A_SESSION")

variants = {
    "他人userId": {**base, "userId": 2002},
    "零值":       {**base, "userId": 0},
    "负值":       {**base, "userId": -1},
    "空":         {**base, "userId": ""},
    "超大值":     {**base, "userId": 999999},
    "数组":       {**base, "userId": [1, 2]},
    "字符串":     {**base, "userId": "1"},
}
for name, body in variants.items():
    r = s.post(url, json=body, timeout=10)
    print(f"{name}: {r.status_code}/{len(r.content)} {r.text[:40]}")
```

预期结果：某个替换值返回了**不同响应**（多出数据、状态码变化）→ 该参数是校验点，深挖。
如果不行：所有替换值响应一致 → 该参数可能未被服务端使用（前端装饰参数），换下一个参数测。

#### 第 3 步：测 body 里的嵌套 id 与数组元素
只替换顶层参数是初学者最常见的漏测。逐层检查 JSON body：

```http
POST /api/order/batch HTTP/1.1
Content-Type: application/json

{"orders": [{"id": 5001, "owner": {"userId": 1001}}]}
```

测试动作：`{"data": {"userId": 2002}}` 嵌套对象替换；`{"ids": [5001, 5002]}` 数组元素逐个替换成他人的；多层嵌套 `{"order": {"user": {"id": 2002}}}`。

预期结果：嵌套/数组替换后返回他人数据 → 嵌套层没有归属校验。
如果不行：嵌套层也校验，继续下一步。

#### 第 4 步：删除身份参数与添加角色参数
- **删参数**：把 userId/Cookie 中的身份字段删掉重放，测是否存在默认值/通配（后端可能"没传就用第一个用户/全部数据"）
- **加角色参数**：在请求里追加 `role=admin`、`isAdmin=true`、`level=9`，测后端是否信任前端传来的角色

预期结果：删参数后返回全量数据，或加角色参数后获得管理能力 → 越权/提权命中。
如果不行：删参数报参数缺失、加角色无变化 → 该接口对参数做了白名单校验。

#### 第 5 步：整理"参数 × 替换值"响应差异表
把每一步的响应记录成表，作为报告附件：

| 参数 | 原值 | 替换值 | 响应差异 | 结论 |
|---|---|---|---|---|
| userId | 1001 | 2002 | 返回他人订单 | 水平越权 |
| tenantId | 1 | 2 | 403 | 作用域校验正常 |
| orderId | 5001 | 0 | 返回全部订单 | 通配漏洞 |

预期结果：差异表齐全，每个可疑点都有响应证据，别凭记忆写结论。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 替换所有值响应都相同 | 参数是前端装饰，后端不用它 | 换参数测；用"删掉该参数看是否报错"判断它是否被后端使用 |
| 只改了 URL 里的 id | body 里的嵌套 id 才是校验主体 | 按第 3 步逐层替换，别只测表层 |
| 数组参数替换后全部报错 | 格式不对（如 id 传了字符串） | 保持原类型替换值：数字字段传数字，字符串字段传字符串 |
| 响应差异被误判为越权 | 响应变化可能是错误提示变化 | 确认变化是"数据内容变化"而非"报错文案变化" |

#### 实战要点
- **四类参数一个不漏**：身份、资源、角色、作用域，每类都过一遍替换值集合
- 替换值集合固定打全：他人值 / 0 / -1 / 空 / 超大 / 数组 / 字符串
- "删参数"与"加角色参数"是隐藏校验点的高发区，务必单测
- 响应差异 = 校验点，但必须区分"数据差异"与"报错差异"
- 与 m-compare 配合：对比法定位接口，替换法定位参数，一纵一横全覆盖

### [m-role-matrix] 角色矩阵与 Token 替换清单 | hard | 越权检测;测试清单 | 权限矩阵测试
> 用角色 × 接口矩阵系统覆盖权限边界，避免漏测。

#### 这个条目的作用
角色矩阵法把测试变成**网格**：横轴是角色（匿名、普通用户、管理员、其他租户），纵轴是接口（用户信息、订单管理、用户管理、配置管理），每个格子 = "这个角色调用这个接口"的预期与实测。它解决两个问题：一是**漏测**——哪些角色 × 接口组合没测过一目了然；二是**报告说服力**——一张填好的矩阵表直接就是漏洞证据。同时配套 Token/Cookie 替换清单，把凭证维度的绕过也测全。

#### 前置条件
- 目标站可注册/获取多个角色账号：至少匿名（未登录）、普通用户 A、管理员 C；多租户场景加"另一租户账号 D"
- 目标接口清单：把核心接口按功能分类（读/写、用户域/订单域/管理域）
- 一张表格工具（Excel/Notion/Markdown 表格均可）

#### 第 1 步：列出角色清单（横轴）
先明确你手里有哪些身份，每个身份记录凭证：匿名（无 Cookie）、普通用户 A/B（session=A/B，B 用于交叉替换）、管理员 C（session=C，后台权限，能拿就拿）、其他租户 D（session=D，多租户场景）。

预期结果：每个角色有可用的凭证，能随时切换。
如果不行：拿不到管理员就先用匿名 + 普通用户 A/B 三行，矩阵照样能测水平越权。

#### 第 2 步：列出接口清单（纵轴）
把目标接口按功能域分组，写进矩阵纵轴：

```txt
用户域:   个人信息查询 / 修改资料 / 删除账号
订单域:   下单 / 订单详情 / 退款 / 发货(管理)
管理域:   用户列表(管理) / 配置修改(管理) / 数据统计(管理)
```

预期结果：纵轴有 8-15 个代表性接口，覆盖读和写。
如果不行：接口太少就加参数变体（同一接口不同参数算多行），保持矩阵有密度。

#### 第 3 步：建矩阵表，先填"预期"列
矩阵建好后**先填预期再测试**，防止漏格：

| 角色 \ 接口 | 用户信息 | 订单详情 | 用户列表(管理) | 配置修改(管理) |
|---|---|---|---|---|
| 匿名 | 拒绝 | 拒绝 | 拒绝 | 拒绝 |
| 普通用户 A | 200 | 200(自己的) | 拒绝 | 拒绝 |
| 管理员 C | 200 | 200 | 200 | 200 |

预期结果：每个格子都有预期值（200 或拒绝）；拿不准的格子标"?"，测试后回填。

#### 第 4 步：逐格实测，回填矩阵
按行遍历：先匿名把所有接口过一遍，再 A、再 C。每个格子真实发一次请求：

```python
import requests

matrix = [
    ("匿名", "用户信息", "GET", "http://target/api/user/1001/profile", None),
    ("A",    "用户信息", "GET", "http://target/api/user/1001/profile", {"session": "A"}),
    ("A",    "用户列表", "GET", "http://target/api/admin/user/list",    {"session": "A"}),
    ("C",    "用户列表", "GET", "http://target/api/admin/user/list",    {"session": "C"}),
]
for role, api, method, url, ck in matrix:
    r = requests.request(method, url, cookies=ck, timeout=10)
    print(f"{role:6s} {api:12s} {r.status_code} {len(r.content)} {r.text[:30]}")
```

判定规则：**预期拒绝实际 200 → 漏洞**；预期 200 实际 403 → 记录异常（可能是接口路径变了）。

预期结果：矩阵填满，标注出"拒绝预期但返回 200"的格子。
如果不行：某接口对匿名返回 200 但内容为空——区分"公开数据"与"越权"，见常见错误表。

> [!tip] 每个格子顺手记 `状态码 + 响应长度`，回填矩阵时空格不再出现"没测过"。

#### 第 5 步：Token/Cookie 替换清单——凭证维度全测
矩阵测的是"角色对接口"，这一步测"凭证本身的可伪造性"。对任一关键接口（如用户信息），逐项执行：

| 测试项 | 操作 | 预期 |
|---|---|---|
| 无凭证 | 删掉 Cookie/Authorization 直接请求 | 401/403 |
| 错误凭证 | 填 `session=1`、伪造 JWT | 401/403 |
| 他人凭证 | 用 B 的 Cookie 访问 A 的资源 | 403（200 则越权） |
| 过期凭证 | 用已注销/过期的 token | 401/403 |
| 只留一半 | 删掉 Cookie 里的 role 字段只留 session id | 无降权 → 权限在客户端 |
| Token 类型混淆 | JWT 放 Cookie、Bearer 与 Cookie 互换 | 无变化 → 解析混乱 |
| 大小写/编码 | token 加空格、URL 编码、大小写变体 | 无变化 → 容错过宽 |

预期结果：任一"应拒绝"的测试返回 200 → 凭证校验缺失。
如果不行：全部按预期拒绝 → 凭证维度安全，记录结论。

#### 第 6 步：产出矩阵报告
把矩阵表 + 漏洞格子证据整理成报告附件：角色 × 接口矩阵总表（预期 vs 实测，漏洞格标红）、每个漏洞格的请求 + 响应（状态码/长度/关键字段）、凭证测试结果表、漏洞清单按危害排序。

预期结果：报告里矩阵表 + 证据齐全，可直接提交；矩阵表的每个红格都有对应请求响应。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 匿名访问返回 200 空数据 | 接口对未登录返回空列表（公开空态） | 对比登录态的返回，确认不是越权而是正常空态 |
| 管理员格子全是 200 | 测试环境管理员无鉴权或接口本就公开 | 用"匿名也 200"交叉验证，区分公开接口与越权 |
| 矩阵太大测不完 | 接口数量失控 | 优先覆盖写接口与高价值数据接口，读接口抽样 |
| 越权格复现不了 | 依赖前置状态（如订单属于 A） | 用 A 先造数据，再用其他角色凭证访问该数据 |

#### 实战要点
- **先填预期后测试**：预期列让"漏测"无处可藏，也让报告"预期 vs 实测"更有说服力
- 矩阵优先测**写接口**（改配置、删数据）和高价值读接口（用户列表、订单全量）
- 凭证测试清单里，"只留一半""类型混淆""编码变体"是初学者最容易漏的三项
- 一张填好的矩阵表 = 报告附件核心，比文字描述强十倍
- 矩阵法与 m-compare、m-param-swap 是递进关系：矩阵定范围、对比定接口、替换定参数，三件套全做才叫系统化
