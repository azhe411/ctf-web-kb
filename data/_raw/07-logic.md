## [g-horizontal] 水平越权——只校验了登录，没校验"这是你的"

### [h-idor-principle] 水平越权原理与前提 | medium | 水平越权;IDOR | 对象级授权缺失
> 后端只验证"已登录"，未验证资源归属，导致任意用户可读写他人数据。

#### 原理
水平越权（IDOR，Insecure Direct Object Reference）的本质：**服务端把对象 ID 当成了访问凭证的一部分**。攻击者登录后拿到一个合法会话，然后替换请求中的资源 ID（用户 id、订单号、文件编号、租户号），服务端只校验"请求者已登录"就返回数据。

#### 前提条件（满足越多越可能中招）
| 前提 | 判断方法 |
|---|---|
| 资源 ID 可预测 | 自增数字 id、连续订单号、时间戳拼接 |
| ID 在请求中明文传递 | URL 路径 `/api/user/10086/info`、GET 参数、JSON body |
| 服务端不做归属校验 | 换 id 后响应内容变化即中招 |
| 同一接口供所有角色使用 | 没有按角色区分接口 |

#### 典型特征
- 接口路径语义：`/api/user/{id}/profile`、`/api/order/{orderId}/detail`
- 参数名常见：`id`、`uid`、`userId`、`orderId`、`fileId`、`groupId`、`tenantId`

> [!tip] 先看响应差异：把 id 换成别人的，响应体字段变多/变少、出现"无权访问"以外的内容，都是归属校验缺失的信号。

### [h-idor-detect] IDOR 检测流程 | medium | IDOR;越权检测 | 遍历
> 从功能点出发，系统化替换资源标识，用响应差异判定越权。

#### 检测流程
1. **找入口**：登录两个账号 A/B（无权限差异即可），抓取所有携带资源 id 的请求
2. **确认基线**：用 A 访问 A 的资源，记录正常响应（200 + 完整数据）
3. **替换 ID**：把 A 的请求中 id 换成 B 的（或换成一个不存在的 id），观察：
   - 返回 B 的数据 → 水平越权（读）
   - 返回 200 但数据为空 → 可能是软删除/权限过滤，需进一步验证
   - 返回 403/404 → 有校验，继续找其他参数
4. **遍历验证**：用不存在 id 测是否存在通配/全量返回（如 `id=0`、`id=all`、省略 id）
5. **写接口同样测**：PUT/DELETE 改别人订单、删别人文件，危害更高

> [!warn] 检测时避免直接修改真实业务数据，先读后写，写操作要准备回滚或使用测试账号数据。

#### 常见遗漏点
- 只测了 GET，没测 POST/DELETE
- 只替换了路径参数，没替换 body 里的嵌套 id（如 `{"order": {"id": 2}}`）
- 多级资源：`/api/order/2/user/3`，两个 id 都要替换
- 批量接口：`/api/order?ids=1,2,3` 中的数组元素

### [h-idor-bruteforce] 批量遍历脚本思路 | hard | IDOR;脚本编写 | IDOR 遍历
> 用脚本批量遍历连续 ID，通过响应长度/状态码差异自动标记越权点。

#### 脚本思路
1. **先手动确认一个可越权的 ID 样本**（如 id=1001 能读到他人数据）
2. **确定 ID 空间**：自增则从 1 遍历；订单号带时间戳则收集已知订单号样本
3. **响应差异化判定**：每个响应记录 `status_code + content_length + 关键字段值`
4. **过滤噪声**：未登录/空数据响应长度固定，可与真实数据长度区分

#### 参考脚本
```python
import requests

BASE = "http://target/api/user/{uid}/profile"
s = requests.Session()
s.headers["Cookie"] = "session=YOUR_SESSION"

def grab(uid):
    r = s.get(BASE.format(uid=uid), timeout=5)
    return r.status_code, len(r.content), r.text[:50]

# 先取基线
base = grab(10000)
print("baseline:", base)

for uid in range(10000, 10050):
    st, ln, head = grab(uid)
    # 长度显著不同 且 状态码为 200 → 疑似越权
    if st == 200 and abs(ln - base[1]) > 50:
        print(f"[HIT] uid={uid} len={ln} head={head}")
```

> [!tip] 控制速率：加 `time.sleep(0.2)` 或随机间隔，避免触发频率限制和封禁；大批量遍历前先确认目标授权范围内。

## [g-vertical] 垂直越权——普通用户调了管理员接口

### [v-role-model] 角色判断与权限模型 | easy | 垂直越权;权限模型 | 提权
> 权限只在前端或单一字段上区分，后端没有独立鉴权模型。

#### 原理
垂直越权的本质：**服务端没有按角色独立校验权限**，权限判断依赖前端隐藏按钮、路由守卫、或一个可篡改的角色字段。

#### 常见权限模型缺陷
| 缺陷 | 表现 |
|---|---|
| 角色写在前端 | localStorage 存 `isAdmin: true`，改掉即提权 |
| 角色在 Cookie/JWT 明文 | Cookie 里 `role=user` 改成 `admin`；JWT 未签名验证 |
| 接口无角色校验 | 前端没展示管理入口，但接口存在且任何人可调 |
| 只校验"是否登录" | 登录即全权限，管理员/普通用户共用接口 |

#### 确认角色机制
- 登录响应里找 `role`/`isAdmin`/`level`/`permission` 字段
- 抓包看请求头、Cookie、JWT payload 里是否带角色
- 注册接口看能否传 `role=admin` 参数

> [!warn] JWT 场景：先验签（alg 是否为 none、密钥是否泄露），别一上来就改 payload——改完要能通过服务端验签才算漏洞。

### [v-admin-api] 普通用户调 admin 接口 | medium | 垂直越权;接口测试 | -
> 接口文档或 JS 中暴露管理接口，普通用户直接调用即提权。

#### 检测方法
1. **找管理接口**：前端 JS 里搜 `admin`、`manage`、`console`、`/api/v1/` 路径
2. **看接口文档**：Swagger（`/swagger-ui.html`、`/v2/api-docs`）、`/api-docs`、`/openapi.json`
3. **参数猜测**：把普通接口 URL 中的 `user` 换成 `admin`，`get` 换成 `manage/delete`
4. **验证**：普通用户 Cookie 直接请求管理接口，返回 200 即中招

```http
GET /api/admin/user/list HTTP/1.1
Host: target.com
Cookie: session=普通用户会话
```

```http
GET /api/user/delete?id=1 HTTP/1.1
Host: target.com
Cookie: session=普通用户会话
```

> [!tip] 批量测试：把已抓到的普通接口列表，用脚本替换路径关键词（user→admin、list→delete、v1→v2）再批量请求，比较状态码与响应长度。

#### 隐藏接口发现清单
| 位置 | 关键词 |
|---|---|
| JS 文件 | `admin`、`manage`、`backstage`、`internal` |
| 接口文档 | swagger、api-docs、openapi、graphql |
| 参数猜测 | debug、test、backdoor、dev |
| 响应头/注释 | HTML 注释里的接口说明、JS 里 baseURL 常量 |

### [v-frontend-bypass] 前端鉴权绕过 | easy | 前端鉴权;路由守卫 | -
> 权限控制全部在前端路由守卫，直接请求后端接口即绕过。

#### 原理
SPA 应用用前端路由守卫控制页面访问（如 Vue Router `beforeEach` 检查 `isAdmin`），但**所有数据接口都裸露在后端且无鉴权**，绕过前端即可访问管理页面数据。

#### 绕过方式
| 方式 | 操作 |
|---|---|
| 直接调接口 | 用 curl/Postman 直接请求管理接口，不经过前端路由 |
| 改前端状态 | localStorage/sessionStorage 里写入 `isAdmin=true` 再刷新 |
| 改路由 | 手动改 URL 到 `/admin`，若路由守卫只在前端，页面能渲染但接口仍要后端放行 |
| 抓包改响应 | 拦截登录接口响应，把 `role: "user"` 改成 `"admin"` 后放行 |

> [!warn] 前端鉴权绕过本身不是漏洞，必须验证**后端接口是否真的无鉴权**：改完前端状态后直接调管理接口，200 才是漏洞。

## [g-authflow] 注册登录逻辑——认证流程的每一步都可能被绕

### [a-register-overwrite] 注册覆盖与批量注册 | hard | 注册逻辑;账号覆盖 | 同名注册
> 注册逻辑未校验用户名唯一性或未加验证，可覆盖已有账号或批量灌号。

#### 覆盖管理员（同名注册）
- 原理：注册接口查重逻辑缺陷——先查"用户名是否存在"，不存在才插入，但**并发下两条同名注册都通过查询**；或注册时直接 INSERT OR REPLACE
- 触发条件：
  - 管理员账号在另一张表/另一套逻辑维护，注册表没有该用户名 → 注册同名 `admin` 成功
  - 注册接口允许指定 `username` 且服务端未查重
- 验证：注册 `admin`，若提示"用户名已存在"则无覆盖；若成功则直接登录该账号

> [!danger] 覆盖管理员是最严重的注册漏洞：直接获得管理员账号控制权。发现后立即停止进一步操作，走报告流程。

#### 批量注册
- 注册接口无验证码、无频率限制 → 脚本循环注册，消耗资源、灌爆用户表、用于后续撞库
- 检测：注册 2-3 个连续账号，观察是否有限制；有验证码则看是否可复用（同一验证码多次提交）

```bash
# 循环注册（假设无验证码、无频控）
for i in $(seq 1 20); do
  curl -s -X POST http://target/api/register \
    -d "username=test$i&password=123456" -o /dev/null -w "%{http_code}\n"
done
```

### [a-verify-bypass] 邮箱/手机验证绕过 | medium | 验证码绕过;认证逻辑 | 验证码不校验
> 验证码校验不严：不校验、可爆破、回显响应、或校验与使用分离。

#### 绕过方式
| 方式 | 原理 | 测试 |
|---|---|---|
| 不校验验证码 | 接口只收 code 参数但服务端不比对 | 随便填 0000，看是否通过 |
| 万能验证码 | 固定值（如 000000）或 `code=0000` 特判 | 逐个尝试常见固定值 |
| 不失效 | 同一验证码可重复使用多次 | 用同一 code 连续提交 |
| 回显在响应 | 验证码直接放在响应体/响应头里 | 抓注册/发送验证码接口的响应 |
| 空值绕过 | `code=` 空字符串或省略字段被当作通过 | 删除 code 字段重放 |
| 校验与使用分离 | 先调 A 接口校验，再调 B 接口注册（B 不校验） | 跳过校验接口直接调注册 |

> [!tip] 短信验证码测试清单：0/000000/123456/888888/999999、`code=null`、`code=""`、`code` 缺失、发送接口响应体、错误次数不累计。

#### 绕过链示例
```http
POST /api/register HTTP/1.1
Content-Type: application/json

{"phone": "13800000000", "code": "000000", "password": "x"}
```
若返回成功 → 验证码未校验或存在万能码。

### [a-login-reset] 登录限制与密码重置链 | medium | 爆破防护;密码重置 | 登录爆破绕过
> 登录次数限制可绕过；密码重置流程存在验证码/回显/竞态缺陷。

#### 登录次数限制绕过
| 绕过方式 | 说明 |
|---|---|
| X-Forwarded-For 伪造 | 服务端按 IP 计数，改 XFF/X-Real-IP 即换计数 |
| 换参数 | 把 `XFF: 1.1.1.1` 换成随机 IP 循环 |
| 大小写/前后空格 | 用户名 `admin` vs `Admin` 触发不同计数 |
| 并发绕过 | 限制是"同账号错误 5 次锁定"，并发请求同时提交绕过计数（看 g-race） |
| 接口不统一 | 登录接口 A 有限制，另一个登录接口 B 没有 |

```http
POST /api/login HTTP/1.1
X-Forwarded-For: 1.2.3.4
Content-Type: application/x-www-form-urlencoded

username=admin&password=wrong1
```

> [!tip] 爆破前先确认限制机制：锁定是锁 IP 还是锁账号、锁定多久、验证码是否随错误次数出现。锁定账号比爆破危害更大，先测自己的账号。

#### 密码重置链
1. **验证码回显**：发送重置验证码接口的响应体/Set-Cookie 里带 code
2. **重置逻辑缺陷**：重置成功后 session 不失效、旧密码仍可登录
3. **参数污染**：重置时改 `username` 字段为他人账号，验证码是自己的
4. **竞态**：校验 code 与更新密码分离，校验后立即并发修改 username
5. **响应差异**：`该账号不存在` vs `验证码错误` 提示差异泄露账号存在性

## [g-payment] 支付与订单——金额和状态都别信前端

### [p-amount-tamper] 金额与数量篡改 | medium | 金额篡改;支付逻辑 | 0 元购
> 订单金额由前端提交且服务端不重新计算，篡改金额/数量即低价购买。

#### 篡改方式
| 方式 | 操作 | 判定 |
|---|---|---|
| 金额改为 0/负数 | 下单时改 `amount`、`price`、`total` 字段 | 支付 0 元或收到负数退款 |
| 数量为负 | 改 `quantity=-1`，总价计算错误或库存逻辑异常 | 下单成功且金额异常 |
| 小数精度 | `0.01` 改 `0.001` 或 `1e-10`，精度丢失后金额为 0 | 支付金额与商品不符 |
| 隐藏字段 | body 里带 `discount`、`couponAmount`、`isFree` 等字段 | 直接置 0 或 true |
| 越权改价 | 购物车/改价接口未鉴权，先改价再下单 | 改价接口 200 |

> [!warn] 核心验证点：**最终支付金额必须是服务端按商品单价 × 数量重新计算的结果**。前端传的任何价格字段都值得测。

```http
POST /api/order/create HTTP/1.1
Content-Type: application/json

{"itemId": 1001, "quantity": 1, "price": 0.01, "total": 0.01}
```

#### 测试思路
1. 正常下单抓包，找到所有金额相关字段
2. 逐个篡改为 0、负数、极小值、超长小数，观察是否下单成功
3. 关注支付回调：支付成功后服务端是否重新校验金额
4. 检查"改价接口"：购物车修改价格、订单改价、优惠计算接口是否可越权调用

### [p-coupon-points] 优惠券复用与积分刷取 | medium | 优惠券;积分逻辑 | 薅羊毛
> 优惠券一次性校验缺失、积分发放可重放，造成重复薅取。

#### 优惠券复用
| 缺陷 | 表现 |
|---|---|
| 不标记已使用 | 同一券码可反复下单 |
| 前端控制使用状态 | 取消订单后优惠券状态不还原/还原逻辑缺陷 |
| 并发使用 | 同一券同时下单多笔（看 g-race） |
| 券码可枚举 | 优惠券号自增/可遍历 |

#### 积分刷取
- 积分接口未做幂等：重复调用签到/邀请/评价接口，积分累加
- 邀请逻辑缺陷：自己邀请自己（换账号/并发）刷邀请积分
- 负数积分：积分可被扣成负数后购买（服务端未校验余额下限）

> [!tip] 测试幂等：同一请求重复发送 3-5 次，积分/余额变化超过一次即存在重放缺陷。邀请场景记得测"邀请自己"。

### [p-zero-cost] 并发 0 元购思路 | hard | 并发;支付逻辑 | 竞态薅羊毛
> 通过并发绕过库存/金额/状态校验，实现 0 元购或超卖。

#### 原理
订单状态机校验（库存扣减、金额校验、状态流转）不是原子的：先查后写、查库存和扣库存分离，并发请求都能通过"查"阶段。

#### 0 元购思路
| 思路 | 说明 |
|---|---|
| 并发下单抢库存 | 库存 1 件，并发 10 个下单请求，多个成功 |
| 并发支付同一订单 | 订单状态"待支付"→"已支付"流转无锁，重复回调 |
| 支付回调重放 | 回调接口不校验订单状态/签名，重复发送支付成功通知 |
| 并发改价+下单 | 改价接口与下单接口间的时间窗内并发 |
| 并发撤销+使用 | 优惠券状态在"使用"与"撤销"之间并发竞争 |

#### Turbo Intruder 思路
```python
# Turbo Intruder 模板思路（实际运行在 Burp Turbo Intruder 扩展）
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=10,
                           pipeline=False)
    for i in range(50):
        engine.queue(target.req, i)

def handleResponse(req, **kwargs):
    table.add(req)
```

> [!tip] 竞态验证要点：并发请求必须**同时到达**服务端。本地测试用 Turbo Intruder / 多线程脚本，不要把串行重放当竞态证据。成功标志是"多个请求都返回成功"或"数据出现不一致"。

## [g-captcha] 验证码与频率——验证码和限流都可能形同虚设

### [c-sms-bomb] 短信轰炸 | easy | 短信轰炸;频率限制 | 短信接口轰炸
> 短信发送接口无频率限制或限制可绕过，可对任意手机号批量发送短信。

#### 检测
1. 找到短信发送接口（注册、登录、找回密码、绑定手机）
2. 连续发送 3-5 次，观察是否有间隔/次数限制
3. 有 IP 限制则测 XFF 伪造；有限制测不同参数（换手机号格式 `+86`、`86`、空格）

#### 限制绕过方式
| 方式 | 说明 |
|---|---|
| XFF/X-Real-IP 伪造 | 按 IP 计数时换 IP 头 |
| 参数变体 | 手机号加空格、+86、0 前缀，绕过去重 |
| 换接口 | 注册/登录/找回三个接口共用同一短信服务，各自计数 |
| 并发 | 限制是"60 秒 1 条"，并发 10 个请求同时通过 |

> [!warn] 短信轰炸验证点到"确认存在"即可，**不要真的对他人手机号大规模轰炸**——发送几十条即可能触发运营商投诉与法律风险。

```http
POST /api/sms/send HTTP/1.1
Content-Type: application/json
X-Forwarded-For: 10.0.0.1

{"phone": "13800000000", "scene": "register"}
```

### [c-sms-crack] 验证码爆破 | medium | 验证码爆破;短信验证码 | 验证码枚举
> 验证码位数短、不限制错误次数、不失效，可暴力枚举。

#### 爆破前提
| 前提 | 判断 |
|---|---|
| 位数短 | 4 位（10000 组合）或 6 位纯数字 |
| 无次数限制 | 连续错误 10 次仍不锁定 |
| 不失效 | 过期时间长或发送后一直有效 |
| 回显 | 响应体、响应头、Set-Cookie 里带验证码 |

```python
import requests

url = "http://target/api/verify"
# 4 位纯数字验证码爆破
for code in range(10000):
    r = requests.post(url, json={"phone": "13800000000", "code": f"{code:04d}"})
    if r.status_code == 200 and "success" in r.text:
        print(f"CODE: {code:04d}")
        break
```

> [!tip] 爆破前先用 3-5 个错误 code 确认"无锁定、无延迟"，再决定是否值得爆破。6 位数字 100 万次请求需要更高带宽，先测限制再投入。

### [c-image-captcha] 图形验证码绕过 | medium | 图形验证码;OCR | -
> 图形验证码可 OCR、可复用、可空值绕过，或校验在前端。

#### 绕过方式
| 方式 | 说明 |
|---|---|
| OCR 识别 | 简单数字/字母验证码用 tesseract 或在线 OCR 识别 |
| 复用 | 同一验证码值可多次提交（服务端不标记已用） |
| 前端校验 | JS 里写死答案或前端生成验证码，后端不校验 |
| 空值/固定值 | `captcha=` 空、`captcha=0000`、删字段 |
| 随响应返回 | 图片 URL 或答案出现在响应里 |
| 逻辑缺陷 | 先提交"错误验证码"触发某分支，再正常提交绕过 |

> [!warn] OCR 成功率低的验证码（扭曲、干扰线、中文）优先测复用/空值/前端校验，OCR 是最后手段。

```txt
测试顺序：空值 → 固定值 → 复用 → 前端校验 → 响应回显 → OCR
```

## [g-race] 状态机与竞态——业务逻辑不是原子的

### [r-state-machine] 订单状态跳变与越步操作 | hard | 状态机;订单逻辑 | 越步操作
> 订单状态流转无严格校验，可跳过中间状态直达终态。

#### 原理
订单状态机（待支付→已支付→已发货→已完成）每个转换都应有前置状态校验。若服务端只做"目标状态"判断（如"只有待支付可支付"用 `if status == 1` 而状态 2/3 也能支付），则状态可跳变。

#### 越步操作
| 操作 | 原理 |
|---|---|
| 跳过支付直接发货 | 调用"发货"接口不校验订单是否已支付 |
| 未支付先退款 | 退款接口只校验订单号存在 |
| 取消已发货订单 | 取消接口不校验状态 |
| 重复完成 | 已完成订单可再次"完成"触发二次结算 |

```http
POST /api/order/refund HTTP/1.1
Content-Type: application/json

{"orderId": "20240101001"}   # 未支付/已发货订单也能退款？
```

> [!tip] 拿到订单接口清单后，先画状态机（哪些状态存在、哪些转换合法），再对每个接口测试"非预期状态转换"。

### [r-duplicate] 重复提交 | easy | 重复提交;幂等 | -
> 下单/提现/转账等接口无幂等，同一请求重复发送多次产生多次业务。

#### 检测
1. 正常下单抓包
2. 用相同请求连续发送 2-3 次
3. 观察是否生成多个订单/多次扣款/多次发放

#### 常见场景
- 下单：同一请求发送两次 → 两个订单（或一个订单扣两次款）
- 提现/转账：重复提交 → 多次转账
- 签到/领奖：重复提交 → 多次领取
- 支付回调：支付平台回调重放 → 订单重复入账

> [!tip] 服务端幂等方案应是订单号/请求 ID 唯一约束。测试时观察响应中的订单号：两次响应订单号相同（幂等）还是不同（漏洞）。

```http
POST /api/withdraw HTTP/1.1
Content-Type: application/json

{"amount": 100, "account": "bank_account"}
# 连续发送两次，若到账 200 即重复提交漏洞
```

### [r-concurrency] 并发竞态与时间窗利用 | hard | 竞态;并发 | Race Condition
> 先查后写、非原子校验逻辑在并发下失效，制造重复权益或绕过限制。

#### 典型竞态点
| 场景 | 竞态逻辑 |
|---|---|
| 优惠券/积分 | 先查"是否已使用"再标记 → 并发都查到未使用 |
| 库存 | 先查"库存>0"再扣减 → 并发超卖 |
| 余额扣减 | 先读余额再写 → 并发覆盖更新（余额丢失/变负） |
| 签到 | 先查"今日已签"再写入 → 并发重复签到 |
| 验证码 | 先校验 code 再标记已用 → 并发共用同一验证码 |
| 支付状态 | 先查"待支付"再置"已支付" → 并发重复支付 |

#### 利用方法（Turbo Intruder 思路）
```python
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=20,
                           pipeline=False)
    for i in range(100):
        engine.queue(target.req, i)
```

#### 时间窗利用
- 有些逻辑存在"宽限期"：如优惠券核销与订单取消之间、改价与支付之间
- 检测：正常操作与触发操作之间插入延迟（如先发请求再延迟 500ms 发第二个），找到非原子窗口

> [!warn] 竞态验证必须**真实并发**（多连接同时到达），串行重放出现多次成功只是重复提交不是竞态。用 Turbo Intruder、自写多线程脚本或 race 工具验证。

## [g-method] 越权检测方法论——系统化地找越权，别靠运气

### [m-compare] 接口对比法 | easy | 越权检测;方法论 | -
> 用两个账号对比同一接口的响应，快速定位越权面。

#### 流程
1. 准备账号 A、B（同角色，最好权限略有差异）、管理员账号 C
2. A 登录抓全部业务请求（登录、读数据、写数据）
3. 逐个请求换成 B 的 Cookie 重放，对比响应
4. 换成 C 的 Cookie 重放，找"普通接口管理员响应"

#### 对比维度
| 维度 | 关注点 |
|---|---|
| 状态码 | 200 vs 403 是否与身份匹配 |
| 响应长度 | 换身份后长度变化说明返回了不同数据 |
| 响应字段 | 是否出现他人数据/管理字段 |
| 响应时间 | 命中真实数据的接口通常更慢 |

> [!tip] 用 Burp 的"请求替换 + 对比器"或自写脚本批量跑：同一请求体 × 三个身份，输出状态码/长度矩阵。

### [m-param-swap] 参数替换法 | medium | 越权检测;参数测试 | -
> 系统化替换请求中的身份/资源参数，发现隐藏校验点。

#### 替换清单
```txt
身份: uid userId user_id openid token
资源: id orderId fileId goodsId
角色: role type level isAdmin
作用域: tenantId orgId groupId channel
```

#### 测试动作
1. 把参数值换成：另一个账号的值、0、-1、空、超大值、数组 `[1,2]`、JSON 嵌套
2. body 里的嵌套 ID 也要替换：`{"data": {"userId": 2}}`
3. 删除身份参数，测是否存在默认值/通配
4. 角色参数加进请求：`role=admin`、`isAdmin=true`

> [!warn] 记录每次替换的响应（状态码+长度+关键字段），响应差异 = 校验点。响应相同也可能都是越权（都返回数据），要对比数据归属。

### [m-role-matrix] 角色矩阵与 Token 替换清单 | hard | 越权检测;测试清单 | 权限矩阵测试
> 用角色 × 接口矩阵系统覆盖权限边界，避免漏测。

#### 角色矩阵
| 角色 \ 接口 | 用户信息 | 订单管理 | 用户管理 | 配置管理 |
|---|---|---|---|---|
| 匿名 | ? | ? | ? | ? |
| 普通用户 | ? | ? | ? | ? |
| 管理员 | ? | ? | ? | ? |
| 其他租户 | ? | ? | ? | ? |

每个格子实际请求一遍，预期是"越权返回 403，合法返回 200"，实际返回 200 即漏洞。

#### Token/Cookie 替换测试清单
| 测试项 | 操作 |
|---|---|
| 无凭证 | 删掉 Cookie/Authorization 直接请求 |
| 错误凭证 | 随便填 session=1、伪造 JWT |
| 他人凭证 | 换账号 B 的 Cookie 访问 A 的资源 |
| 过期凭证 | 用已注销/过期 token |
| 只留一半 | 删掉 Cookie 中部分字段（如只留 session id 删 role） |
| Token 类型混淆 | JWT 当 Cookie、Bearer 与 Cookie 互换 |
| 大小写/编码 | token 加空格、URL 编码、大小写变体 |

> [!tip] 矩阵法产出直接可用作报告附件：一张"角色 × 接口"表格，标出哪些格子存在越权，比文字描述更有说服力。
